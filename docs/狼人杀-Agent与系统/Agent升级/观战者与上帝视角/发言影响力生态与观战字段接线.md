## U1: 发言影响力生态（Influence Score）

### 设计理念

当前系统里，「发言」的唯一后果是「被别人读到」。一个 Agent 说了极有洞察力的话，
和说了一句废话，在系统层面完全等价 —— 没有任何字段记录「这句话改变了什么」。

影响力生态把「发言的后果」量化：每轮结束后，系统按 4 个**完全公开、可复算**的信号，
为每个座位计算 0~100 的影响力分数。分数进入 Agent 的 GameContext，成为决策输入；
也进入 `ClientGameState`，成为观战者可见的徽章。

### 核心价值

- **社交资本游戏化**：影响力 =「第二血量」。低影响力的预言家跳身份没人信；高影响力的狼人悍跳更容易成功。
- **LLM 策略深度**：Agent 能看到「我说的话有没有用」，从而调整发言策略（继续跟票 vs 主动带节奏）。
- **动态平衡**：影响力高的玩家自然成为焦点，被查验/被刀/被道具攻击的概率上升 —— 形成负反馈。
- **观赏性**：观众一眼看出「谁在主导这局」。

### 四个信号（公式完全公开）

所有信号都只用**已经存在的房间级数据**，不新增任何采集点。

| 信号 | 权重 | 数据来源 | 计算 |
|---|---|---|---|
| **跟票率**（Persuasion）| 40 | `GameState.LastDayVoteMap`（`engine.go:342`）| 上一轮白天，有多少人的投票目标与本座位一致（不含本人）。`跟随人数 / (存活数-1)` |
| **关注度**（Attention）| 25 | `whisperInbox`（`room.go:158`）+ `propHistory`（`room.go:347`）| 本座位作为 whisper 收件人 / 道具目标被指向的次数，对数归一 |
| **发言参与**（Presence）| 20 | `recentSpeeches`（`room.go:134`）| 本座位在最近 50 条发言缓冲中的占比 |
| **存活加成**（Survival）| 15 | `Player.Alive` + `DayNumber` | 存活轮数占比；死亡后影响力冻结不再增长 |

**设计约束：公式必须公开透明。** 分数写入 system prompt 时附带公式说明，
避免 Agent 把它当成不可知的黑箱而产生迷信行为。**不使用任何需要 LLM 判断的信号**
（如「发言质量」），保证 13 个座位在同一把尺子下被度量（§120 公平性）。

### 实现方案

#### 1. 新模块 `ServerGo/game/werewolf/influence_tracker.go`（≤300 行）

```go
package werewolf

// influence_tracker.go — 发言影响力生态（§20260811-02 U1）
//
// §92a 锁约束：所有方法均为 *Locked 语义（调用方必须已持 r.mu）。
//   RecalculateInfluenceLocked 由 fillDayVoteMapLocked 末尾调用（已持锁）。
//   **绝不**提供会自行加锁的公开变体 —— R212 的教训：被 BuildClientState*
//   家族调用的方法默认必须是 *Locked。
// §119 协议层隔离：影响力是**公开**信息（与 HeartThought 相反），
//   全房 + 观战者可见，写入 ClientGameState。
// §120 公平性：公式不含任何 LLM 判断信号，13 座位同一把尺子。

// InfluenceScore 一个座位的影响力明细（分项公开，便于前端 tooltip 与复算）。
type InfluenceScore struct {
    Seat       int `json:"seat"`
    Total      int `json:"total"`      // 0~100
    Persuasion int `json:"persuasion"` // 0~40
    Attention  int `json:"attention"`  // 0~25
    Presence   int `json:"presence"`   // 0~20
    Survival   int `json:"survival"`   // 0~15
}

// InfluenceTracker 房间级影响力存储。懒初始化，与 infoLedger / hypothesisStore 同模式。
type InfluenceTracker struct {
    scores map[int]*InfluenceScore
    round  int
}

func NewInfluenceTracker() *InfluenceTracker
func (t *InfluenceTracker) GetLocked(seat int) *InfluenceScore
func (t *InfluenceTracker) SnapshotLocked() []InfluenceScore

// RecalculateInfluenceLocked 重算全部座位影响力。
// **调用前置**：必须已持 r.mu（§92a）。
func (r *WerewolfRoom) RecalculateInfluenceLocked()

// influenceTrackerLocked 懒初始化访问器（同 ledgerLocked / hypothesisStoreLocked 模式）。
func (r *WerewolfRoom) influenceTrackerLocked() *InfluenceTracker
```

## U2: 三个 spectator 字段接线修复（§130 第 N 次复现）

### 缺陷本质

后端认真产出、`view.go` 认真下发、注释认真描述了前端渲染位置 —— 而那些前端位置从未存在。
每次 spectator `game.state` 广播都在传输无人读取的字节。

与以往 §130 案例的区别：**这次「另一端」确实在工作**，所以 `grep` 后端能看到完整链路，
只有真正去前端 `grep` 才会发现断点。这提示一条新的自检规则：

> **跨端字段的接线验证必须双向 grep** —— 后端加字段时 grep 前端消费点，
> 前端加字段时 grep 后端产出点。单向 grep 只能证明一半。

后端三个字段的产出逻辑**完全正确**，不需要任何改动。只补前端消费者。
