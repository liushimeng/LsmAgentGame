## U1: 胜率趋势追踪（T12，Mimo §8.3）

### 动机

§20260812-02 U1 落地了 5 维能力雷达图（`GET /api/llm/radar`），§20260810-03 F3
落地了模型天梯（`GET /api/llm/leaderboard`），但两者都是**全期聚合**——
无法回答「某模型最近是变强还是变弱」「某模型坐几号位 / 拿什么角色时胜率最高」。
T12 补齐「按模型 / 角色 / 座位号统计胜率 + 时间趋势」的最后一块数据分析拼图。

### 设计

**后端** — `ServerGo/service/model_log_service.go` 新增 `WinRateTrends`（~200 行）：

- 数据源：`t_lsm_game_model_game_log`（§118 起逐局写入，含
  `provider_id / seat / role / result / started_at` 全部所需列）。
- **三段聚合**（三条 GROUP BY 查询，命中 `idx_provider_created`）：
  1. **时间趋势**：`GROUP BY provider_id, DATE(started_at)` →
     每模型每日 `{day, games, wins}`；Go 侧换算累计胜率并裁剪到最近
     `winTrendMaxDays = 30` 天（防长尾表膨胀）。
  2. **按角色**：`GROUP BY provider_id, role`（过滤 `role = ''`）→
     `{role, games, wins, win_rate}`；每模型最多保留 8 个角色（按 games 降序）。
  3. **按座位**：`GROUP BY provider_id, seat` → `{seat, games, wins, win_rate}`；
     13 人局座位 0..12 全量返回。
- 返回 `map[provider_id]*ModelWinTrend`（与 `RadarStats` 同形状，§121 前端
  `http<Record<string, ModelWinTrend>>` 直解，**不包 wrapper**）。
- `agent_name` 走 `LEFT JOIN t_lsm_game_llm_provider`（与 RadarStats 同做法）。
- **纯转换函数 `buildWinTrends(...)` 独立可测**（nil-DB 单测 + 转换单测，
  §20260811-08 教训 (5)：转换结果必须断言非空）。

**API** — `ServerGo/api/llm_api.go` 新增 `WinTrends` handler：

- `GET /api/llm/win-trends`（需登录，任意角色；与 leaderboard/radar 同组）。
- `modelLogs == nil` → `data: {}`（防御默认，与 Radar 一致）。

**前端** — `ClientWeb/src/components/common/ModelAnalyticsPanels.tsx`（新文件，~260 行）：

- `ModelWinTrendPanel` 组件：
  - 每模型一行：`agent_name` + 近 30 天胜率 **SVG sparkline**（纯 SVG polyline，
    无第三方图表库）+ 总胜率 / 最佳角色 / 最佳座位 3 个摘要徽章。
  - 角色 / 座位明细折叠表（`<details>`）。
- 挂载点：`ModelAdminPage` 工具栏新增一个 toggle 按钮 +
  `<ModelAnalyticsSection>` 一行 JSX（该页已 1792 行，逼近 §4 上限 1800，
  **面板逻辑必须全部在独立组件文件**，页面内只允许 ≤8 行接线）。
- 数据加载：组件自行 `useEffect` fetch，失败 best-effort 静默（与雷达图一致）。

**i18n** — 三语补 8 键 `werewolfAdmin.analytics.*`（标题 / 空态 / 胜率 /
近 30 天 / 按角色 / 按座位 / 局数 / 样本不足）。

### 风险

- **低**：纯只读聚合，无 LLM 调用，无游戏流交互。
- **§121 数据形状**：返回 `map`（非 wrapper），前端 TS 类型显式声明。
- **§4 行数上限**：`model_log_service.go` 当前 559 行 + ~200 行 = ~760 行，安全；
  `ModelAdminPage.tsx` 1792 行，页内接线 ≤8 行，安全。

## U2: 道具经济分析（T13，Mimo §8.3）

### 动机

§132/§133 道具系统 v4 已落地 7+3 个道具 + EconTier 三档经济，
`t_lsm_game_prop_usage_log` 表逐条记录了每次道具使用的
`price_paid / pot_return / system_absorb / target_compens / hit`，
但**从未有任何聚合视图消费这张表**（§130 高危信号：写入了却从不读）。
运营侧无法回答「哪个道具性价比最高 / 中招率实测多少 / 金币流向是否健康」，
经济参数调优只能靠猜。T13 补齐道具购买 / 使用 / 命中率 + 金币流向分析。

### 设计

**后端** — `ServerGo/service/model_log_service.go` 新增 `PropEconomyStats`（~150 行）：

- 放在 `ModelLogService`（它已持有 `gormDB`，是既有分析聚合的宿主；
  道具日志分析与 model_game_log 分析同属「运营数据分析」职责面）。
- **单条聚合查询**：`t_lsm_game_prop_usage_log` `LEFT JOIN t_lsm_game_prop`
  （`prop_id → id`）`GROUP BY prop_id` →
  `{uses, hits, hit_rate, total_spent, pot_return, system_absorb, target_compens}`。
- 道具名 / 单价 / 基础中招率从 JOIN 的 prop 目录行取；目录里被删除的孤儿
  日志行（prop 行不存在）显示 `prop_key = prop_id`。
- 返回 `[]PropEconomyEntry` + 顶层汇总 `{total_uses, total_spent,
  total_pot_return, total_system_absorb, total_target_compens, overall_hit_rate}`。
  **返回 wrapper struct `PropEconomyResponse{Summary, Entries}`** ——
  前端按 §121 显式声明 wrapper 类型（§121 教训：`http<T>` 直接展开 `data`）。
- 纯转换函数 `buildPropEconomy(rows)` 独立可测。

**API** — `ServerGo/api/prop_api.go` 新增 `GetPropEconomy` handler：

- `GET /api/games/werewolf/prop-economy`（需登录；挂在 werewolfGames 组，
  与 `/props`、`/rooms/:roomId/prop_history` 同族）。
- PropAPI 已持有 `propSvc *werewolf.PropService`；聚合走
  `ModelLogService`——main.go 将 `modelLogSvc` 以可选参数注入
  `NewPropAPI`（变长参数 `...` 尾部追加，不破坏既有 3 个调用点签名）。

**前端** — `ClientWeb/src/components/common/ModelAnalyticsPanels.tsx` 内
`PropEconomyPanel` 组件（与 U1 同文件）：

- 顶层金币流向条：`总支出 → 回彩池 X% / 系统销毁 Y% / 目标补偿 Z%`（三段色条）。
- 每道具一行表格：名称 / 单价 / 使用次数 / 命中数 / **实测中招率 vs 基础中招率**
  （差值染色：实测高于基础 = 红字「超模」，低于 = 蓝字「弱势」）。
- 挂在 `ModelAnalyticsSection`（U1 同组件）内的第 2 块。

**i18n** — 三语补 10 键 `werewolfAdmin.propEcon.*`。

### 风险

- **低**：append-only 日志表的只读聚合。
- **§130 自检**：`PropEconomyStats` 写完必须 grep 确认 handler 注册 +
  路由注册 + 前端 fetch 三处接线全部存在（本批次测试断言）。
- **§133 EconTier 独立常量**：本项只读分析，**不改**任何销毁率常量。

## U3: 阶段切换动画增强（T1 余项，Mimo §8.1）

### 动机

§124 落地了 Day/Night 三类覆盖层（fade-in/out + emoji pulse），
§20260811-08 U4 补齐了阶段集合。T1 余项「淡入淡出/滑动增强」：
当前 `__inner` 卡片只有整体缩放淡入，没有方向性滑动与文字层次进场，
阶段切换的「仪式感」不足。

### 设计

**纯 CSS 增强**（`ClientWeb/src/styles/werewolf.css`，~90 行新增，零 TSX 改动）：

1. **方向性滑动**：`__inner` 按覆盖类型附加位移进场 ——
   night 自上方 -24px 沉降（夜幕降临）、dawn 自下方 +24px 升起（日出）、
   day 自左侧 +16px 滑入；退场反向滑出（写进既有 FadeOut keyframes 的
   独立变体，保持各类型时长与 §124 分级一致：night 2.5s > dawn 1.8s > day 1.2s）。
2. **文字层次进场（stagger）**：emoji → title → subtitle 依次 0/120/240ms
   延迟淡入上浮，用 `animation-delay` + `backwards` fill 实现。
3. **背景视差**：覆盖层背景渐变在进场期间轻微 `scale(1.06)→scale(1)` 呼吸。
4. **无障碍**：`@media (prefers-reduced-motion: reduce)` 下全部滑动/视差
   退化为纯 opacity 淡入淡出（§26.5 keyframes 必须配 reduced-motion 兜底）。
5. **§124 硬约束不改**：`pointer-events: none` + setTimeout 自动消失 +
   z-index 全部保持；只动 keyframes 与 animation 组合。

### 风险

- **极低**：零逻辑改动；`DayNightOverlay.tsx` 不修改。
- **验收**：`npm run build` 后 `dist/assets/index-*.css` 含新 keyframes 名；
  肉眼验收三类覆盖层滑动方向。

## U4: 夜间血迹图 S2（§7.4 V1，M3 §3）

### 动机

观战者目前只能通过上帝视角面板的**文字列表**看夜间行动
（seer_checks / witch_decisions / guard_protects / public_actions），
缺乏空间感。S2「夜间血迹图」把夜间行动渲染成座位间的箭头/连线，
是知识库中评估「风险低（仅 spectator）、复用既有数据」的观赏性升级。
本批次只做 S2（血迹图），V2（wolf_whisper 推理路径叠加）保留 ——
它需要把 wolfpack 留言下发 spectator 侧，涉及新的 §119 隔离评审，超出本批范围。

### 设计

**后端** — `GodModeSnapshot` 补 2 个字段（`view.go` + `view_godmode.go`，~80 行）：

- `WolfKills []WolfKillEntry \`json:"wolf_kills"\``（`{Day, Target}`）：
  从 `InfoSourceNightWolfVote` 账本条目聚合 —— 每 Round 取 **Seq 最大**的
  `wolf_vote seat=S target=T` 条目的 target 作为该夜狼队最终刀口
  （最后一票即定刀；与引擎 `NightWolfKill` 计票语义一致）。
  若该夜所有狼弃权（target==-1）则跳过。
- `GuardProtectEntries []GuardProtectEntry \`json:"guard_protect_entries"\``
  （`{Day, Seat, Target}`）：`guard_protect seat=G target=T` fact 本就含
  双座位（`buildNightActionsBySeatLocked` 已在用），此处补带 Day+Seat 的
  结构版；**保留既有 `GuardProtects []int` 不动**（前端 GodModeView 在用，
  不破坏 §121 既有契约，纯增量字段）。
- 聚合逻辑全部在 `populateGodModeLocked` 的既有 `switch e.Source` 内扩展 ——
  **锁内直读，无新 Lock**（§92a）；无新写入点（不触碰 §97 六处同步）。
- §135：两字段只含座位号，不含身份明文；下发通道仍是 spectator-only 的
  GodModeSnapshot（玩家视图 / REST 永不下发，既有单点保证）。

**前端** — `ClientWeb/src/components/werewolf/NightBloodMap.tsx`（新文件，~230 行）：

- `HistoryDrawer` 第 12 个 sub-tab「🩸 血迹图」（spectator-only，进
  `SPECTATOR_ONLY_TABS` 白名单）。
- **SVG 椭圆座位阵**：13 座位按椭圆参数方程自行计算坐标（自包含，
  不依赖 WerewolfTable 布局）；座位圆点按存活/死亡着色。
- **按夜选择器**：`<select>` 选第 N 夜（默认最新夜），切换时重绘：
  - 🐺 狼刀：全体狼座（`Factions` 派生）→ target 红色箭头（`WolfKills[day]`；
    当前夜用 `WolfKillTarget`）。
  - 👁 查验：预言家座位 ↔ 目标 绿/红 虚线（`SeerChecks[day]`，result 染色）。
  - 🧪 用药：女巫座位 → 解药目标绿实线 / 毒药目标紫实线（`WitchDecisions[day]`）。
  - 🛡 守护：守卫座位 → 目标 盾形虚线弧（`GuardProtectEntries[day]`，
    守卫座位缺失时从 `Roles` 反查）。
  - ⚔ 猎魔人：`PublicActions[kind=demon_hunter && day]` 橙色箭头。
- 底部图例 + 空态文案（该夜无行动）。
- **§119 不破坏**：组件只消费 GodModeSnapshot 既有 + 本批新增字段，
  不引入 wolf_whisper / chat 数据。

**类型同步** — `ClientWeb/src/types/werewolf.ts` GodMode 类型补
`wolf_kills` / `guard_protect_entries`（§121 手工双文件同步，view.go 注释已警告）。

**i18n** — 三语补 9 键 `werewolf.history.subtab.bloodmap` + `werewolf.bloodmap.*`。
