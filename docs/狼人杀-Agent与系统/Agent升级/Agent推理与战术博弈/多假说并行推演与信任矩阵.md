> **文档版本**：2026-08-10

> **采纳理由（为什么选它）**：
> 1. **它是 P3 梯队里"复杂度 × 价值 × 地基成熟度"综合最高的一条**——优先级总表里 P1-A/B/C/D/E/F 都是单点功能（上帝视角/高光卡片/原班重开/折扣券/Knight UI/EmotionAvatar 碰撞），P2-A/B/C 是工程量相近但价值相对收敛，**P3-D 多假说推演**正好踩在"用已落地的信息账本一期做地基"+"借助 §128 对话即思考扩展 `LastDecisionSummary` 字段而非新建独立存储"两个最稳的支点上。
> 2. **它是 §130「声明了却从不接线」模式的反面教材的根治**：当前每个 Agent 只在 user prompt 里看一段平铺的 chat history，**没有任何结构化的"假说维护"机制**——LLM 跨多轮追踪 13 个玩家的身份是「临时推断」而不是「显式记录」，导致：① 信息太多时丢上下文；② 跨天推理容易自我矛盾；③ 观战者无法看到 AI 的「脑子」长什么样。假说表作为单一真相源，把「我知道什么 + 我猜谁是 X」两件事都结构化。
> 3. **合并两份知识库中本质相同的两条建议**：DeepSeek §一.1「多假说并行推演（驱动行为）」+ Gemini §一.2「心理信任矩阵 / 假说树（展示给观众）」—— 文档已声明合并为单一「身份概率可视化」工具，本设计文档正是把这条合并建议落地为单一实现。
> 4. **与 §20260810-05 信息账本一期强协同**：账本解决「谁知道什么」，本设计解决「他认为谁是谁」—— 两者拼起来就是完整的「AI 认知地图」，对调试、复盘、教学价值极大。

## 1. 现状审计依据

### 1.1 当前 Agent「猜疑链」问题

每个 Agent 在 `buildAgentContextLocked` 拿到的 GameContext **不包含任何结构化的身份假说**：

| 现状 | 问题 |
|---|---|
| `GameContext` 无 `HypothesisTable` 字段 | LLM 必须在 user prompt 末尾的「自由思考」中**临时构造**猜疑链，跨轮不持久 |
| `BotTranscript.LastDecisionSummary` 仅 50 字 | 观战者侧 `AgentInteractionPanel` 只能看到「vote → 2号」，看不到「我为什么觉得 2 号是狼」 |
| `InformationLedger`（§20260810-05 一期）只有 knower_seats | 解决了「谁知道」，但**没有解决「他认为谁是谁」** —— 账本本身是中性的 |
| `MemoryMD`（§131）跨局学习 | 粒度太粗，无法反映"本局第 3 天我对 5 号的猜测从 60% 上升到 85%" |
| `HistoryDrawer` 「🤖 独白」tab 只渲染 `heart_thought` | 观战者看不到「身份概率变化时间线」 |

**根因**：当前系统把"猜疑"当成 LLM 的私有推理能力，但 LLM 没有持久化机制——一段 prompt 触发一次输出，下一段 prompt 就忘掉。

### 1.2 与已落地机制的兼容性

| 机制 | 关系 |
|---|---|
| §119 心口不一 | **同根**：HypothesisTable 是「推理」侧持久化，HeartThought 是「输出」侧私有独白；两者均**不**入 `chat_message` 表 |
| §128 对话即思考 | **承载**：HypothesisTable 落地形态 = 写到 `LastDecisionSummary` 末尾追加的「📊 假说摘要」段（≤30 字），不新增独立字段 |
| §135 身份公开公平性 | **约束**：HypothesisTable JSON 必须走 spectator-only 下发通道（`viewer == -1`），玩家侧只能看到自己 bot 的 |
| §20260810-05 信息账本 | **地基**：账本提供 `KnowerSeats` 集合，HypothesisTable 用它做"以我这个知情集能推出的合理假说数量上限"的推断依据 |
| §20260810-06 行为承诺 | **协同**：`public_commit` 的「预言家查验」模板可被 HypothesisTable 复用为「高置信度假说」的硬锚点（commit 后该玩家 confidence 锁定为 ≥95%） |
| §134 / §134a | 不影响本期——本期不动卡池、不动角色 |
| §197 流式续命 | HypothesisTable 由 LLM 在同一 chat 流中输出，**不**新建 LLM 调用（沿用 `callProvider + parentCtx + extendedTimeout`） |

## 2. 设计

### 2.1 核心数据结构

#### 2.1.1 HypothesisEntry（一条假说）

存于 **`ServerGo/game/werewolf/hypothesis_tracker.go`**（≤ 300 行，含测试 ≤ 600 行），独立存储：

```go
// HypothesisEntry 一条身份假说:"我对 X 号身份的最佳猜测 + 置信度 + 支撑/反驳证据"。
//
// §119 协议层隔离:HypothesisEntry **不**写 chat_message / chat_history,
// 仅进 BotTranscript(观战者可见)+ GameContext.HypothesisTable(本人 bot
// 可见),玩家侧默认收不到(§135)。
type HypothesisEntry struct {
    TargetSeat int    `json:"target_seat"`        // 0-indexed,被猜测的玩家
    RoleGuess  string `json:"role_guess"`         // 封闭枚举:werewolf/seer/witch/guard/villager/idiot/knight/hunter/demon_hunter/king/deceiver/collector/tanner/unknown
    Confidence int    `json:"confidence"`         // 0~100,本 bot 对该猜测的置信度
    Supporting string `json:"supporting"`         // ≤40 字,本 bot 公开承认的支撑依据(可对外广播,§119 OK)
    Refuting   string `json:"refuting"`           // ≤40 字,本 bot 公开承认的反证(可对外广播,§119 OK)
    UpdatedAt  int64  `json:"updated_at"`         // UnixMilli
}
```

#### 2.1.2 HypothesisTable（房间级 + per-bot 视图）

```go
// HypothesisTable 是某个 bot 座位维护的"我对其他玩家的假说集"。
// 房间级唯一键是 (RoomID, Seat),纯内存态,不进 DB。
//
// §119/§135 落地约束:
//   - 写入:LLM 在 tool_use `maintain_hypotheses` 中以 structured payload 提交;
//   - 读取:buildAgentContextLocked 填充 gc.HypothesisTable(本人 bot);BuildClientStateWithRoom
//          对 viewer==-1 填充 cs.BotHypotheses[seat](观战者侧视图);
//   - 人类玩家读取:viewer>=0 时 cs.BotHypotheses 字段 omitempty,前端类型 BotHypothesesJSON 可选。
type HypothesisTable struct {
    Seat     int               `json:"seat"`              // 持有此表的 bot 座位
    Entries  []HypothesisEntry `json:"entries"`           // 对其他玩家的假说(不包含自己)
    Round    int               `json:"round"`             // 上次更新时间(天数)
    UpdatedAt int64            `json:"updated_at"`        // UnixMilli
}
```

#### 2.1.3 房间级 HypothesisStore

```go
// HypothesisStore 房间级假说存储(类似 InformationLedger,所有方法 *Locked 语义)。
// 上限 hypothesisStoreCap = 13*12*5 = 780 条(13 玩家 × 12 目标 × ~5 假说更新轮次)。
type HypothesisStore struct {
    tables map[int]*HypothesisTable // key = bot seat(0..MaxPlayers-1);非 bot 不入表
}
```

### 2.2 LLM 接入：单工具 `maintain_hypotheses`

**关键决策**：复用现有 `speak_with_thought` 工具的 structured-payload 范式，**不新增独立工具**。
- 写入由 LLM 在 `speak_with_thought` / `vote` / `wolf_kill` / `witch_act` / `seer_check` / `guard_protect` 等决策型工具**同一响应**的 `LastDecisionSummary` 末尾追加 JSON 段，由后端 `BuildDecisionSummary` 解析。
- 解析失败（LLM 输出了不合规 JSON）→ 静默丢弃该段，仅保留原 `LastDecisionSummary`，**不计入** `consecutiveFailures`（§120 公平性）。

**JSON 段格式**（嵌入 `LastDecisionSummary` 末尾）：

```
vote → 2号  📊 [{seat:5, role:"werewolf", conf:75, support:"第2轮悍跳预言家", refute:"投票跟好人大流"}, {seat:7, role:"seer", conf:60, support:"金水真实", refute:"逻辑跳跃"}]
```

正则捕获：

```go
var hypothesisSummaryRe = regexp.MustCompile(`📊\s*(\[.*?\])\s*$`)
```

### 2.5 §92a 锁约束

- 所有 `HypothesisStore` 方法均为 `*Locked` 变体，**调用方必须已持有 `r.mu`**（§92a 第 N 次复现的红线）。
- `BuildClientStateWithRoom` / `BuildAgentContext` / `phaseWatchdogTick` 都已持 `r.mu`，直接调 `hypothesisStoreGetLocked(seat)` 即可。
- 公开变体（仅在测试需要）：`*Locked` 命名保持一致，加 `r.mu.Lock()`/`Unlock()` 一层。

### 2.6 §135 spectator 隔离

| viewer 角色 | 可见范围 |
|---|---|
| 真人玩家 (viewer≥0) | 仅**自己 bot** 的 HypothesisTable（如有），其他 bot 的 HypothesisTable **不**下发 |
| 真人观战者 (viewer==-1,isSpectator==true) | **全部** bot 的 HypothesisTable，含 confidence/supporting/refuting |
| AI Agent | 走 `gc.HypothesisTable`（仅本人），不下发 cs.BotHypotheses |

**前端约束**：`ClientWeb/src/types/werewolf.ts` 的 `BotHypothesesJSON` 类型字段标 `spectator_only: true`，组件级 if-guard。
