## 1. E1：`rollHit` 余额修正系数从未实现

### 1.1 现状

`game/werewolf/prop_engine.go:237-238` 的函数注释：

```go
// rollHit 服务端权威骰点判定是否中招。
// 基础中招率 + 修正系数（目标 consecutiveFailures > 2 → +10%，使用者余额 > 2000 → +5%）。
func (e *PropEngine) rollHit(entry *PropCatalogEntry, r *WerewolfRoom, toSeat int) bool {
```

函数体内 `consecutiveFailures > 2 → +10%` 分支**已实现**（`prop_engine.go:241-251`），
但 `使用者余额 > 2000 → +5%` 分支**完全不存在**。

设计文档 [`狼人杀13人局道具系统设计.md:126`](../狼人杀-道具与经济/狼人杀13人局道具系统设计.md) 同样写明：

> 修正系数：使用者本局金币余额 > 2000 → +5%（"富人光环"心理暗示）

即**注释 + 设计文档 + 代码三方中，只有代码没做**。

### 1.2 后果

- 道具中招率**系统性偏低 5%**（对余额 > 2000 的使用者），道具经济模型与设计不符。
- 「富人光环」这一设计意图完全未生效，高余额玩家买道具的性价比低于设计预期。
- 严重度 P2：不影响正确性，只影响数值平衡。

### 1.3 关于「使用者」还是「目标」余额的取舍

K3 知识库原文写的是「**目标**余额 > 2000」，而**代码注释与设计文档均写「使用者余额」**。

**本次采用「使用者余额」**，理由：
1. 设计文档 `:126` 是道具系统的事实来源，明确写「使用者本局金币余额」+「富人光环」语义。
2. 代码注释与设计文档一致，K3 文档属单方面转述误差。
3. **实现成本相差一个数量级**：`bal` 已在 `UseProp` 的 `prop_engine.go:133` 通过
   `e.walletSvc.GetBalance(ctx, req.FromUserID)` 取到，且与 `rollHit` 调用点（`:188`）
   在同一函数内；改用「目标余额」则需要额外一次 `GetBalance` 调用 + 传 `ctx` 进 `rollHit`。

### 1.4 修复方案

给 `rollHit` 增加一个 `userBalance int64` 参数，由调用点传入已有的 `bal`：

```go
// 修复前
func (e *PropEngine) rollHit(entry *PropCatalogEntry, r *WerewolfRoom, toSeat int) bool {
// 调用点
hit := e.rollHit(entry, r, req.ToSeat)

// 修复后
func (e *PropEngine) rollHit(entry *PropCatalogEntry, r *WerewolfRoom, toSeat int, userBalance int64) bool {
// 调用点
hit := e.rollHit(entry, r, req.ToSeat, bal)
```

函数体内在 `consecutiveFailures` 分支之后、`rate > 70` 封顶之前插入：

```go
// 修正：使用者「富人光环」（余额 > 2000）→ +5%
if userBalance > propRichAuraBalance {
    rate += propRichAuraBonus
}
```

**保留既有 70% 上限封顶**——这是防止道具变成必中的关键保护，不因新增修正而失效。

### 1.5 风险评估

- **风险等级**：低（纯数值修正，走既有封顶保护）
- **影响面**：余额 > 2000 的使用者中招率 +5%（绝对值，非相对），符合设计文档
- **不做的部分**：K3 F4 原文还建议「把骰点细节写入 `t_lsm_game_prop_usage_log`」——
  该部分需要新增 DB 列 + AutoMigrate，**超出本轮 TINY 标准，不采纳**，留待后续迭代。
- **回归测试**：新增 `prop_rollhit_test.go` 断言余额分支与封顶保护

## 2. E2：法官 `GameSnapshot.SpeakOrder` 零写入点

### 2.1 现状

`agent/wwjudge/judge.go:316` 声明：

```go
SpeakOrder   []int    // 当前 speak 轮次的发言座位顺序
```

全 `agent/wwjudge/` 包内对该字段的引用**有且仅有这一行声明**——
既无生产写入点，也无消费点。

生产者 `game/werewolf/judge_summary_bridge.go:480` 的 `buildJudgeSnapshotLocked`
填充了 Phase / Day / Winner / AliveSeats / DeadSeats / WolfSeats / SheriffSeat /
Votes / LastDeathCause / LastDeathVerdict / IsHumanInRoom，**唯独跳过 SpeakOrder**。

而数据源就在手边：`game/werewolf/engine.go:286` 的 `gs.SpeakOrder []Seat`，
由 `engine_day.go:37-49` 在每轮发言开始时正常填充，`view.go:419-423` 也已正常
下发给前端。**只有法官这条链路断了。**

### 2.2 后果

法官在 `judge_speak_start` 唤醒时看不到本轮发言顺序，导致：

- 无法宣告「接下来由 X 号发言，然后是 Y 号」这类顺序引导。
- 无法判断当前发言者处于发言序列的什么位置（首位 / 中段 / 收尾），
  宣告文案的信息量受限。
- 这是 §130「声明了却从不接线」的又一次复现——字段存在会让后来者
  误以为法官已经拿到了发言顺序。

### 2.3 修复方案

**两处改动，均为复制既有 `Votes` 处理范式。**

**(a) 生产端** —— `judge_summary_bridge.go` 的 `buildJudgeSnapshotLocked` 中，
在 Votes 快照之后插入：

```go
// SpeakOrder 快照:仅 PhaseSpeak 时有意义(§20260810-02 E2 补齐零写入点字段)。
if r.State.Phase == PhaseSpeak && len(r.State.SpeakOrder) > 0 {
    order := make([]int, 0, len(r.State.SpeakOrder))
    for _, s := range r.State.SpeakOrder {
        order = append(order, int(s))
    }
    snap.SpeakOrder = order
}
```

与 Votes 一致地**限定在 `PhaseSpeak`**：`SpeakOrder` 在平票 PK（`engine_day.go:586`）
和警长竞选（`engine_day.go:253`）时会被复用为「参与者列表」，非发言阶段下发会让法官误读。

**(b) 消费端** —— `agent/wwjudge/judge_prompt.go` 在 `current_votes` 块之后插入
（座位号 **+1** 转为对外 1-indexed，遵循 §82a）：

```go
if len(snap.SpeakOrder) > 0 {
    s.WriteString("speak_order(本轮发言顺序):")
    for _, seat := range snap.SpeakOrder {
        s.WriteString(fmt.Sprintf(" %d", seat+1))
    }
    s.WriteString("\n")
}
```

**(c) 权威字段清单同步** —— `judge_prompt.go:37` 的硬约束 ❸ 列出了
`AliveSeats/DeadSeats/SheriffSeat/Votes/Winner` 作为权威字段，`SpeakOrder` 需补入，
否则 LLM 不会信任该字段。

### 2.4 风险评估

- **风险等级**：低（纯只读快照字段填充，法官 goroutine 内只读）
- **§92a 合规**：改动发生在 `*Locked` 变体内部，调用方已持 `r.mu`，不新增加锁
- **影响面**：法官 prompt 增加一行 ≈ 20 token；宣告质量提升
- **回归测试**：新增 `judge_speak_order_test.go` 断言 PhaseSpeak 填充 + 非 speak 阶段留空

## 3. E3：`WerewolfPropKey` TS 类型缺 4 个道具

### 3.1 现状

`ClientWeb/src/types/werewolf.ts:606-613`：

```ts
/** 道具 prop_key 枚举(对齐 ServerGo/prop_catalog.go 的 6 种道具)。 */
export type WerewolfPropKey =
  | 'markdown_bomb'
  | 'nested_maze'
  | 'char_confuse'
  | 'long_swear'
  | 'task_disguise'
  | 'emotion_plea';
```

后端 `game/werewolf/prop_catalog.go` 实际注册 **10 个**：上述 6 个 +
`task_disguise_v3`（§133 v3 强化版）+ `md_bomb_human` / `nested_maze_human` /
`char_confuse_human`（§20260807-04 三个人类反制道具）。

`prop_test.go:148` 的规范清单同样是 10 个。**TS 类型落后后端 4 个，且注释还写着「6 种道具」。**

### 3.2 后果

- `useWerewolf.ts:275` 处 `ev.prop_key as WerewolfPropKey` 是一次**不安全断言**：
  后端推送 `md_bomb_human` 时，运行时值根本不在联合类型的取值域内，
  类型系统给出的是错误的安全保证。
- `PropUseOverlay.tsx:60` 已经在使用 `task_disguise_v3` 作为 `Record<string, PropTheme>`
  的键——因为该 Record 退化用了 `string` 索引，才没被类型检查拦住。
- 任何后续基于 `WerewolfPropKey` 做穷尽性检查（`switch` + `never` 兜底）的代码，
  都会漏掉这 4 个道具且**不报错**。

### 3.3 修复方案

补齐 4 个缺失成员，并修正注释中的数量：

```ts
/**
 * 道具 prop_key 枚举(对齐 ServerGo/game/werewolf/prop_catalog.go 的 10 种道具)。
 *
 * §20260810-02 E3:补齐 4 个后端已注册但 TS 未声明的道具 ——
 * task_disguise_v3(§133 v3 强化版) + 3 个 TargetCamp:"human" 人类反制道具
 * (§20260807-04)。此前 useWerewolf.ts 的 `as WerewolfPropKey` 断言对这 4 个
 * 取值是失真的。
 */
export type WerewolfPropKey =
  | 'markdown_bomb'
  | 'nested_maze'
  | 'char_confuse'
  | 'long_swear'
  | 'task_disguise'
  | 'task_disguise_v3'
  | 'emotion_plea'
  | 'md_bomb_human'
  | 'nested_maze_human'
  | 'char_confuse_human';
```

### 3.4 风险评估

- **风险等级**：极低（**纯加宽联合类型**，对既有代码是向后兼容的）
- **影响面**：无运行时变化；`PropUseOverlay.tsx` 的 `Record<string, ...>`
  与 `themeFor` 的 `?? fallback` 兜底继续生效，3 个 human 道具走灰色默认主题
- **刻意不做**：不给 3 个 human 道具补 `PROP_THEMES` 配色。那属于 UI 增强
  （需配色 + CSS 动效 + i18n 三语），超出本轮 TINY 标准
- **回归测试**：`tsc --noEmit` + `npm run build` 通过
