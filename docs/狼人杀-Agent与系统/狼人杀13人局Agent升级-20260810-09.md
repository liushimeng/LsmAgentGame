# 狼人杀 13 人局 Agent 升级 — 20260810-09（上帝视角观战增强 + 警长发言定序权）

> **文档版本**：2026-08-10
> **采纳来源**：[`Agent-Surpport-01.md`](../../Agent-Surpport-01.md) §12 优先级总表 **P1-A「上帝视角观战增强」+ P3-A「警长定序权」**
> （原始出处：K3 §2 V3「上帝视角观战模式增强」+ LongCat §2 F2「警长定序权」）
>
> **采纳理由（为什么这两项是知识库剩余项中最重要、最复杂的一对组合）**：
>
> 1. **P1-A 是知识库 §12 中明确标注「性价比最高项」的唯一建议** — 工程量 0.5w、风险低（§135 spectator 隔离）、影响面 ~200 行，且实现后观战者获得「全部身份 + 夜间狼刀目标 + 查验结果」的法官级视野，是狼人杀观众体验从「看热闹」到「品博弈」的**单一最大飞跃**。§135 单点判定 + §92a 锁内变体 + §119 协议层隔离 三条硬约束刚好把"做对"的边界画得很清楚。
> 2. **P3-A 是知识库中明确标注为「规则补全而非规则发明」的唯一建议** — 标准竞技狼人杀中，警长的核心权力就是「决定发言顺序」，但本仓库代码仅实现了 1.5 票 + 警徽流。补全这条规则后，警长从「吉祥物」变成「战略资源」，LLM 必须学会「何时抢警 + 警徽流交付时机 + 定序权时机」的三段决策，能力展示密度高。
> 3. **两者一起做能把"观战理解门槛 + Agent 决策深度"双双打掉一档**：上帝视角让观众实时对照「真相 vs 发言」，警长定序让观众看到「同一个发言顺序在顺时针/逆时针下的策略差异」——一条线是「观众能看懂」，另一条线是「策略更值得看」。
> 4. **复杂度结构性叠加**：P1-A 触碰 `BuildClientStateWithRoom`（R212 自死锁案发现场）+ `SpectatorView` 两条 spectator-only 下发路径；P3-A 触碰 `engine_day.go::startSpeakPhase`（所有发言顺序源头）+ §97 五处同步（`SkipPhaseAction`/`watchdogActingSeat`/`dispatchQuarantinedSkipLocked`/`isActingPhase`/`defaultPhaseDeadlineSec`）。两者**互不冲突**（前者只读 spectator 视图，后者只动发言顺序生成），但都触及**已有的、被反复踩过的地雷**——CLAUDE.md §13 的 7 条核心约束在本批次至少被命中 4 条（§92a / §97 / §130 / §135）。
>
> **工作面边界**（按 CLAUDE.md §13 §14 拆分）：
> - `ServerGo/game/werewolf/view.go` + `engine_day.go` + 新增 `room_sheriff_order.go` + `view_godmode.go` + `phase_deadlines.go` 五处同步 → **backend-dev**

## 2. 设计

### 2.1 上帝视角（GodMode）— 数据流

#### 2.1.1 新增字段（仅 spectator 下发）

```go
// ServerGo/game/werewolf/view.go — ClientGameState 新增
type ClientGameState struct {
    // ... 既有字段 ...

    // §20260810-09 上帝视角 — 仅 spectator（viewer<0）下发；玩家+REST 永远 omitempty
    // 字段名集中放在 §135 spectator-only 区块，便于未来审计。
    GodMode *GodModeSnapshot `json:"god_mode,omitempty"`
}

type GodModeSnapshot struct {
    Enabled           bool             `json:"enabled"`             // 由观战者客户端 localStorage toggle 决定
    Roles             map[int]string   `json:"roles"`               // seat -> role_key 全量身份
    Factions          map[int]string   `json:"factions"`            // seat -> faction_key
    WolfKillTarget    int              `json:"wolf_kill_target"`    // -1 = 当夜无刀 / 已守 / 已救
    WolfVotes         map[int]int      `json:"wolf_votes"`          // wolf_seat -> target_seat
    SeerChecks        []SeerCheckEntry `json:"seer_checks"`         // 历史预言家查验（公开 + 警徽流）
    WitchDecisions    []WitchDecision  `json:"witch_decisions"`     // 历史女巫用药（解药/毒药/未用）
    GuardProtects     []int            `json:"guard_protects"`      // 历史守卫守护目标
}
```

#### 2.1.2 「开启」语义

- **不在服务端做开关**。服务端永远下发完整 `GodMode` 字段；前端按 `localStorage.ww_god_mode === "1"` 决定是否渲染。
- **理由**：服务端开关会导致「观战者 A 开了、B 没开」需要维护「谁订阅了谁」的会话级状态，复杂度爆炸；客户端开关天然支持每用户独立，且不污染服务端权威视图（§135 服务端永远不下发到玩家 —— 字段在玩家侧 omitempty）。
- **隐私边界**：人类玩家通过 GameContext / BuildUserPrompt 路径**永远看不到** GodMode 字段（§121 `http<ClientGameState>` 字段不下发，详见 §3.2）。

#### 2.1.3 数据来源

| 字段 | 来源（已存在） | 备注 |
|---|---|---|
| `Roles/Factions` | `gs.Roles[seat]` + `gs.Players[seat].Faction` | 既有 |
| `WolfKillTarget` | `gs.WolfKillTarget` + `gs.GuardProtectTarget` + `gs.WitchSavedTarget` 推导 | 已有字段 |
| `WolfVotes` | `gs.WolfKillVotes map[int]Seat` | 已有字段（夜间狼刀投票）|
| `SeerChecks` | `InformationLedger`（§20260810-05 落地的 source=`night_seer` 全部条目）| **复用既有**，不新建存储 |
| `WitchDecisions` | `InformationLedger` source=`night_witch` | 复用 |
| `GuardProtects` | `InformationLedger` source=`night_guard` | 复用 |
