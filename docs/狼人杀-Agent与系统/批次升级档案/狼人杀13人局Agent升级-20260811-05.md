## 1. 现状与问题

### 1.1 U1 —— Agent 对「人类对手」零记忆

- §131 `t_lsm_game_agent_memory` 让 Agent 拥有了**自我**跨局记忆（4 段 MEMORY.md），
  §20260811-03 U2 `AgentReputation` 让**模型**拥有了公开声誉档案。
- 但两者都只覆盖「bot ↔ bot / bot ↔ 自己」维度。**当房间里坐着一个人类玩家时**，
  Agent 对这个人类的认知每局清零：上一局「3 号人类总是首夜跳预言家诈身份」这种
  高价值信息完全丢失。
- `GameContext.AllPlayers []PlayerBrief` 只有 `Seat/UserID/Account/AgentName/IsBot`
  五个字段——**没有任何历史打法画像**。
- M3 §5 P1 的观察：13 人局里混合房间（人类 + bot）是最有传播价值的形态，但
  Agent 对人类「一视同仁」会让重复游玩的人类觉得「这个 AI 不长记性」。

### 1.2 U2 —— 对局结束后 Memory 即刻封存，价值单向

- 一局结束时，bot 的 `Memory.messages` 里沉淀了整局的推理链、心口不一（§119
  `HeartThought`）、道具命中反馈、狼队 whisper 协商——这是全场**信息密度最高**
  的数据资产。
- 现状：§129 冷却期（默认 30 分钟）里人类只能**被动复盘**静态的
  `bot_contexts` / `DecisionTrail` / `judge_summary`；想问一句「你第二晚为什么
  毒 5 号？」没有任何入口。冷却期结束或关门后，Memory 随房间 GC 彻底消失。
- K3 §3 A2 的精妙点：§128 确立了「对话即思考」，那么**赛后问答**就是这条
  理念的自然对偶——玩家用语言提问，Agent 用本局 Memory 快照回答，全程不需要
  新增任何「结构化留痕」字段。

## 2. U1 玩家行为画像（PlayerProfile）

### 2.1 数据模型

新表 `t_lsm_game_agent_player_profile`（一模型 × 一人类 = 一行）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | char(36) PK | UUID |
| `model_key` | varchar(64) | LLM 模型 key（与 `t_lsm_game_agent_memory` 同键） |
| `user_id` | varchar(64) | 人类玩家 `t_lsm_game_user.id` |
| `profile_md` | text | LLM 生成的结构化画像（≤ 8KB；风格标签/历史倾向/心理画像） |
| `games_together` | int unsigned | 同局累计次数 |
| `wins_together` | int unsigned | 同阵营且胜利的累计次数 |
| `last_seen_at` | datetime | 最近一次同局时间 |
| `version` | int unsigned | 乐观锁（对齐 §131 memory 表） |
| `created_at` / `updated_at` | datetime | GORM 自动 |

**唯一索引**：`(model_key, user_id)` —— 一个模型对一个玩家只有一份画像。

**隐私合规**（知识库 §4.1 明确要求）：
- 只持久化**打法画像**（LLM 摘要后的标签/倾向），**不存聊天原文**；
- 管理端复用 §131 已有 `DELETE /api/admin/llm/providers/:id/memory` 同款语义，
  新增按 `(model_key, user_id)` 清除画像的管理端点；
- 画像只对 **bot 自己**（prompt 注入）与 **admin** 可见，绝不下发前端公开接口。

### 2.2 写入路径（赛后异步，对齐 §131 / §118）

```
PersistSummary 成功路径(judge_summary_bridge.go)
  → m.IterateAgentMemoriesAsync(...)          [已有, §131]
  → m.IteratePlayerProfilesAsync(r)           [新增, 本批次]
      lockRoomBriefly 快照: seatModelKeys + 每个 seat 的人类 UserID/Account +
                            阵营/胜负（复用 BuildSummaryInputLocked）
      for each (bot modelKey × human userID) 组合:
        goroutine(单飞锁 per modelKey):
          1. store.LoadProfile(modelKey, userID) 读旧画像
          2. BuildPlayerProfilePrompt(旧画像 + 本局该人类的事实:
             角色/阵营/胜负/存活天数/投票倾向快照/道具使用)
          3. registry.Get(modelKey).Chat (90s timeout, AgentClassName=
             LsmAgentGame-Werewolf-PlayerProfileIter)
          4. 校验 ≤8KB + 非空; 失败 → 保留旧画像仅更新计数器
          5. store.SaveProfile (version 乐观锁,冲突重试 1 次)
```

硬约束（继承 §131 全部教训）：
- 异步不阻塞游戏流，失败仅 `logger.Warn`；goroutine 入口 `defer recover`；
- per-model `sync.Mutex` 单飞 + DB version 乐观锁双保险；
- goroutine 内访问 `r.State` 一律 `lockRoomBriefly` 快照，绝不裸持 `r.mu`（§92a）；
- 开关 `werewolf.player_profile_enabled`（默认 true），关闭时整链 no-op。

### 2.3 消费路径（prompt 注入）

- `GameContext` 新增 `PlayerProfiles map[int]string`（seat → 该座位人类的画像摘要，
  ≤ 400 rune/人，仅人类座位有值）。
- `buildAgentContextLocked`（§92a 锁内）末尾填充：遍历存活座位，若该 seat 是人类
  且本 bot 模型对该 user 有画像 → 填入。**只注入「自己模型」视角的画像**——
  画像主键含 model_key，天然按模型隔离。
- `prompt.go` 渲染块 `【对手画像】`：每个有画像的人类座位一行
  「N 号(昵称): {profile 摘要}（同局 X 次）」。无画像时不渲染该块（零污染）。
- §130 教训：画像加载走 `lockRoomBriefly` 外的预取——`buildAgentContextLocked`
  是热路径（每次 wake 都走），不能在里面做 DB 查询。**方案**：房间级
  `profileCache map[string]map[string]profileEntry`（modelKey → userID → entry），
  在 `StartAgentsLocked` / 人类入座时一次性预取本房间所有 (bot × human) 组合，
  之后只读内存；TTL = 房间生命周期。

## 3. U2 赛后复盘对话（Recall Chat）

### 3.1 入口与权限

- **时机**：`Status=="over"` 之后（含 §129 冷却期与重开投票窗口），房间未关闭前。
- **提问方**：本房间的玩家（含已死亡）与观战者——即所有能合法看到结算页的人。
- **被问方**：本局任意 bot 座位（按 seat 寻址，不问模型，避免跨座位穿帮）。
- **REST 入口**：`POST /api/games/werewolf/rooms/:roomId/recall_chat`
  `{seat: int, question: string(≤200字)}` → `{answer: string(≤600字)}`。
- **鉴权**：JWT 必須；服务端校验调用者是该房间玩家或观战者
  （复用 `Hub.spectators` / `r.Seats` 成员判定）。
- **限流**：每用户每房间 10 次 / 每 bot 每分钟 3 次（复用令牌桶模式）；
  超限返回 errcode 而非静默丢弃。

### 3.2 回答生成（冻结快照，§197 长预算）

```
POST recall_chat
  → manager.RecallChat(roomID, userID, seat, question)
    1. lockRoomBriefly 快照: r.Status=="over"? + bot := r.BotAgents[seat] +
       该 bot 的 Memory.Snapshot()(messages + recentTools) + modelKey +
       本局角色/阵营/胜负（BuildSummaryInputLocked）
    2. 锁外构造请求:
       system = BuildRecallSystemPrompt(角色, 阵营, 胜负, 天数)
         —— 复盘人格指令:「对局已结束, 你是 X 号位的扮演者, 用第一人称
             诚实复盘, 可以承认欺骗/失误, 禁止剧透未公开的引擎内部字段名」
       messages = [identity user msg] + memory 快照(截断到预算) +
                  [user: "观众提问: ..."]
    3. registry.Get(modelKey).Chat(parentCtx + extendedTimeout)  // §197
       AgentClassName = LsmAgentGame-Werewolf-Recall               // §24
    4. 失败 → 返回友好降级文案(不报 500; bot「太累不想复盘」)
    5. ScrubIdentityLeak 已经无意义(身份已终局公开), 但仍跑一遍
       normalizeDeathTerms 保持术语一致(§123)
```

关键设计决策：
- **Memory 冻结**：复盘期间 bot 的 `Run` 循环已停（游戏结束），`Memory.Snapshot()`
  天然是冻结态；不需要额外 freeze 标志。
- **单轮问答**：不复用 bot 的 `Run`/`Memory.Push` 循环——复盘问答**不写回** Memory，
  避免污染下一局的 `recentMessages`（§128：复盘对话不是对局内思考）。
- **预算**：memory 快照走与正常调用相同的 `MaxPromptBytes` 截断链
  （`PruneByBytes`），不会因为是赛后路径就膨胀。
- **不写 chat 表**：复盘问答是纯请求/响应，不进 `chat_message` /
  `chat_history` 队列（它不是对局信息流，§119 的反面——对局已结束，
  没有「频道隔离」对象需要保护）。

### 3.3 前端

- `SettlementModal` 新增「💬 复盘问答」折叠面板：
  - bot 座位下拉（显示座位号 + 角色 + 模型名——终局身份已公开）；
  - 提问输入框（≤200 字）+ 问答历史列表（本地 state，不落库）；
  - 失败时按 §7.1 规范：面板内联红条 + `reportGlobalError` 兜底。
- 仅当 `game.state.status=="over"` 时渲染入口；观战者与玩家共用同一面板。
- i18n 三语种新增 `werewolf.recall.*` 键（约 10 个）。

## 5. 验收标准

1. `go build ./...` + `go test ./game/werewolf/... ./agent/... ./service/...` 全绿。
2. 新测试覆盖：
   - U1：赛后迭代真实写入 DB（含乐观锁冲突重试）；混合房间只给人类座位生成画像；
     全 AI 房间整链 no-op；开关关闭 no-op；prompt 块在无画像时不渲染。
   - U2：非房间成员 403；游戏未结束 400；超限流 429；Memory 快照不被复盘写回
     （复盘后 `Memory.Len()` 不变）；LLM 失败返回降级文案而非 500。
3. 前端 `tsc --noEmit` + `npm run build` 通过；SettlementModal 复盘面板
   在 over 态可见、提问有回答/有降级提示。
4. `./rebuild_restart_app.sh` 重启成功，无 panic 日志。
