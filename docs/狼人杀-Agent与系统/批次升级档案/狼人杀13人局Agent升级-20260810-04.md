## 1. U1：`wolf_whisper` 夜间挂载修复（K3 §0 F1）

### 1.1 现状与缺陷

- `tools_wolf.go:24` 把 `wolf_whisper` 注册为 `Phase: ToolPhaseSpeak`，`MountTools`/`mountFromRegistry` 按 phase 过滤后，**夜间 `night_wolves` 阶段根本不挂载**——但工具描述第一句就写着「夜间刀人前协调目标」。
- `MountIf` 还要求 `gc.WolfTeammateSeat >= 0`（§132 的 30% 开局互知率）——即 **70% 对局狼队白天也不能私聊、100% 对局夜间无法协商刀人**。狼人夜间实际是纯盲投（`engine_night.go::tallyWolfVotes`），与工具描述严重不符。
- 服务端 `agentRunner.WolfWhisper`（`agent_runner.go:1267`）与 `WolfPackRoom`（`room_agent.go:37-40`，`SetMembers(allWolfSeats)`）**从不依赖 `WolfTeammateSeat`**——通道本身一直存在，只是工具层没挂。

### 1.2 修复方案

1. **`ToolSpec` 增加多阶段支持**：新增可选字段 `Phases []ToolPhase`（非空时优先于 `Phase`），`MountTools`/`mountFromRegistry` 的 phase 匹配改为 `specMatchesPhase(t, phase)` 单点函数（避免 §135 式复制判定）。
2. **`wolf_whisper` 注册改为 `Phases: [speak, night]`**；`MountIf` 去掉 `WolfTeammateSeat >= 0`，仅保留 `Faction == "wolf"`（服务端二次校验 `Roles[seat]==RoleWerewolf` 不变，双重防御保持）。
3. **`BuildTools` 的 `night_wolves` case** 追加 `mountFromRegistry(add, ToolPhaseNight, gc)`，让 registry 中 night 阶段工具（wolf_whisper）与内联 `wolf_kill` 一同挂载。

### 1.3 约束核对

- **§97 五处同步**：本项**不新增 phase、不新增动作**，仅扩大既有工具的挂载窗口 —— `SkipPhaseAction`/`watchdogActingSeat`/`dispatchQuarantinedSkipLocked`/`isActingPhase`/`defaultPhaseDeadlineSec` 均无需改动（`night_wolves` 五处映射早已存在）。
- **§119/§133 协议层隔离**：留言仍只入 `WolfPackRoom` → 狼 bot user prompt（`WolfPackPromptBlock`），不入 chat_message / chat_history / HeartThought。
- **§130 接线验证**：`specMatchesPhase` 写完当场 grep 确认 `MountTools` 与 `mountFromRegistry` 两个消费点都改为调用它。

## 2. U2：`wolf_kill` 刀人理由（K3 §1 S1 二期）

### 2.1 动机

狼人夜间从「各自为战的盲投」升级为「有限带宽下的真实协商」（U1）后，投票仍只有 target 一个维度。K3 S1 二期建议：`wolf_kill` 附带一句 ≤30 字刀人理由，让其他狼在 GameContext 看到 `WolfVotesWithReason`——观众/队友能看见「狼队为什么刀这个人」的决策痕迹。

### 2.2 实现方案

1. **引擎**：`GameState` 新增 `WolfVoteReasons [MaxPlayers]string`，`startNight()` 与 `WolfVotes`/`WolfVoteCast` 一同重置；`NightWolfKill(actor, target Seat, reason string)` 记录理由（rune 截断 ≤30 字；弃权/空理由记 ""）。
2. **双路径同步（§92b）**：
   - `Action_WolfKill(roomID, userID, target, reason)`（manager/WS 路径；`ws/game_service_werewolf.go` 人类路径传 ""）；
   - `wolfKillLocked(r, userID, target, reason)`（watchdog/quarantine 路径传 ""）；
   - 弃权复位分支同步清 `WolfVoteReasons[seat] = ""`。
3. **Agent 工具链**：`ToolRunner.WolfKill(target int, reason string)`（实现方仅 `agentRunner` + 测试 `fakeRunner` 两处）；`wolf_kill` schema 增加可选 `reason` 字段并在描述中说明「≤30 字，队友可见」。
4. **GameContext**：新增 `WolfVoteReasons map[int]string`（seat→reason，与 `WolfVotes` 同条件：仅狼人、仅 `night_wolves`、仅已投票且理由非空）；`prompt.go` 夜间投票渲染处把「N号→X号(理由:…)」拼入。

### 2.3 约束核对

- **§119**：理由只入狼 bot GameContext，不入公屏/chat 表。
- **§135**：理由文本可能含身份词，`ScrubIdentityLeak` 只管公屏发言；wolfpack 通道本就对非狼不可见，无身份泄露面。reason 进 GameContext 前做一次 rune 长度截断（≤30），防 LLM 超长注入队友上下文。
- 视图层（`view.go`）**不下发** `WolfVoteReasons` 给人类客户端——保持狼队通道对玩家不可见（仅 bot 间可见，与 `WolfVotes` 现有下发策略一致：人类玩家视图本就有 wolf_vote_view，但理由属狼队内部语义，暂只进 bot prompt，不进 ClientGameState，最小改动）。

## 3. U3：警徽流按真实查验历史结算（K3 §0 F3 + LongCat §2 F3）

### 3.1 现状与缺陷

- `streamFaction`（`sheriff_stream.go:20-25`）直接读 `gs.Roles[target]` 底牌，**不校验预言家是否真的查验过该目标**（注释自承「完整历史查验未来扩展」）。
- 假预言家当警长后可借警徽流「验」任何人且服务端权威为真 → 狼队可利用此漏洞无限造谣（P1 公平性漏洞，与 §135 身份公开规则同源）。
- LongCat 补充的关键点：`Player.LastSeerCheck` 只存**最后一次**查验，即便想校验也没有历史数据 —— 第一步必须加 `SeerCheckHistory`，且警徽流可能在预言家**死后**结算，历史必须存在 `GameState`（Player 结构）而非依赖存活状态。

### 3.2 实现方案

1. **`Player.SeerCheckHistory []Seat`**：`NightSeerCheck` 成功时追加（`gs.Players[actor].SeerCheckHistory = append(..., target)`）；`engine.go:635` 的重开局复位路径同步清零。
2. **`streamFaction(gs, seer, target)` 单点判定（§135 模式）**：目标存活 **且** `target ∈ gs.Players[seer].SeerCheckHistory` → 返回真实阵营；否则 `"unknown"`（按撕警徽倾向处理）。`isGoldWater`/`isWolfKill` 同步加 `seer` 参数；唯一消费点 `SettleSheriffOnDeathLocked` 传入 `deadSeat`（死去的警长即声明警徽流的预言家）。
3. **语义**：真查过 → 按真实阵营结算；没查过 → 声明无效（单流撕警徽；双流中 unknown 落入 default 撕警徽分支），假预言家造谣空间被关闭。

### 3.3 约束核对

- **§92a**：`streamFaction` 是纯函数（无锁），`SettleSheriffOnDeathLocked` 调用方已持 `r.mu`，不新增锁内变体需求。
- **§130**：`SeerCheckHistory` 写入点（`NightSeerCheck`）+ 读取点（`streamFaction`）当场 grep 确认。
- **向后兼容**：`LastSeerCheck` 字段保留不动（`view.go:486` 预言家自己视图、`room_agent.go:748` GameContext 仍用），只新增历史字段。

## 4. U4：记忆迭代注入真实对手模型映射（LongCat §1 D4）

### 4.1 现状与缺陷

- §131 记忆迭代强制 4 段标题，第 3 段「## 其他模型特点分析」要求 LLM 分析对手模型——但喂给迭代的 `seatFacts`（`agent_memory_bridge.go::buildSeatMemoryFacts`）只有 7 个标量（房间/座位/自己模型/角色/胜方/死活/天数），**整条链路上不存在任何「几号位是哪个模型」的映射**。
- 后果：LLM 被强制写一个没有数据支撑的段落，只能编造；编造被 `SaveIterated` 持久化进 DB，下一局又被 `InjectBlock` 注入 prompt —— **幻觉被持久化并跨局复利**。
- 附带缺陷：`InjectBlock` 是**头部 4000 rune 截断**（段落顺序即重要性），排在第 4 段的「决策策略迭代」（唯一真正指导行为的段落）在记忆变长后最先被丢弃。

### 4.2 实现方案

1. **`buildSeatMemoryFacts` 注入真实映射**：函数已持锁（`lockRoomBriefly`），直接读 `r.seatModelKeys`，追加「本局对手模型映射: 1号=GLM-model; 3号=Kimi-model; …」（跳过自己座位；无其他 bot 时写「本局无其他模型玩家」）。第 3 段从此有据可依。
2. **`InjectBlock` 按段配额**：新增 `TruncateMemoryBySections(md string, maxRunes int)`：按 4 个固定标题切段，每段配额 `maxRunes/4`（各段独立截断，标题永远保留），拼回；任一标题缺失（旧格式/异常记忆）回退现有头部截断。`InjectBlock` 改调新函数，总配额仍为 `MemoryInjectMaxRunes=4000`。

### 4.3 约束核对

- **§131 注入位置不变**：仍走 user prompt 末尾（`InjectBlock` 消费点不动）。
- **§118 异步不阻塞**：`buildSeatMemoryFacts` 本就在异步迭代 goroutine 内（锁内快照 → 锁外用），无新增阻塞。
- **纯函数可测**：`TruncateMemoryBySections` 与 `BuildIterationPrompt` 同为 wwplayer leaf 纯函数，单测直接覆盖。
