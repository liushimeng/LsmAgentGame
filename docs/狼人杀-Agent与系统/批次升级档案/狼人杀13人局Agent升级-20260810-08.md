## 2. 设计

### 2.1 总体：一个真相源，三条消费链路

```
                    ┌──────────────────────────────────┐
   17 处写入点 ───▶ │  InformationLedger (r.infoLedger) │  ← §20260810-05 一期（不改）
                    └───────────────┬──────────────────┘
                                    │
            ┌───────────────────────┼───────────────────────┐
            ▼                       ▼                       ▼
   ① 行为侧（本期新增）      ② 观战侧（本期新增）      ③ 审计侧（本期新增）
   KnowledgeDigest          InfoEntryJSON 时序图      InfoLeak 说漏嘴检测
   → gc.KnowledgeDigest     → cs.InfoLedger（已有）   → cs.InfoLeaks[]
   → prompt「🗂 知情清单」   → HistoryDrawer 🗂 tab    → HistoryDrawer 🗂 tab 告警区
   （全体 bot 可见自己的）    （spectator only）        （spectator only）
```

**三条链路共享同一 `r.infoLedger`，互不写入**——读取侧全程只读，杜绝一期建立的写入不变量被破坏。

### 2.2 链路 ①：行为侧 —— `KnowledgeDigest` 注入 Agent prompt

#### 2.2.1 为什么不是「把账本原文塞进 prompt」

一期账本单局 ~250 条、每条 ≤120 rune，全量塞入 prompt ≈ 30K rune ≈ 15K token/轮/bot × 7 bot = **每轮 105K token**，直接击穿 §197 的长预算与成本模型。

**因此二期设计的核心是「摘要而非原文」**：`KnowledgeDigest` 是**按来源聚合的计数 + 最近 N 条要点**，而不是逐条流水账。

#### 2.2.2 数据结构（`ServerGo/agent/wwtypes/context.go` 新增）

```go
// KnowledgeDigestEntry 是「本座位从某来源获知的信息」的聚合摘要。
// 2026-08-10 §20260810-08 信息账本二期 —— 行为侧消费链路。
type KnowledgeDigestEntry struct {
    Source     string   `json:"source"`      // InfoSource 字符串值
    Count      int      `json:"count"`       // 本座位从该来源获知的条目总数
    LastRound  int      `json:"last_round"`  // 最近一条的 round
    Highlights []string `json:"highlights"`  // 最近 ≤2 条要点（已 redact，≤60 rune）
}

// KnowledgeDigest 是注入 GameContext 的「我的知情清单」。
// §119：仅本人 bot 可见；不进 chat_message / chat_history。
// §135：Fact 已在写入侧 redactLedgerFact，不含身份明文。
type KnowledgeDigest struct {
    Seat        int                    `json:"seat"`
    TotalKnown  int                    `json:"total_known"`   // 本座位知情条目总数
    TotalInRoom int                    `json:"total_in_room"` // 全房条目总数（信息劣势感知）
    Entries     []KnowledgeDigestEntry `json:"entries"`       // 按 Count 降序，≤6 条
}
```

`GameContext` 新增字段：

```go
// KnowledgeDigest 是本 bot 的「知情清单」摘要（§20260810-08 信息账本二期）。
// 由 buildAgentContextLocked 从 r.infoLedger 聚合；nil 表示账本为空。
KnowledgeDigest *KnowledgeDigest `json:"knowledge_digest,omitempty"`
```

#### 2.2.3 账本侧新增聚合方法（`information_ledger.go`，全部 `*Locked` 语义）

```go
// DigestForSeat 聚合「某座位知情的全部条目」为按来源分组的摘要。
// caller 必须持 r.mu（§92a）。maxHighlights 控制每组要点条数。
func (l *InformationLedger) DigestForSeat(seat int, maxHighlights int) *SeatDigest
```

- 逐条扫描 `l.entries`（≤400 条，O(n) 且 n 有硬上限，单次 <10μs，锁内可接受）；
- 命中 `e.KnowerSeats[seat]` 的条目按 `e.Source` 分组计数；
- 每组保留最近 `maxHighlights`（默认 2）条 `Fact`，按 60 rune 二次截断；
- 按 `Count` 降序输出，最多 6 组（避免 prompt 膨胀）。

**预算核算**：6 组 × (1 行标题 + 2 条 ≤60 rune 要点) ≈ 400 rune ≈ 200 token/轮/bot，7 bot 合计 ~1.4K token/轮。与 §120 的既有 prompt 块同量级，可接受。

#### 2.2.4 prompt 渲染（`agent/wwplayer/prompt.go` 新增 `KnowledgeDigestBlock`）

拼接位置：`BuildUserPrompt` 末尾，**在 `HypothesisTableBlock` 之前**——语义上「我知道什么」应先于「我猜谁是谁」。

```
【🗂 你的知情清单（第 3 天）】
你共掌握 24 条信息;本局全房累计产生 87 条 —— 你处于信息劣势,发言时注意别暴露你知道得比表现出来的多。
- 公开发言 ×12（最近:「3号说他昨晚验了…」/「7号反驳…」）
- 私聊 ×5（最近:「你信我吗」）
- 狼队密语 ×4（最近:「今晚刀 5」）
- 预言家查验 ×2（最近:「查验 seat=3」）
⚠️ 注意:狼队密语 / 私聊 / 夜间技能属于**私密来源**,白天公开发言引用这些内容等于自曝身份。
```

**最后一行是本块的战术价值核心**——它把「说漏嘴」这个抽象风险，变成每轮 prompt 中的显式约束。

#### 2.2.5 §119 隔离验证

- `KnowledgeDigest` 只经 `GameContext` → user prompt，**不**写 `BotTranscript`、**不**入 `chat_message` / `chat_history`；
- 内容源自 `redactLedgerFact` 之后的 `Fact`，天然不含身份明文（§135）；
- 每个 bot 只能拿到 `DigestForSeat(自己的 seat)`，`buildAgentContextLocked` 的 `seat` 参数是唯一入口。

### 2.3 链路 ③：审计侧 —— 说漏嘴检测（`information_leak.go`）

#### 2.3.1 检测原理

一条公开发言若**引用了只在私密来源出现过的具体信息**，即为「说漏嘴」。判定要素：

1. **私密来源集合**：`whisper` / `wolf_pack` / `night_seer` / `night_witch` / `night_guard` / `night_wolf_vote` / `prop_inject` / `role_deal`（其余为公开来源）。
2. **指纹 —— 两套编号并存，必须按模式分支归一化到引擎内部 0-indexed**：账本 fact 在同一账本内**两套编号并存**，漏解析或错解析都会让检测完全失效 —— 这是本期最容易被后人踩的坑，必须落文档：
   - **0-indexed（结构化 Action_* 写入点）**：`seer_check seat=%d target=%d`（`room_action.go:69`）、`wolf_vote seat=%d target=%d reason=%s`（`:1017`）、`wolf_pack from=%d text=%s`（`agent_runner.go:1300`）、`role_deal seat=%d`（`:307`）—— 机器生成，`%d` 直接取自 `int(seat)`。
   - **1-indexed（人类可读）**：`InfoSourcePublicSpeech` / `InfoSourceWhisper` / `InfoSourceDeathEvent` 的 fact 来自人类/bot 发言原文（`room_chat.go:97`/`:152`/`:220`），且 `wolf_pack` 内嵌的 `text` 字段也是人手写（"今晚刀5号"）；`activity_emitter.go:778` 死亡事件拼成 `"💀 " + strconv.Itoa(seat+1) + "号 死亡(...)"`；prompt 渲染统一按 1-indexed 输出（`agent/wwplayer/prompt.go:236` `itoa(seat+1) + "号→"` / `:253` / `:320` 等）。
   - **归一化规则**：`extractSeatRefs` 维护两份正则列表：
     - `seatRefZeroIndexed` 匹配 `seat=N` / `target=N` / `from=N` / `to=N`（`\b` 词边界避免误命中），原值保留作为 0-indexed ref；
     - `seatRefOneIndexed` 匹配 `N号` / `第N位`，捕获的 N 是 1-indexed，**归一化时 -1**；
     - 两者结果合并到同一 `map[int]bool`，范围校验 `0 <= seat < MaxPlayers`。这套规则下的「私密 seat=4 / 公开 5号」会被正确交叉命中（4 == 5-1）。
   - **R213 教训**：早期版本对三种形式统一按 0-indexed 解析，导致真实泄漏系统性漏报（私密 `seat=4` vs 公开「5号」= 内部 4 永远对不上）且产生系统性误报（「5号」被解析成 ref=5 与另一条 `seat=5` 私密条误交叉）。
3. **判定**：某座位 S 的公开发言 P，其指纹集合 F(P) 中若存在座位号 n，满足
   - 存在一条私密条目 E，`E.KnowerSeats[S] == true` 且 `n ∈ F(E.Fact)`，且
   - 在 P 之前**不存在**任何公开条目 E' 使 `n ∈ F(E'.Fact)`，
   - **且 `n != S`**（R213 修复：跳过自指；`role_deal` 给每个座位种下「私知自己座位号」，不跳过会产生每局 ~13 条稳定噪声，淹没真实信号），
   则记一条 `InfoLeak{Seat:S, Seq:P.Seq, HintSeat:n, FromSource:E.Source}`。

即：**「这个座位号，你只可能从私密渠道知道，但你公开说出来了」**。

> **⚠️ 定位声明（防止误用）**：本检测是**观战者侧的复盘线索**，不是作弊裁决器。座位号在狼人杀里是最高频词，误报不可避免（例如「我觉得 5 号今天很沉默」纯属公开观察）。因此：
> - **绝不**据此惩罚、quarantine、扣分或干预对局；
> - **绝不**下发给对局内玩家（含 bot），避免污染博弈；
> - UI 文案必须写明「疑似 / 仅供复盘参考」。

#### 2.3.2 数据结构

```go
// InfoLeak 一条「疑似说漏嘴」记录（§20260810-08 审计侧）。
// 仅 spectator 下发；绝不进入 GameContext / prompt / chat 通道。
type InfoLeak struct {
    Seq        int64      `json:"seq"`         // 触发检测的公开发言条目 Seq
    Seat       int        `json:"seat"`        // 疑似说漏嘴的座位
    Round      int        `json:"round"`
    Phase      string     `json:"phase"`
    HintSeat   int        `json:"hint_seat"`   // 被提及、且仅私密可知的座位号
    FromSource InfoSource `json:"from_source"` // 该私密信息的来源
    Excerpt    string     `json:"excerpt"`     // 公开发言摘录（≤60 rune）
}
```

#### 2.3.3 计算时机：**懒计算，不进热路径**

**不**在 `appendRoomMessage` 里做（每条发言 O(n²) 扫描会拖慢聊天热路径）。改为在 `BuildClientStateWithRoom` 的 `viewer < 0` 分支**按需计算**，并加**结果缓存**：

```go
// leakCacheSeq 记录上次计算时账本的 seq；账本未增长则直接复用缓存。
leakCache    []InfoLeak
leakCacheSeq int64
```

观战者刷新频率 ≈ 每秒 1 次，账本 ≤400 条，最坏 O(400 × 400) = 160K 次 map 查询 ≈ 1ms，且有 seq 缓存兜底（无新条目时 0 开销）。**锁内可接受**。

> **§92a 硬约束**：`detectLeaksLocked` 必须是锁内变体，由已持 `r.mu` 的 `BuildClientStateWithRoom` 调用——这正是 R212 自死锁的案发函数，**绝不允许**在其中新增任何 `Lock()`。

### 2.4 链路 ②：观战侧 —— 信息传播时序图

前端 `HistoryDrawer` 新增第 6 sub-tab **「🗂 信息流」**（仅 spectator，与 🤖 独白 / 🔮 假说同隔离级别）。

## 5. 决策记录

- **D-01 为什么 digest 而非账本原文进 prompt**：全量 ~250 条 ≈ 15K token/轮/bot，7 bot × 每轮 = 105K token，成本不可接受且触发 §197 长响应风险。摘要方案压到 ~200 token/bot。
- **D-02 为什么泄漏检测用座位号指纹而非文本关键词**：一期 `redactLedgerFact` 已把角色词抹成 `▪`（§135 正确决策，不应回退），文本交叉失效；座位号是狼人杀信息的最小可识别单元，且天然不含身份。
- **D-03 为什么泄漏检测懒计算 + 缓存而非写入时增量**：写入路径（`appendRoomMessage`）是聊天热路径，每条发言 O(n²) 扫描会拖慢全房广播；观战者读取频率低且有 seq 缓存，代价可忽略。
- **D-04 为什么 `KnowledgeDigestBlock` 排在 `HypothesisTableBlock` 之前**：认知顺序「我知道什么」→「我据此猜谁是谁」，与 LLM 推理链自然顺序一致；且 prompt 末尾（最高注意力段）留给假说表更利于决策。
- **D-05 为什么泄漏检测只做观战者提示而不做惩罚**：座位号误报率高（「我觉得 5 号沉默」是纯公开观察），一旦用于扣分/quarantine 会造成大量误伤；且把检测结果回灌给 bot 会污染博弈（bot 会学会规避检测而非规避说漏嘴）。定位为**复盘线索**是唯一安全的落点。
- **D-06 为什么 `gc.KnowledgeDigest` 对全体 bot 开放而非仅狼人**：好人同样需要感知「我处于信息劣势」；且 `TotalInRoom` 对比是公平的（双方都知道全房总量，不知道对方具体知道什么）。

## 6. 三期展望（不在本期范围）

1. **账本反向驱动 prompt 组装**：把 `RecentSpeeches` / `WhisperInbox` / `WolfVotes` 等散落字段**全部**改从账本按 `KnowerSeats` 查询装配，彻底消除 D1 类缺陷的诞生土壤（本期只做「叠加 digest」，不动既有字段，降低回归风险）。
