# 狼人杀 13 人局 Agent「对话即思考」设计

> 2026-07-12 §128 重构核心方法论文档。
> 围绕 LLM API 调用的本质,全面删除冗余的"思考"环节。

---

## 1. 核心论点

**LLM API 调用的输出本身就是"思考的产物"**——模型返回的 `text` + `tool_use` 已经包含了推理、决策和行动的全部信息。当前系统曾在此之上叠加了 5 层冗余的"思考"环节(兼容字段 + ParallelThink + idle_think + SeatCell 内嵌 heart_thought + 文档语义混淆),本节明确全部删除,**对话即思考**。

LLM 不在"思考"——它已经在响应。真正的"思考"已发生在 API 内部的 token 生成过程中(Anthropic 自家的 prompt processing + sampling),玩家无需看到中间步骤。

## 5. 协议层 thinking block 处理

### 删除前(原 §122 行为)

1. 请求侧:`req.Thinking = &ThinkingConfig{Type:"enabled", BudgetTokens:4096}`
2. Anthropic 流式:`thinking_delta` → 累加到 `bb.Thinking`
3. 响应:`ContentBlock{Type:"thinking", Thinking: ...}` 与 text 块并列
4. `recordAssistant` push 到 `Memory.messages`,但 UI 永不消费
5. 某些代理(DeepSeek/GLM)要求每个 assistant 消息必须有 thinking 块 → stub 占位

### 删除后(§128 行为)

1. 请求侧:`req.Thinking = nil`
2. Anthropic 流式:`content_block_delta` 仅识别 `text_delta` / `input_json_delta`
3. 响应:`ContentBlock{Type:"text"|"tool_use"|"tool_result"}` 三种类型
4. `Memory.messages` 仅存 text + tool_use + tool_result,无冗余 thinking
5. 代理要求兼容:在 DeepSeek/GLM 代理测试中验证 text-only 也能正常工作(2026-07-10 后默认行为)

### 失败兜底

如果某些旧代理(2026-07-10 前 DeepSeek/GLM 强依赖)出现 400 "missing thinking parameter":
1. **首选**:联系代理运维升级,或切换 provider endpoint
2. **次选**:在 `LsmAgentGame.conf` 的 `llm.providers[].endpoint` 切到不需要 thinking 的代理
3. **不再**:在 agent 层加 auto-healing fallback — §128 删除该逻辑以保持代码简单

## 7. idle_silent 工具合并设计

### 删除前(双工具)

| 工具 | 调用方 | 语义 |
|------|--------|------|
| `idle_think` | 玩家(白名单 phase) | 沉默思考,不广播,留 audit |
| `idle_silent` | 法官 / 玩家(仅 pre_wolves) | 同上 |

### 合并后(§128 单工具)

```
idle_silent {
  reason: string,        // ≤ 50 字
  role: "player"|"judge" // 默认 player
}
```

### ToolRunner 接口

```go
type IdleSilentRunner interface {
    IdleSilent(role, reason string) (string, error)
}
```

### 派发逻辑

- `idle_silent` 工具被 LLM 调用时 → `dispatchTool` 走 `IdleSilentRunner.IdleSilent(role, reason)`
- run.go handleEvent 在 spectator_speech 路径上自动追加 `[idle_silent]` 审计行(role=player)
- 法官侧 `idle_silent` 由 `JudgeRunner` 实现(role="judge" 审计行格式略有不同)

## 10. 教训(Lessons Learned)

### (a) "思考"语义在不同文档间歧义

- §重构前:BotTranscript.LastThinking 指 LLM 的"完整 CoT"(模型内部推理文本)
- §122:ParallelThink 指"辅助并行推理 worker"
- §119:HeartThought 指"speak_with_thought 的 internal_thought 字段"
- §126:"思考中 N 秒"指"LLM 调用进度状态机"

四种不同含义混用同一关键词,导致大量认知开销。§128 后统一为:
- **对话**(text + tool_use)= 模型推理 + 决策 + 行动的总和
- **响应** = LLM API 调用进行中
- **内心独白**(HeartThought)= LLM 主动通过工具声明的"心口不一"
- **决策可观测** = LastDecisionSummary / LastToolInput 等 5 字段

### (b) 协议层冗余 vs 协议层能力

Anthropic thinking block 是协议层**能力**,但客户端是**冗余**消费者。客户端应该明确:
- 哪些字段必须消费(text / tool_use / tool_result)
- 哪些字段是协议能力但不消费(thinking / signature)
- 哪些字段是协议层约束但语义无意义(stub 占位)

§128 明确只消费 text / tool_use / tool_result,其余当作"协议层黑盒"。

### (c) LLM 不在思考,它在响应

这是最容易混淆的一点。LLM 推理发生在 token 生成过程中,**玩家视角只看到响应**。UI 上写"思考中 N 秒"暗示 LLM 正在推理,但实际上 LLM 已经在 streaming 输出 token(PhaseStreaming)或等待 HTTP 响应(PhaseCalling)——这都是"响应"而非"思考"。

### (d) 自动愈合 fallback 要谨慎

§122 / §127 / §128 反复涉及"auto-healing fallback":
- §127:auto-healing 解决 §122 的"上游缺 thinking 配置导致 400"
- §128:**删除**该 fallback

教训:**auto-healing 不能解决根本问题**(代理 / 上游的协议要求),只能拖延暴露。当重构上线后,如果某些代理真的需要 thinking block,正确的做法是**联系代理运维或切换 endpoint**,而不是在客户端叠加兼容逻辑。

### (e) "兼容字段置空"是技术债务

BotTranscript.LastThinking / FullThinking / RecentMessages 三个字段在 §重构(2026-07-09)后置空,保留 wire 兼容。这是**渐进式重构的合理选择**,但累积 3 天后(§128)就应该物理删除,而不是无限期保留。
