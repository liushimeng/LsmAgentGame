## U1. 法官多轮记忆（Narrative Continuity）

### 1.1 现状与痛点

**现状**：`AgentJudge` 每次唤醒都是**单轮无状态调用**——`Messages` 恒为一条 user prompt（`ServerGo/agent/wwjudge/judge.go:336-341`），无任何历史。

**痛点**：
- 法官不可能说出「正如昨天所说」「这已是本局第三次平票」这类承上启下的话，整局旁白是 N 条互不相干的独白。
- 叙事断裂导致观众/玩家觉得法官是「每局一次复读机」而非「真正的赛事主持人」。
- K3 文档 A3、M3 文档 G3、LongCat 文档 G3 三方独立指出此问题——共识度极高。

**数据现状**：`judge.go` 每次唤醒已经构造好完整的 `Messages []llm.Message`，且 `judgeWakeKind` 已记录唤醒原因（§130 两段式）。要做的就是**给法官加一个轻量环形缓冲**。

### 1.2 设计

#### 数据结构

```go
// ServerGo/agent/wwjudge/judge_memory.go (新增)
package wwjudge

// JudgeMemoryRing 是 AgentJudge 的轻量环形缓冲
// 容量 20 条，超过自动覆盖最早的 announce 文本
// 协议层隔离：只存法官自己的输出文本，绝不存 GameSnapshot（含 WolfSeats 等全知视野）
type JudgeMemoryRing struct {
    mu       sync.Mutex
    capacity int           // 默认 20
    entries  []JudgeMemoryEntry  // FIFO
}

type JudgeMemoryEntry struct {
    Round      int    `json:"round"`
    Phase      string `json:"phase"`
    WakeKind   string `json:"wake_kind"` // announce / prompt_actor / summary / declare_cause
    Text       string `json:"text"`     // 法官本次 announce 的原文
    Timestamp  int64  `json:"ts"`
}
```

#### 接入点（3 处）

1. **写入**：`AgentJudge.AnnounceLocked`（或任何发送 announce 的路径）成功后追加一条 `JudgeMemoryEntry`。
2. **读取**：在 `judge.go` 构造 `Messages` 时，把 `JudgeMemoryRing.Snapshot()` 的最近 8 条作为 `assistant` 历史消息插入到 user prompt 之前（Anthropic 协议要求 `user/assistant` 交替）。
3. **清理**：`finishCoolingLocked`（§129）或 `stopAgentsLocked` 时 `Memory.Reset()`。

#### Anthropic 协议约束（§14.1）

- 历史消息的 role 必须是 `assistant`（法官自己的输出），不能是 `user`
- 不能把 `GameSnapshot` 任何字段（`WolfSeats` / `SeerCheckResults` 等）写进历史——只能写法官自己 announce 出去的**已公开**文本
- messages 数组必须严格交替——`SanitizeMessagesForAnthropic` 已存在，传入即可

### 1.3 影响面与改动量

| 文件 | 改动 |
|------|------|
| `ServerGo/agent/wwjudge/judge_memory.go` | 新建（约 80 行） |
| `ServerGo/agent/wwjudge/judge.go` | +30 行：`MemoryRing *JudgeMemoryRing` 字段 + 写入/读取 2 处 |
| `ServerGo/agent/wwjudge/judge.go` reset 路径 | +10 行：`stopAgentsLocked` / `Reset()` 调用 |

**总改动**：~120 行。**零前端改动**。

### 1.4 测试用例

`ServerGo/agent/wwjudge/judge_memory_test.go`：
1. 容量上限：超过 20 条后第 1 条被覆盖
2. 严格交替：注入 3 条历史后 `Messages` 数组 user/assistant 顺序正确
3. 协议层隔离：尝试写入包含 "WolfSeats" 字样的 entry 应被 SanitizeMessagesForAnthropic 拒绝
4. Reset：冷却后 `Snapshot()` 返回空

### 1.5 风险评估

- **§119 协议层隔离**：法官 announce 本身就是要广播的文本，不存在"内部独白泄露"问题 ✅
- **§197 流式续命**：不涉及 LLM 调用路径变更 ✅
- **§128 对话即思考**：不新增 `BotTranscript` 字段（法官没有 BotTranscript）✅
- **§130 接线验证**：写入/读取点各 1 处，grep 即可验证 ✅

## U2. Bot 票型回灌（LastRoundVoteMap）

### 2.1 现状与痛点

**现状**（LongCat-D1 文档确认的最严重公平性缺陷）：
- `EmitVoteCast` 广播 `🗳 N号 投票给 M号`，但末位参数 `silentForBots=true`（`activity_emitter.go:284-285`）
- `silentForBots=true` 的语义是**直接 return，不进 500K 队列**（`room_chat.go:85-88`）
- `GameContext` 中**没有任何**白天票型字段——`grep "Vote" agent/wwtypes/context.go` 只有 `MyVoted` / `AllVoted` / `WolfVotes`（狼人夜间专用）/ `RestartVote*`
- `ClientGameState.Votes` 是 `map[seat]count` **聚合计数**，不含投票人

**后果**：**7 个 LLM 在缺失核心推理素材的情况下与人类对局**。票型分析是狼人杀最核心的推理素材（"昨天跟着我票的人今天倒戈了"），目前 Agent 完全看不到「谁投了谁」。

**人类能看到票型**（`useChat.ts:103` 收进聊天流 + `BroadcastRoomIncludingSpectators`），但 Agent 看不到。**这是 §135 公平性的镜像反例**——人类玩家拥有 Agent 看不到的推理素材，跨模型胜率数据全部在这个偏差下产生。

### 2.2 设计

#### 数据结构

```go
// ServerGo/agent/wwtypes/context.go 新增字段
type GameContext struct {
    // ... 既有字段 ...
    
    // LastRoundVoteMap 上一轮白天投票的「谁投了谁」映射
    // key = voter seat (1-13), value = target seat (1-13)
    // 仅在白天投票阶段结束后填充；其他阶段为空 map
    LastRoundVoteMap map[int]int `json:"last_round_vote_map,omitempty"`
}
```

#### 改造方案（采用 LongCat-D1 推荐方案 B：聚合后下发）

**方案 B：投票结束时聚合成一条结构化事件**，而非方案 A 的"每条都广播"。理由：
- 13 人局每轮产生 13 条队列消息 → 改为 1 条聚合消息，队列成本 1/13
- 避免 13 条文本注入 LLM 上下文导致膨胀
- 给 `GameContext` 加 `LastRoundVoteMap map[int]int`，prompt 能结构化引用而非依赖文本解析

#### 接入点（5 处）

1. **聚合入口**：`finishVoteLocked`（投票结算路径）后追加一条结构化事件
   ```go
   // activity_emitter.go 新增函数
   func EmitVoteTallyForBots(votes map[int]int, silentForBots bool) {
       // 聚合为 "🗳 票型: 1→3, 2→3, 4→5 …" 一条
       // silentForBots=false（关键修改）→ 进 500K 队列
   }
   ```

2. **GameContext 填充**：`buildAgentContextLocked`（`room_agent.go`）新增：
   ```go
   if gc.CurrentRoundVoteMap != nil {
       gc.LastRoundVoteMap = gc.CurrentRoundVoteMap
   }
   ```
   并在 `startDay` 时把上一轮的 `CurrentRoundVoteMap` 复制到 `LastRoundVoteMap`，然后清空当前轮。

3. **Prompt 注入**：`prompt.go::BuildSystemPrompt` 末尾新增一段（仅在 `LastRoundVoteMap` 非空时）：
   ```
   🗳 上一轮投票结果（你刚刚收到的实时票型）:
   - 1 号投了 3 号
   - 2 号投了 3 号
   - 4 号投了 5 号
   …
   ```

4. **view.go 透传**：确保 `LastRoundVoteMap` 不下发到 `ClientGameState`（仅注入 LLM prompt；人类玩家已通过聊天流看到票型，不重复下发避免冗余）

5. **PlayerJSON 不变**：人类玩家 UI 已能看到票型，无需改动。

### 2.3 影响面与改动量

| 文件 | 改动 |
|------|------|
| `ServerGo/agent/wwtypes/context.go` | +5 行：`LastRoundVoteMap map[int]int` 字段 |
| `ServerGo/game/werewolf/activity_emitter.go` | +50 行：`EmitVoteTallyForBots` 函数 |
| `ServerGo/game/werewolf/room.go` 或 `engine_day.go` | +30 行：`finishVoteLocked` 后调 `EmitVoteTallyForBots` |
| `ServerGo/game/werewolf/room_agent.go` | +30 行：`buildAgentContextLocked` 填充 + `startDay` 复制 |
| `ServerGo/agent/wwplayer/prompt.go` | +20 行：`BuildSystemPrompt` 末尾条件注入段 |

**总改动**：~135 行。**零前端改动**。

### 2.4 测试用例

`ServerGo/game/werewolf/vote_broadcast_test.go`：
1. 13 人全投票 → 1 条 `EmitVoteTallyForBots` 事件 + GameContext.LastRoundVoteMap 含 13 条
2. 弃权票处理：弃权者不进入 Map
3. 平票：仍然聚合但不影响内容
4. bot 端到端：`buildAgentContextLocked` 后 `gc.LastRoundVoteMap` 正确填充
5. 回归：`finishVoteLocked` 之前的所有 `EmitVoteCast` 仍走 `silentForBots=true`（人类聊天流不受影响）

### 2.5 风险评估

- **§92a 锁内变体**：`finishVoteLocked` 已在持锁态；新增 `EmitVoteTallyForBots` 调用**直接在锁内**，符合既有模式 ✅
- **§119 协议层隔离**：票型是公开信息（人类玩家已能看到），不存在隔离问题 ✅
- **§135 身份公开**：票型不含身份信息（仅座位号），合规 ✅
- **§197 流式续命**：不涉及 LLM 调用路径变更 ✅
- **上下文膨胀**：1 条聚合消息 vs 13 条单独消息，**降低**而非增加队列压力 ✅
- **§130 接线验证**：写入点（finishVoteLocked）+ 读取点（buildAgentContextLocked）各 1 处，grep 即可验证 ✅

## U3. 人类身份猜测准确率（Personal Identity Guess Accuracy）

### 3.1 现状与痛点

**现状**：
- `useIdentityGuess.ts` 让人类给每个座位打身份标签，**纯 localStorage，从不上行**（`ClientWeb/src/hooks/useIdentityGuess.ts:1-16` 的注释明确写「不入服务端状态」）
- `grep guess ServerGo/` 零命中（除无关注释）

**痛点**：玩家认真做的推理标注，**终局后没有任何反馈**——猜对了不知道，猜错了也不知道。这是「唯一能让人类玩家直接、量化地与 LLM 比推理」的功能，且**完全不侵入对局**。

### 3.2 设计（纯前端）

#### 数据来源

- `useIdentityGuess.ts` 已经在 localStorage 存了每局人类对每个座位的身份猜测（`village/werewolf/seer/witch/hunter/idiot/guard/knight`）
- `localStorage` key 形如 `werewolf:guess:{roomId}:{userId}`
- 终局时 `SettlementModal` 已经渲染了全部死者身份（`view.go` 已下发 `RolePubliclyRevealed` 白名单 §135）

#### 实现步骤

1. **结算页打开时**：从 localStorage 读取本局猜测 + 从 `game.state` 读取 `players[].role`（仅 `!Alive` 或终局时可见，符合 §135）
2. **比对**：逐座位对比猜测 vs 真实身份（按角色类别归一化：villager/werewolf/god 三大类）
3. **渲染**：`SettlementModal` 金币数字下方新增一段「� 你的推理准确率」：
   - 大数字：X/12 准确率
   - 进度条：绿/红分色
   - 折叠列表：每座位对错（✓/✗ + 猜测角色 → 真实角色）

#### 新组件

interface GuessAccuracyCardProps {

export function GuessAccuracyCard({ roomId, userId, actualRoles }: GuessAccuracyCardProps) {

三语种补 2 个键：
- `werewolf.settlement.guessAccuracy.title`：「你的推理准确率」
