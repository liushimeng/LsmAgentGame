## 1. 概述与定位

### 1.1 产品定位

德州扑克是 LsmWebGame 平台**第一款真人筹码经济模型**游戏（区别于棋类与斗地主的纯休闲模式）。其定位是：

- **封闭资金池**：所有金币由系统发放（注册/登录/胜场/任务/邀请），**无充值、无提现**。
- **真实消耗 × 真实收益**：参加"带注房间"消耗金币，赢得对手的金币进入自己钱包。
- **纯内部休闲**：与真实货币无锚定关系，规避合规风险。

### 1.2 德州扑克特殊性与决策影响

相比已上线的 4 款游戏（xiangqi / chess / junqi / doudizhu），德州扑克有本质差异：

| 维度 | 棋类/斗地主 | 德州扑克 |
|------|------------|---------|
| 玩家数 | 2 或 3 | **2-6**（不对称对抗） |
| 平均对局时长 | 2-10 分钟 | **10-30 分钟** |
| 随机性 | 低（完全信息/有限隐藏） | **高**（5 张公共牌 + 2 张底牌） |
| 波动（variance） | 可控 | **高**（单局输赢可达数倍盲注） |
| 筹码流动 | 单局定胜负 | **多手牌连续流转** |
| 段位分层必要性 | 低 | **高**（必须用盲注级别分流玩家） |

**设计结论**：

1. 底注（blind level）范围需要**更宽**（50 / 200 / 1000 / 5000），覆盖休闲到高波动。
2. 单手上限更要**收紧**，避免单局破产。
3. 胜场奖励需要**按底池比例**发放（底池越大奖励绝对值越大），而非固定值。
4. 必须引入**买入（buy-in）机制**：用户的钱包金 ≠ 桌内筹码，入座时在两个池子间按规则划转。
5. 需要**段位分层**保护新人（WSOP 盲注级别思路）。

## 2. 金币获取途径

### 2.1 注册奖励

- **金额**：1000 金币（统一值，与总纲一致）。
- **时机**：`Register()` 成功即发放，写入 `t_lsm_game_wallet` + `t_lsm_game_transaction`。
- **备注字段**：`"register_bonus"`。
- **设计意图**：覆盖最低买入房间（见 §4.3 BUY_IN_MIN=500）× 2 倍安全垫。

### 2.2 每日登录奖励

- **金额**：2000 金币/天（与总纲一致）。
- **规则**：
  - UTC+8 自然日，**不补领**。
  - 唯一键 `(user_id, reward_date)` 防重复。
  - 落表 `t_lsm_game_daily_reward(user_id, reward_date, amount, created_at)`。
  - 同一用户一天内多次登录不重复发放；第一次登录时发放。
- **备注字段**：`"daily_login_yyyyMMdd"`。
- **设计意图**：单用户每天最高领取 2000，刚好够一次中等房间（blinds=200）的完整 rebuild（20000 重建）周期的一部分，**不足以长期覆盖中等房损耗** — 胜场奖励才是主要来源。

### 2.3 胜场奖励（核心循环）

**牌局结束（一手结算 ≠ 房间结束）时发放**，按赢得底池的一定比例计提：

```
win_reward = floor(win_pot × WIN_RATE)
WIN_RATE   = 10%
```

示例：某玩家一手赢得 5000 底池 → 获得 500 金币胜利奖励（**外加赢得的本金**，本金从输家桌内筹码直接划拨，见 §5.3）。

**特殊情况**：

- 输家 / 弃牌者：**不发放**胜场奖励，但**参与奖励**每人每手 50 金币（防挂机刷分）。
- 房间解散时未完成的最后一手：不发放胜场奖励（避免刷分手）。
- 每日上限：单人每天最多获得 20,000 胜场奖励（超出的胜场仍结算底池，但奖励上限 20,000）。

### 2.4 连胜奖励 (Streak Bonus)

在一房间内**连续获胜 N 手牌**时触发：

| 连胜数 | 额外奖励 | 触发时机 |
|--------|---------|---------|
| 2 连胜 | +200 金币 | 第二手结算时 |
| 3 连胜 | +500 金币 | 第三手结算时 |
| 5 连胜 | +1500 金币 | 第五手结算时 |
| 10 连胜 | +5000 金币 + "连胜徽章"（商城解锁） | 第十手结算时 |

- **断连胜条件**：输掉任意一手 → 连胜计数归零；弃牌但底池仍归你 → **不算连胜**（要求你真正 Showdown 获胜）。
- 同房间内延续；离房重进重新计数。

### 2.5 邀请好友奖励（复用现有 referral 系统）

利用 `t_lsm_game_referral_log` + `t_lsm_game_user.referral_count`：

| 事件 | 奖励 | 备注 |
|------|------|------|
| 被邀请人完成注册 | +300 金币（一次性） | 邀请人称"推荐奖" |
| 被邀请人首次参与带注房间 | +200 金币（一次性） | 防脚本注册作弊 |
| 被邀请人累计赢得 10,000 底池 | +500 金币（一次性） | 持续活跃度绑定 |

- 单人累计邀请奖励上限：10,000 金币（超限后仍记录 quantity，不再发放）。
- 触发点：被邀请人完成对应事件后写入 `t_lsm_game_transaction`，备注 `"referral_event"`+"stage"。

### 2.6 其他获取（任务/成就/活动）

按任务系统统一规划，以下为德州扑克特化示例：

| 任务 ID | 描述 | 奖励 | 周期 |
|---------|------|------|------|
| `texas_play_5_hands` | 玩满 5 手牌（无论输赢） | +300 | 每日 |
| `texas_win_1_hand` | 赢 1 手牌 | +200 | 每日 |
| `texas_reach_showdown_3` | 摊牌 3 次 | +500 | 每周 |
| `texas_play_50_hands` | 生涯玩满 50 手 | +5000 | 一次性 |
| `texas_win_pot_10k` | 单手底池 ≥ 10000 | +2000 | 一次性 |

> 任务系统由专项策划统一调度，本节仅定义德州扑克相关的任务钩子点，具体数值由任务策划调整。

## 3. 金币消耗途径

### 3.1 创建带注房间的底注（ante）

房间创建时由发起人指定一个"盲注级别"参数（见 §4.1），**创建者不预缴**，系统仅校验"所有入座玩家买入后桌内筹码 ≥ 买入下限"。

> 与斗地主不同：**德州扑克带注房间的"创建成本"=0**；消耗发生在对局内的真实押注；用户的金币在结算时从赢家流向输家（见 §5.3）。

### 3.2 买入 (Buy-in)

用户在入座（入座动作 `game.join`）时**从钱包扣款**注入桌内筹码（见 §4.3）。这是德州扑克**主要的、也是唯一强制的金币消耗**。

### 3.3 商城（简要提及，不展开）

商城入口预留，不进入 MVP。后续可上架：

- 头像框（100-5000 金币，永久解锁）
- 卡牌背面（500-2000 金币，永久解锁）
- 牌桌背景/桌布（1000-10000 金币，永久解锁）
- 特殊筹码外观（500-3000 金币，永久解锁）

**设计原则**：纯外观道具，**绝不售卖任何金币加成**。

## 4. 房间带注规则

### 4.1 创建房间的盲注级别

房间创建参数新增 `blinds_level`（int 枚举），前端提供下拉选择：

| 级别 | 显示名 | 小盲 (SB) | 大盲 (BB) | Ante | 目标用户 |
|------|--------|----------|----------|------|---------|
| 1 | 新手 | 5 | 10 | 5 | 新人熟悉 |
| 2 | 休闲 | 25 | 50 | 25 | 休闲玩家 |
| 3 | 业余 | 100 | 200 | 100 | 普通活跃 |
| 4 | 高手 | 500 | 1000 | 500 | 资深玩家 |
| 5 | 精英 | 2500 | 5000 | 2500 | 高波动 |

**数据落库**：`t_lsm_game_room` 新增三列 `sb_amount INT` / `bb_amount INT` / `ante_amount INT`。

### 4.2 设计与原引擎盲注的关系

引擎 `TexasHoldemRoom.BigBlind` 由后端 `room_service.go` 读取房间配置后设置：

```
engineRoom.BigBlind = room.BB
engineRoom.SmallBlind = room.SB
engineRoom.Ante = room.Ante
```

引擎侧**完全不动**，仅配置来源从硬编码（当前 `view.go` 里写死 `BigBlind: 200`）改为读取 Room 配置：需要 `backend-dev` 在处理 `game.join` 时把 BB/SB/Ante 注入引擎。

### 4.3 买入 (Buy-in) 范围

每个盲注级别固定 min/max 买入（**相对 BB 的倍数**）：

```
BUY_IN_MIN = BB × 20   (例：休闲房 BB=50 → min=1000)
BUY_IN_MAX = BB × 100  (例：休闲房 BB=50 → max=5000)
BUY_IN_DEFAULT = BB × 50
```

**玩家入座时指定买入金额**（默认取 BUY_IN_DEFAULT），范围校验：

```
BUY_IN_MIN ≤ request_amount ≤ min(BUY_IN_MAX, wallet_balance)
```

- 若钱包不足 BUY_IN_MIN → 拒绝入座，返回错误码 `ERR_INSUFFICIENT_FUNDS` + 金额建议（进入无注房间 / 领取每日奖励）。
- 若钱包超过 BUY_IN_MAX → 仅扣 BUY_IN_MAX，剩余留在钱包。

**钱包扣款时机**：

1. 前端发起 `game.join` 时带 `buy_in: number`（可选，默认 BUY_IN_DEFAULT）。
2. 后端在扣款前开启 DB 事务，校验钱包 ≥ buy_in → 写入 `transaction(type=BUY_IN_DEBIT)` → 扣减 wallet.balance → 注入引擎 `Player.Stack = buy_in` → 提交。
3. 任一环节失败 → 事务回滚，返回错误。

### 4.4 边池 (Side Pot) 处理

引擎已有正确实现（`engine.go` 的 `EndHand` 按筹码量拆分主池和边池）。**金币结算与引擎筹码结算规则一致**：

- 主池由所有投入玩家按牌型竞争。
- 每个边池仅由该边池的 eligible_seats 竞争。
- 赢家分别赢得对应池，输家的投入不再回收。

**一致性保证**：结算时服务端按引擎产出（`winners[].winnings`）为单位**原子写入流水**，赢家入金币 = winnings（见 §5.3）。

### 4.5 全押 (All-in) 保护

- 引擎已据此拆分边池（见 §4.4），无需额外处理。
- 但当玩家桌内筹码为 0 时，该玩家被标记"淘汰"，淘汰后：
  - 允许玩家**补充买入 (re-buy)**：再缴纳 BUY_IN_MIN 即可重新激活座位（仅淘汰后 30 秒内允许，超时座位清空）。
  - 若 30 秒内未补充买入 → 座位清空，后续玩家可入座。

### 4.6 破产保护（余额 < 最低买入时的兜底机制）

当用户钱包余额 < BUY_IN_MIN（任意带注房）时：

1. **拒绝入座**所有带注房间。
2. **大厅展示橙色提示条**："您的金币不足，请通过以下方式获取：每日登录（+2000）/ 完成任务 / 参加免费房间"。
3. 提供"练习模式"入口（无注房间，筹码仅作 UI 显示，不与钱包挂钩），玩家可继续熟悉规则。

## 5. 引擎筹码与用户钱包的解耦模型

### 5.1 为什么要解耦

德州扑克的 `Player.Stack`（引擎内筹码）与用户钱包是**两个独立账户**：

- **桌内筹码**：对局引擎的内部状态，表示该玩家当前座位上可用的博弈资源。
- **用户钱包**：`t_lsm_game_wallet.balance`，是全平台通用的跨游戏账户。

两者不可直接合并，原因：

1. **多手牌**（multiple hands）在一个房间生命周期内进行，中途不入不出金币（仅清算加注/赢池），仅在**入座时购入**、**离座时售出**时才与钱包交互。
2. **并发安全**：房间结算（一手）时钱包扣款/入账必须原语化。
3. **审计需要**：桌内筹码变动（每一步 action 对应的押注）在引擎内部记录；钱包变动在 `t_lsm_game_transaction` 分开记录。

### 5.2 两层筹码的关系图

```
  ┌──────────────────────────────┐
  │  User Wallet (DB: t_wallet)  │
  │  balance: 10,000             │◄── 注册/每日/任务/奖励发放来源
  └───────────┬──────────────────┘
              │ buy-in (transaction: BUY_IN_DEBIT)
              │ sell   (transaction: SELL_CREDIT)
              ▼
  ┌──────────────────────────────┐
  │  Room Seat Stack (in-memory)│
  │  seat[my].stack  = 5,000    │◄── 桌内筹码，引擎内部流转
  └───────────┬──────────────────┘
              │ 一手结算时，赢家按 winnings 入金币
              ▼
  ┌──────────────────────────────┐
  │  User Wallet                 │
  │  balance: 12,000 (+2,000)   │◄── 输家: -buy_in; 赢家: +winnings
  └──────────────────────────────┘
```

### 5.3 一手结算的原子操作

每手结束（`engine.EndHand` 产出 `winners[]`）时，后端在**一个 DB 事务**内：

```
BEGIN;
  FOR each winner:
    UPDATE wallet SET balance = balance + winnings WHERE user_id = w.seat_uid;
    INSERT INTO transaction(type='WIN_CREDIT', amount=winnings, ref_hand=hand_id);
  FOR each loser:
    -- 输家已在对局中把 stack 交给赢家，无需扣钱包（筹码已在 buy-in 时扣过）
    -- 输家仅剩的"零"体现在于其钱包未入账
    INSERT INTO transaction(type='LOSS', amount=0 /*象征性记录*/, ref_hand=hand_id);
  -- 胜场奖励 (§2.3)
  FOR each winner WHERE floor(winnings × 0.1) > 0:
    IF daily_win_reward_total < 20000:
      UPDATE wallet SET balance = balance + floor(winnings × 0.1);
      INSERT INTO transaction(type='WIN_REWARD', amount=floor(winnings × 0.1));
  COMMIT;
```

> 注意：**输家不额外扣金币**（金币在 buy-in 时已扣）；赢家赢得的本金 = 各输家的桌内筹码合计。

### 5.4 离座/退出时的"售出"结算

玩家主动 `game.leave` 或断线超时时：

- **进行中一手未结束**：该玩家按弃牌处理，桌内筹码继续留在池中参与后续结算。等到一手结束时：
  - 若赢得奖金 → 按 §5.3 入账。
  - 未赢得 → 桌内筹码归剩余赢家分配。
- **一手已结束，玩家仍有桌内 stack**：
  - 立即触发 `SELL_CREDIT` 事务：`balance += stack`。
  - 写入 `transaction(type='SELL_CREDIT', amount=stack, reason='leave_room')`。

### 5.5 chips_committed 与钱包的关系

引擎 `Player.ChipsCommitted` 字段（见 `view.go`）表示**该玩家当前这一手累计投入的筹码**，用于：

- 后端押注轮的状态机校验（"还能不能加注"）。
- 边池计算。

该字段**永远只在引擎内部**，不参与钱包流水。仅在"一手结算完成"且"玩家需要重新入座/补充买入"时，引擎才会将其重置为 0。

## 6. 风控与防作弊

### 6.1 刷分检测

| 场景 | 检测方式 | 阈值 | 动作 |
|------|---------|------|------|
| 同 IP 多账号 | 记录 `t_lsm_game_login_log(ip, user_id)` | 同 IP > 3 账号 | 限制 IP 每日注册 ≤ 3；"高胜率+"额外审查 |
| 同设备多账号 | 前端上报 `device_fingerprint`（hash of UA+canvas） | 同 FP > 2 账号 | 同 IP 规则 + 强制 KYC 前置（暂不实现，仅审查） |
| 机器人定时操作 | WS 押注时间间隔分布检测 | 方差 < 100ms 即疑似 | 告警 + 降级匹配 |

### 6.2 异常胜率监控

| 指标 | 窗口 | 阈值 | 动作 |
|------|------|------|------|
| 胜率（hands） | 1000 手滑动 | > 70% | 告警 + 抽样审批 |
| 入池率（ voluntarilly put money in pot） | 1000 手 | > 80% | 疑似 ultra-tight 或软件辅助 |
| Showdown 率 | 1000 手 | > 40% 且胜率 > 60% | 疑似 collusion |

### 6.3 德州特殊风险：玩家串通 (Collusion)

| 类型 | 说明 | 监控手段 |
|------|------|---------|
| Soft-playing | 老玩家不打新人（避免抽水） | 两位玩家在同一桌的加注频率显著低于其他桌 |
| Check-raising 串通 | A 总是让 B 加后拿下 | AB 在同一桌的 check-raise 比例异常高 |
| Collusion 送筹码 | 一玩家故意在两人全押时弃牌让另一人赢 | 观察"2 人全押但一方弃牌"事件；>= 3 次/天触发审查 |
| Multi-account 同一人 | 同 IP/设备 2 账号入对局 | 同 §6.1 + 强制限制同 IP 房间（MVP 阶段：**禁止同 IP 玩家入同一房间**） |

### 6.4 流水审计要求

- 所有金币变动必须落 `t_lsm_game_transaction`，字段至少：
  `id / user_id / amount / balance_after / type / ref_table / ref_id / created_at / request_id`
- 关键类型枚举：`REGISTER_BONUS / DAILY_LOGIN / WIN_CREDIT / WIN_REWARD / LOSS / BUY_IN_DEBIT / SELL_CREDIT / REFERRAL / TASK / ACHIEVEMENT`
- 流水支持按 `ref_id` 回溯源（房间+手+赢家/输家）。

### 6.5 提现 / 资金外流的额外防护

- **禁止转账给用户**：transaction 表不记录 user-to-user 转移。
- **商城购买记录**：商城订单流水单独落表，不进入 transaction 统一视图。
- **金币账户冻结**：风控触发时 `wallet.frozen = true`，frozen 期间仅可领任务/奖励，不可入座带注房间。

## 7. 数值平衡建议

### 7.1 金币通胀 / 通缩控制

| 调控参数 | 当前值 | 用途 |
|---------|------|------|
| 每日登录发放 | 2000/用户/天 | 基础通胀 |
| 注册奖励 | 1000/用户（一次性） | 新用户引导通胀 |
| 胜场奖励率 | 10% of 底池 | 与胜场强相关，玩家越强越富（马太效应） |
| 连胜奖励 | 最高 +5,000 | 活跃老玩家激励 |
| 商城消耗 | 持续 | 金币回收 |
| 任务/活动消耗 | 持续 | 金币回收 |

**设计目标**：

- **新用户**：通过 1000 + 2000(N 天登录) ≈ 在 M=7 天内积攒 ≥ 15,000，可尝试中等房。
- **活跃玩家**：每日收益 ≈ 70% 来自胜场，30% 来自任务/登录，**不鼓励挂机**。
- **高波动玩家**：注意"单手上限"控制（§7.3），避免一天输掉全部存款。

### 7.2 段位分层（WSOP 风格盲注级别表）

面向休闲到硬核玩家的分层；未来可扩展为"段位制"（根据胜场数解锁高_blind_房间）：

| 级别 | 显示名 | BB 范围 | 典型玩家资产（金币） | 解锁条件 |
|------|--------|--------|------------------|---------|
| 1 | 新手 | 10 | < 2,000 | 默认解锁 |
| 2 | 休闲 | 50 | ≥ 2,000 | 默认解锁 |
| 3 | 业余 | 200 | ≥ 10,000 | 累计胜 ≥ 5 手 |
| 4 | 高手 | 1,000 | ≥ 50,000 | 累计胜 ≥ 30 手 |
| 5 | 精英 | 5,000 | ≥ 200,000 | 累计胜 ≥ 100 手 |

> MVP 阶段所有房间**不强制段位**，但前端用上述表显示"推荐资产"标签引导新人选择适合的 blind。

### 7.3 单手上限（防破产）

- **单手赢家赢得上限=玩家入座时 buy_in 的 6 倍**（可通过房间配置调整）。
- 超过上限的奖金仍分配给赢家，但"胜场奖励"不计入上限。
- 目的：限制新人被鲨鱼玩家一次清退出游戏。

### 7.4 钱包持有上限（防通胀堆积）

- **单用户钱包硬上限 = 1,000,000 金币**。
- 超额奖励入"冻结收益"，需在商城消费后才能解冻；超出部分返给系统（焚币机制）。

## 9. 与其他游戏的差异化

| 维度 | 象棋/军棋/斗地主 | 德州扑克 |
|------|----------------|---------|
| 玩家数 | 2 或 3 | 2-6 |
| 平均对局长度 | 2-10 分钟 | 10-30 分钟 |
| 单局输赢上限 | 低（固定底注） | **高（全押一次倾家荡产）** |
| 底注范围 | 100-1000（斗地主典型） | 5-5000（德州十级） |
| 消费模型 | 一局定胜负清零 | **连续多手**、中途不入不出 |
| 同 IP 玩家 | 可同桌 | **必须禁止同桌** (§6.3) |
| 段位/分层 | 不需要 | 必须做 (§7.2) |
| 单手上限 | 不需要 | 必须做 (§7.3) |
| 重购机制 | 不需要 | 必须支持 (§4.5) |
| 破产保护 | 不需要 | 必须做 (§4.6) |

**核心差异点**：德州扑克的**金币流动性**、**波动性与安全性**同时高，是世界上第一款真实反映"资金池博弈"的游戏，策划必须做到"新人输得起、资深玩家赢得爽、欺诈分子无空钻"。

## 10. 多玩家房间 (2-6 人) 输赢分配

### 10.1 玩家 2-6 人时金币流转规则

- **所有玩家**：入座时 buy-in 扣除。
- **每手结算**：引擎产出 `winners[]`（主池 + 各边池赢家）→ 每个赢家获得 `winnings`。
- **赢家入账**：`wallet.balance += winnings`。
- **输家不额外扣**：金币已在 buy-in 扣过，输的是桌内筹码（已转为赢家的奖金）。

### 10.2 场景示例

场景：6 人房间，BB=100，5 号位倒下

1. 6 人各 buy-in = 5,000 → 系统共接收 30,000（全入桌内）。
2. 经过多路加注与 all-in，主池 12,000 + 边池 6,000 + 边池 4,000。
3. 主池赢家: seat_1 (+12,000)；边池1 赢家: seat_3 (+6,000)；边池2 赢家: seat_5 (+4,000)。
4. 各赢家钱包 `+ winnings`。
5. 输家 seat_2/4/6/8 在 buy-in 已扣，不再额外扣。
6. 若 seat_5 仍存活但其 stack 已归零 → 触发淘汰提示（§4.5 re-buy）。

### 10.3 所有玩家同时离座 / 房间解散

- 中断的最后一手按弃牌处理，未完成的底池按比例退还各玩家（按投入比例）。
- 退还金额立即写 `transaction(type='REFUND', reason='room_dissolve')`。

### 10.4 流局（一手无法正常结束：仅 1 人未弃牌且其赢了）

仅剩 1 人时，该玩家自动赢得全部底池（showdown 直接跳过）。仍按 §5.3 结算。

## 附录 B：测试用例钩子（给 integration-tester 参考）

1. **新用户**：注册 → 钱包余额 1000 → 能入座新手房（BUY_IN_MIN=200）。
2. **入座拒绝**：钱包 100，请求入座 BUY_IN_MIN=200 房 → 返回 `ERR_INSUFFICIENT_FUNDS`。
3. **买扣入座**：钱包 5000，buy-in 2000 → 钱包剩 3000，桌内 stack=2000。
4. **赢家入账**：seat_1 buy-in=2000，赢得底池 5000 → 钱包 +5000（本金）+ 500（奖励）= +5,500。
5. **输家不二次扣**：seat_2 输掉一手，wallet 保持 buy-in 后余额。
6. **all-in + side pot**：验证多赢家按边池分配。
7. **退出座位结算**：桌内 2000 未参与下一手 → 钱包 +2000。
8. **同 IP 拒绝**：IP 已被 A 使用，B 试图入同房 → 拒绝。
9. **段位解锁**：胜场达 5 次后解锁 amateur 房。
10. **钱包达上限**：商城消费后才能解冻超额奖励。
