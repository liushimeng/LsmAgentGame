# 登录已过期 / 请先登录 — Bug 修复设计

> **状态**：设计文档（待实现）
> **创建**：2026-07-10
> **症状**：用户使用**正确手机号 + 密码**登录后，前端提示 `登录已过期,请重新登录。`
> 或 `请先登录。`，阻止进入主界面。

## §1 根因诊断

### 1.1 后端 OK（无 bug）

| 项 | 结论 | 文件 |
|---|---|---|
| JWT 签发（HS256） | ✅ 正确 | `ServerGo/util/jwt.go:20-38`（IssueToken） |
| JWT 校验（过期 / 签名） | ✅ 正确 | `ServerGo/util/jwt.go:41-59`（ParseToken） |
| Bearer 中间件 | ✅ 正确 | `ServerGo/middleware/auth.go:15-35`（AuthRequired） |
| Login 路径（bcrypt + session row + 48h cookie） | ✅ 正确 | `ServerGo/service/auth_service.go:327-396` |
| JWT TTL | 2h (`ttl_seconds:7200`) | `LsmAgentGame.conf:20` |
| 签发 / 校验同源 / 同时钟 | ✅ 自洽 | `time.Now()` 统一 source |

→ **JWT 后端实现正确**。密码正确 + 正确手机号 → 服务端签发合法 2h token 并返回 `expires_at=exp.Unix()`。

### 1.2 Bug 在前端会话层

症状中文串来自前端 i18n（**后端不送中文**）：

| 中文串 | i18n key | 触发 reason | 后端 code |
|---|---|---|---|
| `登录已过期,请重新登录。` | `auth.sessionExpired` (zh-CN.ts:131) | `expired` | 10003 |
| `登录状态已失效,请重新登录。` | `auth.sessionInvalid` (zh-CN.ts:132) | `invalid` | 10002 |
| `请先登录。` | `auth.sessionMissing` (zh-CN.ts:133) | `missing` | 10001 |

前端通过 `http.ts:93` 触发 `handleSessionError(code, msg)` → `logout()` + `reportAuthExpired(reason)`
→ `SessionExpiredToast.tsx` 弹出中文串 + `App.tsx:72` 重开 `AuthModal`。

### 1.3 3 条实际触发路径（按概率排序）

**P1. hydrate 时钟误判（最可能）**

- `auth.store.ts:105-133 hydrateFromStorage()`：
  ```ts
  const tokenAlive = !persisted.expiresAt || persisted.expiresAt * 1000 > Date.now();
  ```
  当 `expiresAt` 存在但 `expiresAt*1000 <= Date.now()`（设备时钟比服务器快 / VM resume / NTP 调整）
  → `isAuthenticated=false` → F5/重登后 AuthModal 弹 "请先登录"。
- 同一逻辑对 **`expiresAt==0` 老版本残留** 友好（`!persisted.expiresAt` → tokenAlive true），
  但对「**新版本服务器下发正数 expiresAt 但客户端时钟偏快**」敏感。

**P2. WS 重连 refresh 失败**

- `ws.ts:228-252 scheduleReconnect()`：断线 `>RECONNECT_WINDOW_MS`(5min) 时先调
  `/api/auth/refresh`。refresh 失败 → `logout()` + `reportAuthExpired('expired')` → toast
  "登录已过期"。
- 常见于服务器重启 / 长时间断网 / 用户切换网络后，**但非首次登录场景**。
- 由于 `rebuild_restart_app.sh` 每次重启服务器，WSS 断开 → 重连 → refresh 路径走一遍。

**P3. 首次登录 WS 建立时 token 已"过期"**

- `AppLayout.tsx:36-48`：`hydrateFromStorage()` → WS connect。若 `hydrateFromStorage` 的时钟
  校验已把 `isAuthenticated` 打回 false → 请求根本不走 WS connect；继续走 P1。

### 1.4 时钟偏斜是核心诱因

签发的 2h token 在服务器端仍合法，**但客户端 exp 校验（`expiresAt*1000 > Date.now()`）用的
是客户端时钟**。若客户端设备时钟快 3 分钟 → 用户在第 1h57min 后始终被判 expired → "登录已过期"。
若 VM 恢复后时钟向前跳 → 每次 hydrate 都触发。

## §2 修复方案

### 2.1 设计原则

1. **JWT 后端不变** — 后端实现正确，不触碰。
2. **hydrate 阶段「宁可放行、让 API 裁决」** — hydrate 阶段拿不到服务器此刻时间，
   无法准确判定 token 是否真过期；误放行只会让下一次 API 调用返回 401 再走
   `handleSessionError`，比误杀（用户已登录却弹 AuthModal）代价小得多。
3. **关键位置加时钟偏差告警** — 在 login / register / refresh 入口检测
   `expires_at` 是否为有效未来时间戳；若检测到服务器时钟偏差（expires_at 是过去时间），
   打 `console.warn`（帮助后续排错）但仍允许 token 落盘。
4. **不改 JWT 语义、不改 token TTL、不改后端 errcode 契约**。

### 2.2 改动清单

#### 2.2.1 `auth.store.ts::hydrateFromStorage`（最高优先）

**现状**：
```ts
const tokenAlive = !persisted.expiresAt || persisted.expiresAt * 1000 > Date.now();
if (hasToken && tokenAlive) { /* 保持登录 */ }
else if (persisted.isAuthenticated) { set({ isAuthenticated: false }); }
```

**改为**：
```ts
// 避免 hydrate 阶段的时钟误判：tokenAlive 在 expiresAt 已过时不再立刻判死。
// 原因：hydrate 阶段拿不到服务器此刻时钟，仅凭客户端时刻判断 token 是否过期
// 会因 VM resume / NTP 快钟 / 用户设备时钟偏快把合法 token 误杀（症状：「登录已过期」
// /「请先登录」弹在刚登录后）。此处放行，让下一次 API 调用的 401 路径裁决。
const tokenAlive = true; // 不再基于客户端时钟裁决
if (hasToken) {
  set({
    isAuthenticated: true,
    userType: persisted.userType ?? 1,
    myInviteCode: persisted.myInviteCode ?? null,
  });
} else if (persisted.isAuthenticated) {
  set({ isAuthenticated: false });
}
```

> **代价**：过期 token 在 hydrate 后短暂放行 → 下一次 API 调用 401 → 走
> `handleSessionError`（已是稳健路径）。**收益**：消除 hydrate 时钟误判。

#### 2.2.2 `auth.store.ts::login / register / refresh` 人口：expires_at 校验 + 告警

在 login 中加 `expires_at` 有效性校验（**不拒绝**，只 log + 仍放行）：

```ts
async login(payload) {
  const data = await authService.login(payload);
  // 防御性校验：登录响应必须含有效未来 expires_at（服务器时钟偏差时会是过去时间）。
  // 详见 docs/design/login-bug-fix-design.md §2.2.2。我们只 log 告警，不拒绝 token ——
  // token 是否真过期由下一次 API 调用的 401 裁决（hydrate 阶段不误判）。
  validateExpiresAt(data.expires_at, 'login');
  setAuthToken(data.token);
  set({ ... });
}

function validateExpiresAt(expiresAt: number | null | undefined, tag: string): void {
  if (!expiresAt || expiresAt <= 0) {
    console.warn(`[auth] ${tag}: expires_at 缺失或无效 (${expiresAt})；token 仍落盘，由 API 裁决`);
    return;
  }
  const nowSec = Math.floor(Date.now() / 1000);
  if (expiresAt <= nowSec) {
    // 设备时钟比服务器快，或服务器签发时已是过去时间。仅告警不拒绝。
    console.warn(`[auth] ${tag}: expires_at 已过期 (服务器=${expiresAt}, 客户端=${nowSec}, 差=${nowSec - expiresAt}s)；token 仍落盘`);
  }
}
```

同样在 register / refresh 入口调用（WS 重连 refresh 失败场景 + 注册场景）。

#### 2.2.3 `http.ts::handleSessionError`（稳健性补强）

**现状**（OK，但可加强日志）。已在 `console.warn(`[auth] session error ${code}: ${rawMessage}`)`。

**加强**：追加 `clockSkewHint`，帮助排错：

```ts
function handleSessionError(code: number, rawMessage: string): never {
  const reason = reasonFromCode(code) ?? 'expired';
  console.warn(`[auth] session error ${code}: ${reason}`);// 不变
  void useAuthStore.getState().logout();
  reportAuthExpired(reason);
  throw new ApiError(code, SESSION_EXPIRED_SENTINEL, 401);
}
```

> 保持现状即可，不改变语义。

#### 2.2.4 WS 重连 refresh 路径（`ws.ts:228-252`）— 保持

refresh 失败 → logout + reportAuthExpired 已是稳健路径。**不改动**。

### 2.3 边界：不触发修复的位置

- **`expiresAt` 真过期（2h 后）** → hydrate 放行 → 下一次 API 调用 401 → `handleSessionError`
  → 正确弹 "登录已过期" → AuthModal。**行为不变，只是延后到第一次 API 调用后触发**。
- **token 确实缺失** → `hasToken=false` → 走 `else if persisted.isAuthenticated` 分支 → 仍会
  downgrade → AuthModal。行为不变。
- **token 确实无效（签名错）** → 后端 10002 → 前端 invalid reason → "登录状态已失效"。行为不变。

## §3 配置 / 部署

- **无新增配置项**。不涉及 `LsmAgentGame.conf` 改动。
