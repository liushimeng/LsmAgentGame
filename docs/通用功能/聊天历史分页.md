# Chat History Pagination + Cleanup

This document describes the history API protocol, the index design, the
future sharding story, and the janitor cleanup hooks.

## 1. Protocol — `chat.history`

### Request

| field | type | required | description |
|-------|------|----------|-------------|
| `scope` | `"lobby"` \| `"room"` | ✓ | Scope targeted. `room` requires `room_id`. |
| `room_id` | string | (room scope only) | The room whose history we want. |
| `limit` | number | — | Clamped to `[1, 200]`. Defaults to 50. |
| `before_id` | number | — | Keyset cursor. Return rows with `id < before_id`. Omit to read the most recent page. |

### Response

| field | type | description |
|-------|------|-------------|
| `scope` | string | Echoed back. |
| `room_id` | string? | Echoed back (room scope only). |
| `messages` | array | Messages in **oldest-first** order. |
| `has_more` | boolean | `true` when this page returned exactly `limit` rows (older messages likely exist). |
| `next_cursor` | number \| null | The `id` of the last (oldest) message in the page. The client passes this back as `before_id` to fetch the previous page. `null` when the page is empty. |

### Backwards compatibility

A client that omits `before_id` gets the original "latest N messages" behaviour;
the new `has_more` and `next_cursor` fields are additive and safe to ignore.

### Example — walking back through history

```text
# Initial load — latest 50 messages
c2s: chat.history { scope: "room", room_id: "r", limit: 50 }
s2c: chat.history { messages: [a_1..a_50], has_more: true, next_cursor: 12 }

# User scrolls up — fetch older page
c2s: chat.history { scope: "room", room_id: "r", limit: 50, before_id: 12 }
s2c: chat.history { messages: [a_51..a_100], has_more: false, next_cursor: 1 }
```

The server query is:

```sql
SELECT * FROM t_lsm_game_chat_message
 WHERE scope = 'room' AND room_id = ?        -- idx_scope_room_ts (first two cols)
   AND id < ?                                -- primary-key range; stable
 ORDER BY id DESC
 LIMIT 50;
```

## 2. Index design

| index | columns | use |
|-------|---------|-----|
| `PRIMARY` | `id` | Point lookups, keyset pagination, monotonic ordering. |
| `idx_scope_room_ts` | `(scope, room_id, created_at)` | History queries (scope + room filter); time-based cleanup scans; any query that scopes to a room without tracking exact ids. |
| `idx_from_user_id` | `(from_user_id)` | User-level message lookups (admin audit, user-deletion cascade). |
| `idx_to_user_id` | `(to_user_id)` | Recipient-side lookups (whisper audit). |

Every history query engages `idx_scope_room_ts` for the leading two columns and
either narrows by `id < ?` (keyset) or sorts by `id DESC`. The extra `created_at`
column in the composite index powers the trailing "time < ?" cleanup queries:
the optimizer will use the index's trailing created_at column.

## 3. Sharding strategy (future)

The table is currently a single `t_lsm_game_chat_message`. At high volume,
monthly sharding is planned:

```text
t_lsm_game_chat_message            (default / legacy)
t_lsm_game_chat_message_202607     (July 2026)
t_lsm_game_chat_message_202608     (August 2026)
...
```

Sharding rules:

* `CreatedAt` (UTC month) picks the physical table for WRITES. Every write path
  must populate `CreatedAt` BEFORE the GORM create call so the ORM can route.
* READS that span a known month scope can target one shard. Cross-month reads
  fan out to each relevant shard and merge.
* Cross-month time-range deletes iterate each active shard.

For now the code path is single-table. `ws.ChatService.DeleteMessagesBefore`
must be invoked per-shard by the caller when sharding is enabled.

## 4. Room-delete cascade

Every code path that drops a room also drops its chat messages. The cascade is
inline — the same transaction that deletes `t_lsm_game_room` does
`DELETE FROM t_lsm_game_chat_message WHERE scope='room' AND room_id = ?`.

Covered code paths in `ServerGo/service/room_service.go`:

| function | trigger |
|----------|---------|
| `LeaveRoom` | Last human leaving empties the room. |
| `DeleteRoomsByUser` | Admin deletes a user; their rooms are torn down. |
| `LeaveSpectate` | Last spectator leaving an otherwise empty room. |
| `DeleteRoomIfEmpty` | Janitor-driven auto-cleanup pass. |
| `JanitorSweepStale` | Room force-deleted after staleness cutoff. |

Covered code paths in `ServerGo/service/room_force_disband.go`:

| function | trigger |
|----------|---------|
| `ForceDisbandRoom` | Admin kill-switch. |
| `HardDeleteRoom` | Boot-cleanup companion to `ForceDisbandRoom`. |

The WebSocket layer exposes the same capability via
`(*ws.ChatService).DeleteRoomMessages(roomID)` for callers that can chat with
chat service directly; the service layer uses the inline-SQL form to keep
the transaction scope tight.

## 5. Time-based cleanup (janitor hook)

`(*ws.ChatService).DeleteMessagesBefore(t)` exposes a `DELETE ... WHERE
created_at < t` primitive that a janitor job can call at regular intervals
(e.g. "delete messages older than N months"). It's deliberately a primitive —
the janitor itself is owned by `main.go` and can be swapped out without touching
chatsvc.

The query hits `idx_scope_room_ts` on its trailing `created_at` column, so the
full-row scan is limited to the index range, not the clustered PK.
