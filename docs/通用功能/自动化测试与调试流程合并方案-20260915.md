# 自动化测试与调试流程合并方案

> **§20260915-01** —— 将独立 Debug 流程 (`AutoDebugTestReport.md`) 合并入各游戏测试提示词，
> 实现「测试 → 自动修复 → 提交推送」全流程单一 Agent 会话闭环。
> 文件命名统一为 `AutoTestAndDebug_<Game>`。

## 1. 背景与动机

### 1.1 原有架构的问题

| 问题 | 说明 |
|------|------|
| **双轨分离** | 测试(`AutoTestAndSaveReport_<Game>`)与修复(`AutoDebugTestReport.md`)是两个独立 prompt 文件、两个独立 Agent 会话，规则重复、术语不一致 |
| **接力链路脆弱** | shell 层「确定性接力」(`AutoDebugTestReport.sh`)依赖 flock + 待处理报告预检 + 二次 Agent 选择，任一环节失败就断链 |
| **命名不一致** | 测试用 `SaveReport`、修复用 `Debug`，语义混淆；合并后统一为 `TestAndDebug` |
| **规则文件守门分散** | 「禁止修改 CLAUDE.md/AGENTS.md」守门条款在 `AutoDebugTestReport.md` 中，测试提示词仅在 §9 注意事项中提及，合并后统一守门 |

### 1.2 合并目标

1. **单 prompt 全流程**：测试提示词末尾内嵌「自动修复流程」章节，Agent 测试完成后**直接**在同一会话进入修复
2. **单 shell 入口**：各游戏一个 `AutoTestAndDebug_<Game>.sh` 启动脚本，不再接力外部 debug 脚本
3. **删除冗余文件**：`AutoDebugTestReport.md` / `AutoDebugTestReport.sh` 删除
4. **统一命名**：`AutoTestAndSaveReport_<Game>` → `AutoTestAndDebug_<Game>`

## 4. 「自动修复流程」章节模板（迁入内容）

以下为各游戏提示词末尾新增的章节（以 `[GAME]` 为游戏名占位符，实际替换为「狼人杀」「德州扑克」「辩论比赛」「财商流游戏」）：

```markdown
## 自动修复流程（测试完成后执行）

> **本章节在测试报告落盘后自动执行**。Agent 测试完成并写入测试报告 + 进度文件后，**立即**进入以下修复流程，无需外部脚本接力。

### 硬约束（不可违反）

1. **绝对禁止修改 `CLAUDE.md`、`AGENTS.md` 这两个规则文件。**
   - 修复摘要 / 版本基线 / commit hash / 教训只写到旁路文档(如 `TestReport/<BugID>_validation.md` 或对应 `docs/` 归档),**绝不写入规则文件**。
2. **每一份被处理的报告文件都必须有明确归宿**:
   - **A. 有问题已修复并推送成功** → **删除**该报告文件。
   - **B. 经核查无问题** → **就地重命名**,追加 `_无问题` 后缀。
   - **C. 有问题但构建/重启/验证失败** → **保留原文件名不变**,等待人工介入。

### 报告检索

- **主工程**: 在 `TestReport/` 下按 **本游戏 glob** 检索**生成时间最早、文件名不含 `_无问题` 后缀**的报告。
  - glob 来源: `auto_run_common.sh::GAME_GLOBS`（本游戏条目）。
- **子工程**: 在 `go-web-debug-tool/UseReport/` 下检索本游戏工具报告 glob。
- 无任何待处理报告 → 静默结束修复流程。

### 缺陷分析与代码修复

- 按报告 `Bug ID` + 堆栈 + `ERROR` 日志,在对应代码库定位问题。
- **动手改代码前必须先确认缺陷当前是否仍然存在**:`git log --oneline -10 -- <file>` 看相关文件近期提交。
- **根因分析**: 从逻辑底层修复,避免仅处理表面;核心逻辑遵循 `CLAUDE.md` 架构约束(仅**读取**,绝不修改)。
- 核查后确认问题**均已不存在或非有效缺陷** → 不改任何代码,直跳「报告归档」分支 B。
- 修复后必跑 `go test ./...`(Go) / `npm run build`(前端),确保本地编译与单测通过。

### 构建重启与回归验证

- 主工程跑 `./rebuild_restart_app.sh` 重新编译 + 重启服务。
- `go-web-debug-tool` 子工程独立编译验证。
- 回归测试统一从 `test_account.json` 读账号,执行冒烟测试,核心流程无阻塞。
- **本步骤仅在「实际改了代码」时执行**;分支 B 跳过。

### 文档同步（仅旁路）

- 修复涉及架构调整 / API 变更 / 新增常量 → **只**更新业务/技术文档(`docs/*.md`)与代码内注释。
- **禁止**追加、删除、修改 `CLAUDE.md` / `AGENTS.md`。
- **本步骤仅在「实际改了代码」时执行**;分支 B 跳过。

### Git 提交推送与报告归档

按本轮实际结果,**三选一**:

**分支 A: 有问题已修复并验证通过**
- 主工程 + `go-web-debug-tool` 子工程分别 Git 提交,注释:
  `修复: [BugID] <问题简述> (关联报告: YYYYMMDD_HHMMSS)`
- 提交成功后自动 `git push` 同步远程。
- **推送完成后立即删除**已处理的对应报告文件。

**分支 B: 无问题(无需改代码、无新提交)**
- 报告文件**就地重命名**,追加 `_无问题` 后缀。
- **不删除文件、不代码提交推送**。

**分支 C: 有问题但构建/重启/验证失败**
- **保留原报告文件名不变**,不得删除、不得重命名。
- 记录错误日志,等待人工介入。

### 约束与监控

- **总时长硬上限 25 分钟**: 超时强制终止,报告保留原名。
- **子阶段时间盒**: 检索 ≤ 2 min / 修复 ≤ 12 min / 构建 ≤ 8 min / 文档 ≤ 2 min / 归档 ≤ 1 min。
- **错误处理**: 构建/重启/验证阶段失败 → 保留报告原名,等人工排查。
- **规则文件守门**: 任何「更新 `CLAUDE.md`」冲动,先停下来确认——本流程明确禁止。
```
