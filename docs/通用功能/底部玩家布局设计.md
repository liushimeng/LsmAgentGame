# "我方在底部" 布局设计规范

> 本文件是 LsmWebGame 所有多人/多人格游戏**界面布局**的唯一事实来源。
> 核心规则：**玩家（"我"）的座位 / 棋子 / 手牌永远渲染在屏幕底部**，
> 无论该玩家在游戏内的绝对坐标是什么。
>
> Agent 新增游戏、修改棋盘 / 牌桌 / 座位组件前**必须**先阅读本文件，
> 遵循对应的实现模式。

## 1. 核心原则

| # | 原则 | 描述 |
|---|------|------|
| P1 | **本地旋转 ≠ 服务端旋转** | 服务端始终按绝对坐标（红 = 0..4 / 黑 = 5..9；座位 0..N）推送 `game.state`；客户端根据本地玩家的颜色/座位做视觉旋转，让"我"始终在底 |
| P2 | **观战者见固定视角** | Spectator 收到脱敏视图（无 my_color / my_seat），前端用硬编码默认（`myColor='red'` 或 `mySeat=0`）保证所有观战者看到同一布局 |
| P3 | **服务端权威** | 玩家坐标（my_color / my_seat）由服务端在 `game.joined` 中下发；前端 store 仅在 `payload` 字段非空时更新，避免房间级广播的回声覆盖（详见 CLAUDE.md §19） |
| P4 | **视图字段脱敏** | 私有字段（my_color / my_seat / my_hand / my_hole）走 `BroadcastTo(userID, ...)` 按人推送；房间级 `BroadcastRoom` 不带这些字段 |
| P5 | **旋转只影响视觉，不影响逻辑** | 点击坐标必须通过反向 `pixelToPos` 映射回 board-space，服务端校验依然基于绝对坐标 |

## 2. 三种实现模式

### 2.1 棋类 — Board 180° 翻转模式

**适用游戏**：中国象棋、国际象棋、中国军棋（对局阶段）

```
红方（座位 0）            黑方（座位 1）
┌──────────────┐         ┌──────────────┐
│  对手阵营    │         │   我的阵营    │
│  ┌────────┐  │   flip  │  ┌────────┐  │
│  │ Row 0..4│  │ ──────► │  │ Row 9..5│  │
│  └────────┘  │         │  └────────┘  │
│  我的阵营    │         │  对手阵营    │
└──────────────┘         └──────────────┘
```

**关键代码模式**（`XiangqiBoard.tsx:37-62` / `ChessBoard.tsx:45-72` / `JunqiBoard.tsx:46-69`）：

```ts
const isFlipped = myColor === 'black';   // 仅黑方翻转

function posToPixel(x: number, y: number) {
  const bx = isFlipped ? COLS - 1 - x : x;
  const by = isFlipped ? ROWS - 1 - y : y;
  return { x: PADDING + bx * CELL, y: PADDING + by * CELL };
}

function pixelToPos(px: number, py: number) {
  const bx = Math.round((px - PADDING) / CELL);
  const by = Math.round((py - PADDING) / CELL);
  const x = isFlipped ? COLS - 1 - bx : bx;
  const y = isFlipped ? ROWS - 1 - by : by;
  return { x, y };
}
```

**判定规则**：

| 游戏 | 翻转触发条件 | 行数 / 列数 | 视角翻转后 myColor='red' 的 y=0 在屏幕 |
|------|------------|-------------|------------------------------------------|
| 中国象棋 | `myColor === 'red'` 翻转 | 10 行 × 9 列 | py = PADDING + 9·CELL（底部） |
| 国际象棋 | `myColor === 'white'` 翻转 | 8 行 × 8 列 | py = PADDING + 7·CELL（底部） |
| 中国军棋 | `myColor === 'red'` 翻转 | 12 行 × 5 列 | py = PADDING + 11·CELL（底部） |

> **关键不变量**：服务端始终把"我方阵营"的 y 坐标放在 **y=0**（如象棋红方 / 军棋红方 / 棋 white）。客户端翻转的目标是**让 y=0 在屏幕底部**——所以**阵营起点在 y=0 的一方需要翻转**，终点在 y=N-1 的一方不翻转。
>
> 这是 2026-07-03 修复的 bug：原实现 `isFlipped = myColor === 'black' / 'black'`，导致 y=0 在 py=PADDING（屏幕顶部），双方阵营都跑到了屏幕上半部。修复后 `isFlipped = myColor === 'red' / 'white'`，让"我方起点"在屏幕底部。

**注意事项**：

- 网格线、河界文字（如象棋"楚河汉界"）通常用**屏幕坐标绘制**，**不翻转**（这些是装饰元素，左右阅读方向统一）
- 棋子 / 星位 / 宫殿对角线等逻辑元素**必须**走 `posToPixel`，翻转后才能出现在正确视觉位置
- 房间号、棋盘标题、回合倒计时等 UI 元素同理用屏幕坐标，不翻转

### 2.2 卡牌类 — 虚拟座位旋转模式

**适用游戏**：斗地主（3 人）、德州扑克（2-6 人）

```
座位固定布局（CSS 6 个绝对定位锚点）:
┌──────────────────────────────┐
│ [3]      [4]                  │  ← 顶部 3 个座位
│ [2]                          │
│            [5]                │
│ [1]                          │  ← 左右 2 个座位
│            [0 - 我方]         │  ← 底部中央
└──────────────────────────────┘

旋转: 玩家 mySeat=2 看到:
- 位置 0 → 玩家 mySeat=2 (在底部)
- 位置 1 → 玩家 mySeat=3
- ...
```

**关键代码模式**（`TexasHoldemTable.tsx:32`）：

```ts
// 把"我"的座位旋转到位置 0，其它座位顺时针环绕
const seatOrder = Array.from({ length: 6 }, (_, i) => (mySeat + i) % 6);
const posClasses = ['s0-bottom', 's1-left', 's2-top-left', 's3-top', 's4-top-right', 's5-right'];

// 渲染时: seatOrder[i] → posClasses[i]
```

**斗地主 3 人版**（`DoudizhuTable.tsx:37-39`）：

```ts
const leftSeat = (mySeat + 1) % 3;   // 我左手边的对手
const rightSeat = (mySeat + 2) % 3;  // 我右手边的对手
```

**判定规则**：

| 游戏 | 座位容量 | 旋转公式 |
|------|----------|----------|
| 斗地主 | 3 | `(mySeat + 1) % 3` / `(mySeat + 2) % 3` |
| 德州扑克 | 2-6 | `(mySeat + i) % 6`, `i ∈ [0..5]` |

**注意事项**：

- 服务端按绝对座位号推送 `game.state.players[]`；前端永远按上面公式旋转，**不要改 server 推送顺序**
- 空座位用 `has_player: false` 占位，视觉上淡化（透明度 0.3-0.5）+ "等待加入" 提示
- 观战者 (`my_seat = -1`) 时不旋转，保持固定座位 0 在底部、座位 1 在左上 / 座位 2 在右上的"鸟瞰"视角

### 2.3 混合 / 异常 — `LayoutPanel` 坐标镜像模式

**适用场景**：棋类中**非对局**阶段的拖拽交互（如军旗布局阶段）

```
军棋布局面板:
红方 / 黑方 共用同一个 6×5 拖拽面板，但:
- 红方的"我方"是 y=0..5
- 黑方的"我方"是 y=6..11

解法: 在面板内引入 yBase 偏移
```

**关键代码模式**（`LayoutPanel.tsx:65-72`）：

```ts
export function LayoutPanel({ myColor, ... }) {
  const yBase = myColor === 'black' ? 6 : 0;
  const CAMP_CELLS = CAMP_CELLS_RED.map((c) => ({ ...c, y: c.y + yBase }));
  const HQ_CELLS = HQ_CELLS_RED.map((c) => ({ ...c, y: c.y + yBase }));
  const FRONT_ROW = FRONT_ROW_RED + yBase;
  const BACK_ROWS = BACK_ROWS_RED.map((r) => r + yBase);

  // drop target 循环:
  Array.from({ length: 6 }).flatMap((_, y) =>
    Array.from({ ..., x } => {
      const targetPos = { x, y: y + yBase };   // ← 关键
      ...
    })
  );
}
```

**判定规则**：在面板组件 `useState` 初始化完毕后、第一次引用 board-space 常量**之前**计算 `yBase`，所有硬编码常量（camp / HQ / 前排 / 后排）统一加偏移。

## 3. 观战者的默认视角

观战者 `my_color` / `my_seat` 为 `null` / `-1`，走下列默认值：

| 游戏类型 | 观战者看到 |
|----------|-----------|
| 棋类 | `myColor='red'`（硬编码红方视角，§19 / §22 修复后保持一致） |
| 卡牌类 | `mySeat=0`（硬编码座位 0 在底部） |
| 布局阶段 | LayoutPanel 接收 `myColor='red'`，yBase=0 |

观战者**不旋转**：所有观战者看到的是**同一固定鸟瞰视角**。若需多视角观战应使用 §16.5 描述的 observer routing。

## 4.5 2026-07-03 大修复：5 款游戏"我方在顶部" → 统一改为"我方在底部"

### 现象

| 游戏 | 旧行为（错误） | 修复后行为 |
|------|---------------|-----------|
| 中国象棋 | 红方/黑方视角下，**自己阵营都在屏幕顶部** | 红方阵营在底部（红方视角翻转）；黑方阵营在底部（黑方视角不翻转） |
| 国际象棋 | 同上 | 白方阵营在底部（白方视角翻转）；黑方阵营在底部（黑方视角不翻转） |
| 中国军棋 | 同上 | 红方阵营在底部（红方视角翻转）；黑方阵营在底部（黑方视角不翻转） |
| 斗地主 | 旋转逻辑正确，但未端到端验证 | 已确认 mySeat 落在 s0-bottom |
| 德州扑克 | 同上 | 已确认 mySeat 落在 s0-bottom |

### 根因

服务端 3 款棋类引擎（`ServerGo/game/{xiangqi,chess,junqi}/engine.go`）统一约定
**"我方阵营"在 y=0**：
- `xiangqi/engine.go:5` "Red side: y=0 (bottom), Black side: y=9 (top)"
- `chess/engine.go:5` "White side: y=0 (rank 1, near White player), Black side: y=7 (rank 8)"
- `junqi/engine.go:5-7` "Red side: y ∈ [0,5], Black side: y ∈ [6,11]"

3 款 Board 组件（`XiangqiBoard.tsx:37`、`ChessBoard.tsx:45`、`JunqiBoard.tsx:46`）用
`isFlipped = myColor === 'black'` 做翻转，再用 `by = isFlipped ? ROWS-1-y : y`
映射视觉 row。

但**屏幕 y=0 是顶部**（DOM / SVG 标准坐标系）。所以：
- 红方视角（isFlipped=false）→ by=y → 红方阵营 y=0 落到 py=PADDING（屏幕顶部）❌
- 黑方视角（isFlipped=true） → by=ROWS-1-y → 黑方阵营 y=N-1 落到 by=0（屏幕顶部）❌

**双方阵营都在顶部** —— 与"我方在底部"规范冲突。

### 修复

把判断条件从"颜色是否是黑"反转为"颜色是否是阵营起点方 (y=0 那方)"：

| 文件 | 旧 | 新 |
|------|----|----|
| `ClientWeb/src/components/xiangqi/XiangqiBoard.tsx:37` | `isFlipped = myColor === 'black'` | `isFlipped = myColor === 'red'` |
| `ClientWeb/src/components/chess/ChessBoard.tsx:45` | `isFlipped = myColor === 'black'` | `isFlipped = myColor === 'white'` |
| `ClientWeb/src/components/junqi/JunqiBoard.tsx:46` | `isFlipped = myColor === 'black'` | `isFlipped = myColor === 'red'` |

**军棋额外修复**：网格线（`JunqiBoard.tsx:100-105,107-110`）和铁路线（`JunqiBoard.tsx:115-122`）
原本用屏幕绝对坐标 `PADDING + r * CELL` 渲染，翻转后位置不对。改为走
`posToPixel(c, r)` 让它们跟着视觉翻转。

**国际象棋额外修复**：rank 标签 `(8 - r).toString()` 不依赖 isFlipped，黑方视角下
也显示 8 在顶 / 1 在底。改为 `(isFlipped ? 8 - r : r + 1).toString()`。

### 教训

- **"我方在底部"是个视觉方向问题，但实现藏在数学里**——`isFlipped` 的命名应该
  体现**翻转条件是什么**而不是"被翻转的人是谁"。建议改为
  `myPiecesAtBottom = myColor === 'red'` 这种"语义命名"防止下次再写反。
- **坐标系方向必须显式**：DOM / SVG 的 y 轴向下（顶部=0），服务端棋盘 y=0
  通常表示"起点行"（在屏幕上的视觉位置由 Board 组件决定）。任何新棋类组件都
  必须先确认**服务端 y=0 到底是阵营起点还是终点**——这是规范没明说但实现必须
  假设的前提。
- **棋盘 grid lines / 标签 / 装饰元素不能"绝对定位"** —— 它们看起来是装饰，
  但翻转视角下也需要跟着逻辑坐标走。除非是**真正的全局 UI**（如房间号、计时器），
  否则所有元素都应该经过 `posToPixel`。
- **静态检查脚本 §6 应该升级为强约束**：除了 grep 关键字，还要断言
  `isFlipped` 的等号右边是 `myColor === '阵营起点方'`（红/white）而非
  `myColor === 'black'`，避免后续新游戏写反。

## 5. 新增游戏 Checklist

若要新增一款多人 / 多座位游戏，按下列顺序实施：

1. **确定旋转/翻转模式**：2 人棋盘用 §2.1；3+ 人卡牌用 §2.2；阶段切换 / 拖拽等特殊 UI 用 §2.3。
2. **服务端定义 `my_*` 字段**：`my_color` / `my_seat` 在 `game.joined` 中下发，房间级 `BroadcastRoom` 不带这些字段（§19 教训）。
3. **前端 store**: `myColor` / `mySeat` 初值 `null` / `0`，提供 `setMy*` 与 `reset()` 两个 action。
4. **Hook 守卫**: 收到 `game.joined` / `game.started` / `game.state` 三种帧时统一用 `if (value) set*(...)` 模式，防止房间广播覆盖。
5. **Board/Table 组件**: §2.1 写 `isFlipped + posToPixel/pixelToPos`；§2.2 写 `seatOrder` / `leftSeat`/`rightSeat` 旋转。
6. **Spectator 模式**: `<GamePage>` 计算 `effectiveColor = spectator ? null : myColor`，spectator 时硬编码默认（红方 / 座位 0）。
7. **集成测试**: 至少包含 (a) 玩家 A 创建 + 玩家 B 加入 → B 拿到 `game.state` 时已经在底部；(b) refresh 后两人都还在底部。
8. **更新 CLAUDE.md §15-§17 + 本文件 §2 表格**：在新游戏对应位置补一行描述旋转模式。

## 6. 静态检查脚本（建议）

未来可加一条 `scripts/check-player-at-bottom.sh`，遍历 5 个 GamePage 文件 grep 关键字:

- `isFlipped = myColor === '(阵营起点方)'` (棋类，§4.5 后必须 === 'red' / 'white')
- `seatOrder = ` / `(mySeat + i) %` (卡牌类)
- `effectiveColor = spectator ? null : myColor`

**强化规则（§4.5 后）**：棋类 Board 组件 grep `isFlipped = myColor === 'black'` 必须报错
—— 这是反模式，黑方阵营在 y=N-1 而非 y=0，不该翻转。

缺失任一关键字则报错，确保新增/重构游戏时不会忘记"我方在底部"约束。
