## §1 背景 — 「半实现」角色的静默失效

守卫 `RoleGuard` 在 2026-07-11 扩展神职批次中被加入,但**只做了数据层**:

| 层级 | 现状(实现前) | 位置 |
|------|------------|------|
| 角色枚举 / wire 字符串 | ✅ `RoleGuard` → `"guard"` | `cards.go:61,87` |
| 阵营 / 神职判定 | ✅ `FactionGood` + `IsGodRole` | `cards.go:138,272` |
| **随机牌组池** | ✅ **在 `godRolePool` 中,会真实发牌** | `cards.go:294` |
| 中文显示名 | ✅ "守卫" | `cards.go:384` |
| 前端类型 / i18n 三语 | ✅ 完整 | `types/werewolf.ts:21` 等 |
| **引擎夜间阶段** | ❌ 无 `PhaseNightGuard` | — |
| **引擎 Action_ 方法** | ❌ 无 | — |
| **座位缓存 / 状态字段** | ❌ 无 `GuardSeat` / `GuardLastProtect` | — |
| **Agent 工具** | ❌ 无 `guard_protect` | — |
| **人类玩家 UI** | ❌ `NightActionPanel` 无守卫分支 | — |

**这是 §130 教训的完整复现**:声明了却从不接线 = 静默失效。
后果具体而严重 —— `RandomDeck13()` 会把守卫发给某个座位,**该玩家(人类或 Bot)
整局拥有一个完全无效的身份**:没有夜间行动、没有工具、`prompt.go` 与 `memory.go`
甚至明确告诉 LLM「⚠️ 当前引擎暂无独立工具」。13 人局 4 狼对 9 好人的平衡里,
好人阵营等于**少了一个神职**,而狼人阵营毫不知情地获得了额外优势。

> `activity_emitter.go:739` 早已存在 `case "guard": return "守卫守护"` 的中文标签,
> 是这条链路「设计了一半」的直接物证。

**本次(§134)目标**:把守卫补全为与女巫 / 预言家**同等公民**,打通
引擎 → Agent 工具 → 人类 UI → 法官 → 文档 七层。

## §2 游戏规则(产品定义)

### 2.1 技能

> **守卫**:每晚守护一名玩家,使其**免疫当晚狼刀**。

### 2.2 硬约束(按优先级)

| # | 约束 | 理由 | 引擎校验点 |
|---|------|------|-----------|
| G1 | **不可连续两晚守护同一人** | 防止「铁人」锁死一个关键神职,狼刀永久失效 | `GuardLastProtect[seat]` 比对 |
| G2 | **不可守护自己** | 防止守卫自锁无敌,自身成为免疫体 | `target != actor` |
| G3 | 只能守护**存活**玩家 | 与预言家 / 女巫一致 | `AliveSeat(target)` |
| G4 | 可以选择**空守**(`target=-1`) | 战术需要(如已被查杀需避嫌),也是 quarantine skip 的合法出口 | `NoSeat` 哨兵 |
| G5 | 护盾**只挡狼刀**,不挡女巫毒药 / 猎人开枪 / 白天放逐 | 保持毒药与猎人的威慑力 | 仅在 `cause=="wolf"` 路径生效 |

### 2.3 「同守同救」— 核心裁决规则

> **守卫护盾 + 女巫解药同时作用于同一目标 → 该玩家仍然死亡。**

这是官方经典规则,采用理由:

1. **反无敌组合**:若双重保护叠加生效,守卫 + 女巫可锁死一个目标,4 狼夜间压力归零。
2. **保留博弈张力**:守卫与女巫**互相看不见对方的行动**,「今晚他会不会也救?」
   是这两个神职之间最有价值的心理博弈。
3. **解药被消耗且不退还** —— 女巫为一次无效救援付出真实代价,决策有重量。

死亡语义(遵循 [`狼人杀死亡语义设计.md`](狼人杀死亡语义设计.md)):
`cause = "wolf"` → `verdict = "death"`(**死亡**,非处决)。

### 2.4 夜间结算优先级(判定表)

设狼刀目标 `W`、守卫目标 `G`、女巫解药目标 `A`:

| # | 条件 | 结果 | 说明 |
|---|------|------|------|
| 1 | `W == NoSeat` | 无人死于狼刀 | 空刀 |
| 2 | `G == W` 且 `A != W` | **W 存活** | 守卫单独生效 ✅ |
| 3 | `A == W` 且 `G != W` | **W 存活** | 解药单独生效 ✅ |
| 4 | `G == W` 且 `A == W` | **W 死亡** | 🔴 **同守同救** |
| 5 | `G != W` 且 `A != W` | **W 死亡** | 无保护 |

> 女巫毒杀走**独立**路径(`killPlayer(target,"witch_poison")`),
> 与护盾完全无关 —— 即使 `G == poisonTarget`,该玩家依然死亡(G5)。

### 2.5 夜间阶段顺序

采用官方标准顺序,守卫**最先**行动:

```
pre_wolves  (首夜强制发言缓冲)
    ↓
night_guard    ← §134 新增。守卫「盲守」——此时狼刀尚未产生
    ↓
night_wolves   (狼人投票刀人)
    ↓
night_seer     (预言家查验)
    ↓
night_witch    (女巫用药)
    ↓
dawn           (统一结算:护盾 / 解药 / 同守同救)
```

**「盲守」是刻意的设计**:守卫在狼刀之前行动,因此**无法看到当晚狼刀目标**,
必须靠推理预判狼人会刀谁。这与女巫「可见狼刀」形成鲜明对比,是守卫这个
角色的策略深度所在,也**杜绝了信息泄露**(守卫的 `GameContext.WolfTarget`
永远为 -1)。

## §3 引擎层设计(`ServerGo/game/werewolf/`)

### 3.1 Phase 常量

`engine.go` 的 `Phase` 枚举中,在 `PhasePreWolves` 与 `PhaseNightWolves` **之间**
插入 `PhaseNightGuard`:

```go
PhasePreWolves              // 首夜发言缓冲期
PhaseNightGuard             // §134 夜晚:守卫守护(盲守,在狼刀之前)
PhaseNightWolves            // 夜晚:狼人协商刀人
```

**安全性论证**(为何可以插在中间):
- 全仓 `grep "Phase >= / <= / > / <"` **零命中** —— 无任何按序数比较的逻辑。
- 数据库中 phase 一律以**字符串**列存储(`t_lsm_game_model_action.Phase varchar(32)` 等),
  没有任何表持久化 `Phase` 的 int 值 —— 插入常量不会破坏历史数据。

同步更新:
- `Phase.String()` → `"night_guard"`
- `Phase.IsNight()` → 加入 `PhaseNightGuard`(前端夜间渲染 / 闭眼态)

### 3.2 GameState 新增字段

```go
// 关键神职座位缓存(与 WitchSeat 并列)
GuardSeat Seat            // §134 守卫座位;NoSeat = 本局无守卫

// 守卫当晚守护目标(每晚重置);NoSeat = 空守
GuardProtectTarget Seat

// 守卫上一晚守护目标(跨夜保留,用于 G1 连守校验)
GuardLastProtect Seat
```

三者均在 `NewGameState` 初始化为 `NoSeat`;`GuardSeat` 在 `StartGame` 遍历
`Roles` 时赋值(与 `WitchSeat` 同一循环)。

**关键**:`GuardProtectTarget` 在 `startNight()` 中重置为 `NoSeat`,而
`GuardLastProtect` **不重置** —— 它正是 G1 连守校验的依据,必须跨夜存活。

### 3.3 核心方法

#### `NightGuardProtect(actor Seat, target Seat) *errcode.Error`

```
校验链:
  Phase == PhaseNightGuard        否则 ErrNotYourTurn
  actor == GuardSeat && 存活       否则 ErrPermissionDenied
  target == NoSeat                 → 空守,合法(G4),直接推进
  target != actor                  否则 ErrValidationFailed "cannot guard self" (G2)
  AliveSeat(target)                否则 ErrValidationFailed "target dead"      (G3)
  target != GuardLastProtect       否则 ErrValidationFailed
                                        "cannot guard the same player twice in a row" (G1)
生效:
  GuardProtectTarget = target
  GuardLastProtect   = target      // 空守时置 NoSeat,即"下一晚可守任何人"
  → endGuardPhase()
```

#### `endGuardPhase()`

与 `endWolfPhase` / `endSeerPhase` 完全同构:

```go
func (gs *GameState) endGuardPhase() {
    setPhaseAndDeadline(gs, PhaseNightWolves, hasHumanPlayer(gs))
    gs.TurnActingSeat = firstLivingWolf(gs)
    if gs.TurnActingSeat == NoSeat {
        gs.endWolfPhase()   // 无狼人 → 继续推进,不卡死
    }
}
```

#### `startNight()` 改造

原先直接切 `PhaseNightWolves`,现改为**先尝试守卫阶段**:

```go
gs.GuardProtectTarget = NoSeat     // 每晚重置(GuardLastProtect 保留)
if gs.GuardSeat != NoSeat && gs.AliveSeat(gs.GuardSeat) {
    setPhaseAndDeadline(gs, PhaseNightGuard)
    gs.TurnActingSeat = gs.GuardSeat
} else {
    setPhaseAndDeadline(gs, PhaseNightWolves)
    gs.TurnActingSeat = firstLivingWolf(gs)
}
```

**无守卫 / 守卫已死 → 完全跳过该阶段**,与 `endSeerPhase` 处理无女巫的方式一致。

#### `endWitchPhase()` 改造 — 护盾结算点

护盾在**夜间最末**统一结算,这样守卫、狼人、女巫三方的行动互不可见。

**为何需要 `WitchSavedTarget` 独立记录**:女巫用解药时,`NightWitchAct` 通过
**破坏性赋值** `gs.WolfKillTarget = NoSeat` 来表达「已救」。若护盾逻辑直接读
`WolfKillTarget`,则解药生效后该字段已是 `NoSeat`,护盾无从判断「守的是不是
同一个人」—— **同守同救永远无法触发**。因此必须新增字段独立记录:

```go
// NightWitchAct 的 antidote 分支:记录解药救的是谁(§134)
gs.WitchSavedTarget = gs.WolfKillTarget
gs.WolfKillTarget   = NoSeat
```

`endWitchPhase` 中的最终裁决 —— 两个分支必须**互斥**(`else if`):

```go
func (gs *GameState) endWitchPhase() {
    // §134 守卫护盾 / 同守同救裁决。两者互斥:若写成两条独立 if,
    // 同守同救先把 WolfKillTarget 复位为目标,紧接着护盾分支又会因
    // GuardProtectTarget == WolfKillTarget 把它清成 NoSeat —— 净效果
    // 变回"存活",同守同救规则被完全抵消。
    switch {
    case gs.WitchSavedTarget != NoSeat && gs.GuardProtectTarget == gs.WitchSavedTarget:
        // 同守同救 → 两者抵消,该玩家仍然死亡(解药已消耗,不退还)
        gs.SameGuardSameSave = gs.WitchSavedTarget
        gs.WolfKillTarget    = gs.WitchSavedTarget      // 复活判死
    case gs.WolfKillTarget != NoSeat && gs.GuardProtectTarget == gs.WolfKillTarget:
        // 护盾单独生效 → 挡下狼刀
        gs.GuardSavedTarget = gs.WolfKillTarget
        gs.WolfKillTarget   = NoSeat
    }

    if gs.WolfKillTarget != NoSeat { ... killPlayer("wolf") ... }   // 原有逻辑不变
    ...
}
```

> `WitchSavedTarget != NoSeat` 的前置判断同时也排除了「守卫空守 + 女巫未用解药」
> 时两者同为 `NoSeat` 而被误判为相等的情况。
> `WitchSavedTarget` / `GuardSavedTarget` / `SameGuardSameSave` 均在 `startNight()` 重置。

### 3.4 死亡语义

同守同救致死沿用 `cause = DeathCauseWolf`("wolf") → `verdictFor` → `"death"`(**死亡**),
无需新增 cause 常量,`normalizeDeathTerms` / `death_semantic_version` 不受影响。

### 3.5 Manager 层(`room.go`)

严格遵循 **§92a 双变体**约束 —— 每个 `Action_*` 必须同时有锁内 `*Locked` 变体:

| 方法 | 位置 | 说明 |
|------|------|------|
| `Action_GuardProtect(roomID, userID, target)` | `room.go` | 公开入口,`r.mu.Lock()` |
| `guardProtectLocked(r, userID, target)` | `room_quarantine_skip_locked.go` | 锁内变体,供 quarantine / watchdog |

`guardProtectLocked` 成功后调 `m.EmitGuardProtect(r)` + `m.wakeActingAgentsLocked(r,"state_change")`,
与 `witchLocked` 完全同构。

### 3.6 三处 phase 映射表(§97 硬约束)

新增阶段**必须**同步这三处,漏一处即阶段死锁:

| 位置 | 文件 | 新增内容 |
|------|------|---------|
| `SkipPhaseAction` | `agent/run.go` | `"night_guard"` → `("guard_protect_skip", 0)` |
| `watchdogActingSeat` | `room.go` | `case PhaseNightGuard: return int(gs.TurnActingSeat)` |
| `dispatchQuarantinedSkipLocked` | `room.go` | `case "guard_protect_skip"` → `guardProtectLocked(r,userID,NoSeat)` (空守) |

另需同步:
- `isActingPhase()` → 加 `"night_guard"`(否则 bot 不会被唤醒思考)
- `defaultPhaseDeadlineSec()` → `night_guard`: human=120s / 全 AI=300s(与其它夜间阶段一致)

### 3.7 视图层(`view.go`)

```go
// ClientGameState 新增(仅守卫本人可见)
GuardLastProtect  int  `json:"guard_last_protect,omitempty"`  // 上晚守护目标(-1=无)
```

## §4 Agent 层设计(`ServerGo/agent/`)

### 4.1 工具 `guard_protect`

`BuildTools` 新增分支(仅 `role=="guard"` 且 `phase==night_guard` 时暴露):

```go
case "PhaseNightGuard", "night_guard":
    if role == "guard" {
        add("guard_protect", "守卫夜间守护。<策略段>",
            schema(map[string]any{"target": map[string]any{
                "type": "integer",
                "description": "守护目标座位号(-1=空守)",
                "enum": <存活 ∖ {自己} ∖ {上晚目标} ∪ {-1}>,
            }}, "target"))
    }
```

**关键**:`enum` 在**服务端**就剔除自己与上晚目标 —— LLM 从根本上无法选出
违规目标,而不是靠事后报错纠正。这与 `seer_check` 的 `filterSelf` 同思路,
可显著降低无效 tool_use 轮次(对慢模型尤其重要,见 §197)。

工具 description 中的策略段(与女巫 / 预言家同规格):

```
❶ 优先守护「已跳预言家」的玩家 —— 狼刀首选目标。
❷ Day1 无信息时可守自认为最像神职的玩家,或空守观察。
❸ ⚠️ 不能连守同一人 —— 上晚守过的人今晚不可再守(enum 已剔除)。
❹ ⚠️ 不能守自己。
❺ 你看不到今晚狼刀目标(盲守),必须靠推理预判。
❻ 「同守同救」:若你守的人同时被女巫解药救,该玩家反而会死 —— 
   若你判断女巫极可能救 X,可考虑改守他人。
❼ 公开发言不要直说「我守了 X」,会立刻成为狼刀首选。
```

第 ❻ 条是**规则与策略的闭环**:把同守同救这一反直觉规则显式教给 LLM,
否则模型会按常识认为「双保险更安全」而做出错误决策。
