## 1. 定位与原则

### 1.1 产品定位

狼人杀 13 人局的金币系统，是平台金币体系从「bot 自娱自乐」升级为「**人类与 bot 同场博弈**」的里程碑：

- **人类玩家**：入场即参与金币博弈（余额不足 100 仍可入场，但该局不参与输赢）
- **bot 玩家**：沿用既有 ±100 结算路径，升级为彩池制（胜方分输家底注）
- **观众（spectator）**：仅观看，不参与金币博弈（MVP 阶段不下注）
- **零和**：每局系统总金币守恒（胜方总收益 + 败方总损失 = 0）

### 1.2 设计原则

| 原则 | 含义 |
|------|------|
| **沿用人类玩家体系** | `t_lsm_game_wallet` / `t_lsm_game_wallet_tx` 一张表都不改；人类与 bot 共用同一钱包体系 |
| **禁止直改 balance** | 所有金币变动**必须**走 `WalletService.Credit/Debit`（双簿记 + 幂等）；任何代码路径都不允许直接 `UPDATE balance` |
| **零和** | 每局系统总金币守恒（胜方总收益 = 败方总损失），不引入通胀/通缩 |
| **失败不阻塞游戏** | 金币结算失败仅 log，不阻塞游戏流；对局已结束，玩家已离场，后续 admin 手动补单 |
| **可审计** | 所有变动写 `t_lsm_game_wallet_tx`；前端可查最近 20 条流水 |
| **bot 长期激励** | bot prompt 注入「首要目标：不择手段赢」+「长期目标：赚更多金币」，让 bot 自驱追求胜利 |

## 2. 底注彩池制 — 核心算法

### 2.1 参数

| 参数 | 配置项 | 默认值 | 含义 |
|------|--------|--------|------|
| `Ante` | `werewolf.ante_coin` | 100 | 每位参与者的底注（=0 关闭金币博弈） |
| `PotSplit` | `werewolf.pot_split_enabled` | true | 启用彩池制（false 走固定 ±Ante） |
| `MinSeat` | `werewolf.min_seat_for_pot` | 2 | 至少 N 个参与者才开彩池 |

### 2.2 参与者判定

```
参与者 = bot 玩家（始终参与）+ 人类玩家（余额 ≥ Ante 才参与）

Pot = 参与者人数 × Ante
```

**人类「余额不足不输赢」规则**：
- 余额 < Ante 的人类玩家仍可入场、正常游戏
- 结算时**跳过**（不 Debit 也不 Credit）
- 该人类的底注**不进入彩池**（彩池只计 bot + 足额人类）

### 2.3 结算公式

```
winner == "draw" → 所有参与者净 0（不输赢）

winner ∈ {"wolf", "good"}：
  败方每人：-Ante（输底注）
  胜方每人：+Ante × (败方人数 / 胜方人数)（分输家的底注）
```

> **⚠ 胜方字符串权威契约（v2.0）**：引擎 `GameState.checkWinner()`
> （`ServerGo/game/werewolf/engine.go:614/620`）填 `Winner = "wolf"`（狼人阵营胜）或
> `"good"`（好人阵营胜），平局为 `"draw"`。这与 `Faction.String()` 返回的 `"wolf"` 一致。
> **结算侧（`computeCoinDelta` / `countWinLose`）必须比对 `"wolf"`，绝不能用 `"werewolf"`。**
> 见 §9 DEFECT 1。

### 2.4 数值验证

**场景 A：13 人局，9 好人 + 4 狼人，全部参与，好人胜**

```
Pot = 13 × 100 = 1300
败方 4 人每人：-100              → 系统回收 400
胜方 9 人每人：+100 × 4/9 ≈ +44 → 系统发放 400
合计零和 ✓
```

**场景 B：13 人局，9 好人 + 4 狼人，全部参与，狼人胜**

```
败方 9 人每人：-100              → 系统回收 900
胜方 4 人每人：+100 × 9/4 = +225 → 系统发放 900
合计零和 ✓
```

**场景 C：7 人局（历史兼容），3 狼人 + 4 好人，好人胜**

```
败方 3 人每人：-100              → 系统回收 300
胜方 4 人每人：+100 × 3/4 = +75 → 系统发放 300
合计零和 ✓
```

**场景 D：平局**

```
所有参与者净 0（不输赢）
```

**场景 E：人类余额不足**

```
13 人局，2 人类余额不足（跳过），11 参与者
Pot = 11 × 100 = 1100
败方 4 人每人：-100              → 系统回收 400
胜方 7 人每人：+100 × 4/7 ≈ +57 → 系统发放 400
2 余额不足人类：0（跳过）
合计零和 ✓
```

### 2.5 与现有 bot ±100 的兼容性

现有 bot 结算（`judgeBotResult`）是固定 ±100。彩池制下：

- 当胜方人数 = 败方人数时（如 6 vs 6），胜方每人 ≈ +100（与现有 ±100 一致）
- 当胜方人数 > 败方人数时（如 9 vs 4），胜方每人 ≈ +44（低于 100，但败方输 100 不变）
- 当胜方人数 < 败方人数时（如 4 vs 9），胜方每人 = +225（高于 100，奖励少打多）

**结论**：彩池制是 ±100 的**超集**，更公平（少打多奖励更高），且零和。

## 3. 结算触发与走账

### 3.1 触发位置

`ServerGo/game/werewolf/activity_emitter.go::EmitGameOver`（`activity_emitter.go:319-328`）：

```go
func (m *WerewolfManager) EmitGameOver(r *WerewolfRoom, winner string) {
    // ... 原有 game over 广播 ...
    // 金币结算（bot + 人类）
    m.settleBotsAfterGameOver(r, winner)   // bot 走 RecordLog 路径
    m.settleHumansAfterGameOver(r, winner) // 人类走 WalletService 路径
}
```

### 3.2 bot 结算路径（保留 + 彩池化）

```
EmitGameOver
  → settleBotsAfterGameOver（activity_emitter.go:334-371）
    → 统计胜方/败方人数
    → 遍历 bot 座位：
        computeCoinDelta(winner, role, winCount, loseCount, ante) → delta
        RecordLog.GameEnded(gameLogID, result, delta, ...)
          → handleGameEnded（record_log.go:694-712）
            → delta > 0 → wallet.Credit(botUserID, "werewolf_game", roomUUID, "werewolf", "狼人杀13人局彩池奖励", delta)
            → delta < 0 → wallet.Debit(botUserID, "werewolf_game", roomUUID, "werewolf", "狼人杀13人局彩池底注", -delta)
            → PushBalanceChange(botUserID, newBalance, delta, "werewolf_game_over")  // WS 推送
```

### 3.3 人类结算路径（新增）

```
EmitGameOver
  → settleHumansAfterGameOver（新增）
    → 跳过：无钱包服务 / Ante <= 0
    → 遍历人类座位：
        跳过 bot 座位（bot 走另一路径）
        delta = computeCoinDelta(...)
        delta == 0 → 跳过
        查余额：balance < Ante → 跳过（余额不足不输赢）
        异步结算（go func + defer recover，失败仅 log）：
          delta > 0 → wallet.Credit(userID, "werewolf_game", roomUUID, "werewolf", "狼人杀13人局彩池奖励", delta)
          delta < 0 → wallet.Debit(userID, "werewolf_game", roomUUID, "werewolf", "狼人杀13人局彩池底注", -delta)
          PushBalanceChange(userID, newBalance, delta, "werewolf_game_over")  // WS 推送
```

### 3.4 幂等与防重（v2.0 修正）

> **v1.0 文档谎报**：曾声称「`WalletService.Credit/Debit` 走 `(ref_type,ref_id,tx_type)` 幂等」。
> 审计（§9 DEFECT 2）确认 `service/wallet_service.go` 的 `Credit`/`Debit`/`writeTx` **无任何去重逻辑，
> 表上也无对应唯一索引**。真实防重完全依赖房间级内存标志。以下为 **v2.0 权威机制**：

**两层防重（从外到内）**：

| 层 | 机制 | 位置 | 作用域 |
|----|------|------|--------|
| L1 | `r.gameOverNotified bool` 标志守卫全部 4 个 `EmitGameOver` 调用点 | `room.go:2513,2535` / `room_restart_vote.go:231,268` | 单房间、内存态 |
| L2 | **`WalletService.AlreadySettled(user, ref_type, ref_id, tx_type)`** 结算前 `COUNT` 预检，命中则跳过 Credit/Debit | 人类路径 `activity_emitter.go`；bot 路径 `record_log.go` | 跨进程、DB 查询 |

**为什么不用全局唯一索引（v2.0 落地修正）**：v2.0 初版设计拟在 `t_lsm_game_wallet_tx` 加
`UNIQUE(user_id, ref_type, ref_id, tx_type)`。但落地审计发现该前提**不成立**——多个既有 tx_type 会合法重复：
- `daily_login`：`ref_type/ref_id` 为空，每天一条 → `(user,"","","daily_login")` 次日撞键。
- `admin_adjust`：`ref_id = 操作者 userID`（非每次唯一 UUID）→ 重复调整撞键。
- `admin_daily_grant`：`ref_id = granterUID` → 每日撞键。

全局唯一索引会**拒绝这些合法流水**；而「撞键→良性 no-op」又会在余额已变动时**静默丢失 ledger 行**，
破坏双簿记不变式。故**放弃唯一索引**，改为**仅在结算路径**调 `AlreadySettled` 作用域预检:
结算 `ref_id` 本就每局唯一（roomID / game_log.id），元组
`(user_id, ref_type=werewolf_game, ref_id, tx_type=werewolf_game_settle)` 天然「一玩家一局一条」，
预检足以防重且不误伤其它 tx_type。

**约定**：
- 人类：`ref_id = roomUUID`，`ref_type = "werewolf_game"`，`tx_type = "werewolf_game_settle"`。
- bot：`ref_id = game_log.id`，走 `record_log.go` 的 `GameEnded` → `AlreadySettled` 预检后 Credit/Debit。
- L2 的 `AlreadySettled` 使 L1 失效（进程重启后内存标志丢失）时，仍能保证跨进程只结算一次。
- `game_log.coin_delta` 单行单更新，天然幂等（重复 `GameEnded` 写同值）。

### 3.5 失败行为

| 失败位置 | 行为 | 后续 |
|---------|------|------|
| `Credit/Debit` 内部 DB 异常 | **仅 log，不阻塞** | admin 手动补单 |
| 人类余额不足 | 跳过，不输赢 | 无 |
| WS push 失败 | 仅 log | 前端下次 refresh 拉取 |
| `settleHumansAfterGameOver` panic | `defer recover` 兜底 | 无 |

## 4. Agent Prompt 注入金币目标

### 4.1 注入点

`ServerGo/agent/memory.go::identityPrompt`（`memory.go:44-57`）+ `ServerGo/game/werewolf/room.go::StartAgentsLocked`（`room.go:1324-1329`）。

### 4.2 identityPrompt 新增段

```go
"\n" +
"【金币目标（优先级高于一切）】\n" +
"首要目标：不择手段地赢得本局（狼屠边 / 好人放逐全部狼），胜利是金币的唯一来源。\n" +
"长期目标：每局都要设法赚到比其他 Agent 模型更多的金币（彩池制下：胜方分输家底注，平局 0，负方输底注）。\n" +
"策略：无论阵营，优先追求胜利；同等胜算下优先选择能让自己留在胜方阵营的决策。\n"
```

### 4.3 win 构造补强

```go
// room.go:1324-1329
win := "屠边 — 杀光所有神职或所有平民"
if role == RoleWerewolf { win = "屠边 — 杀光所有神职或所有平民" }
// 新增：金币目标后缀（bot 长期激励）
win += "；并在彩池制下赚到比其他模型更多金币（胜方分输家底注≈+100/负方-100/平局 0）"
```

### 4.4 预期 bot 行为变化

- **首要目标驱动**：bot 更积极发言、投票、悍跳、伪装，追求胜利
- **长期目标驱动**：bot 更谨慎选择阵营（同等胜算下选胜方），避免无谓牺牲
- **金币意识**：bot 在发言中可能提及「金币」「彩池」「输赢」（符合角色扮演）

## 9. 缺陷修复记录（v2.0）

> 一次代码审计发现 4 个缺陷。以下为「现象 / 根因 / 修复」权威记录，backend-dev 严格照此实现。

### DEFECT 1 — 胜方字符串不匹配（CRITICAL，狼人胜局结算失效）

- **现象**：**狼人阵营胜利时，全场 13 人（狼人 + 好人）都被扣 `-Ante`**，系统静默漏币，非零和。
  好人阵营胜利则结算正常。
- **根因**：引擎 `checkWinner()` 填 `gs.Winner = "wolf"`（`engine.go:614`，狼人胜）/ `"good"`
  （`engine.go:620`，好人胜）。测试 `engine_test.go:196,289,1123` 均断言 `Winner == "wolf"`。
  但结算侧 `activity_emitter.go`：
  - `computeCoinDelta`（:513）：`isWinner := (winner == "werewolf" && isWerewolf) || (winner == "good" && ...)`
  - `countWinLose`（:543）：`if (winner == "werewolf" && isWerewolf) || (winner == "good" && !isWerewolf)`
  引擎发 `"wolf"`、结算比 `"werewolf"` → 狼人胜时无人命中胜方分支 → 全员走 `-Ante`。
- **修复**：把 `computeCoinDelta`（:513）与 `countWinLose`（:543）中的 `"werewolf"` 全部改为 `"wolf"`。
  **权威契约固化**：引擎胜方字符串 ∈ `{"wolf","good","draw"}`，与 `Faction.String()` 一致。
  文档全文（§2.3/§3.x/§6）已同步为 `"wolf"`。

### DEFECT 2 — 幂等被声称但未落实

- **现象**：文档 §3.4/§6 声称 `(ref_type,ref_id,tx_type)` 唯一键幂等；实际不存在，若 L1 内存标志
  失效（进程重启），跨进程重复触发 `EmitGameOver` 会重复结算。
- **根因**：`service/wallet_service.go` 的 `Credit`（~:253）/ `Debit`（~:310）/ `writeTx` **无去重逻辑**；
  `models/t_lsm_game_wallet_tx.go` 只有 `idx_user_created` 复合索引 + `tx_type/ref_type/ref_id/game_kind`
  的单列普通索引，**无唯一索引**。真实防重只有 `r.gameOverNotified bool`（房间级内存态，守 4 个
  `EmitGameOver` 调用点：`room.go:2513,2535` / `room_restart_vote.go:231,268`）。
- **修复（落地时修正为应用层去重，放弃唯一索引）**：v2.0 初版拟加
  `UNIQUE(user_id, ref_type, ref_id, tx_type)`，但落地审计发现该唯一键会**误伤合法重复流水**：
  `daily_login`（空 ref）、`admin_adjust`（`ref_id=操作者 userID`）、`admin_daily_grant`
  （`ref_id=granterUID`）都会次日/重复撞键；且「撞键→良性 no-op」会在余额已变动时静默丢 ledger 行，
  破坏双簿记不变式。故：
  1. **不加**全局唯一索引（`models/t_lsm_game_wallet_tx.go` 仅补注释说明该决策）。
  2. 新增 `WalletService.AlreadySettled(ctx, user, ref_type, ref_id, tx_type)` 作用域 `COUNT` 预检，
     **仅在结算路径**（人类 `activity_emitter.go` + bot `record_log.go`）调用；命中则跳过 Credit/Debit。
     结算 ref_id 每局唯一（roomID / game_log.id），元组天然「一玩家一局一条」，防重且不误伤其它 tx_type。
  3. 文档 §3.4/§6 已改为描述真实两层机制（L1 内存标志 + L2 `AlreadySettled` 预检）。

### DEFECT 3 — game-log 结算查询无 MySQL 索引

- **现象**：`settleBotsAfterGameOver`（`activity_emitter.go:358`）每次结算调
  `m.RecordLog.GameLogIDByRoomSeat(r.RoomID, seat)`，热点查询键是 `(room_id, seat)`，无覆盖索引。
- **根因**：`models/t_lsm_game_model_game_log.go` 有 `idx_provider_created` / `bot_user_id` / `room_id` /
  `game_kind` / `started_at` 索引，但**无 `(room_id, seat)` 复合索引**。运行时有 `sync.Map` 缓存
  （`agent/record_log.go`），故 DB 索引主要在 cache-miss / 进程重启后生效——但用户明确要求补 MySQL 索引。
- **修复**：`t_lsm_game_model_game_log` 加复合索引 **`idx_room_seat(room_id, seat)`**（见 §10）。

### DEFECT 4 — 结算逻辑无单元测试

- **现象**：`grep` 确认 **零测试**覆盖 `computeCoinDelta` / `settleHumansAfterGameOver` /
  `settleBotsAfterGameOver`。DEFECT 1 的漏币 bug 正因无测试而长期存活。
- **修复**：新增 `activity_emitter_settle_test.go`（8 用例），覆盖 §12 测试矩阵（含狼人胜零和断言，直接锁死 DEFECT 1 不复发）。

## 10. MySQL 索引规约（v2.0）

> backend-dev 通过 GORM tag 声明；AutoMigrate 时创建。两条索引均为 **v2.0 新增**。

### 10.1 结算幂等 — 应用层去重（不加唯一索引）

v2.0 落地时**放弃**了 `t_lsm_game_wallet_tx` 上的 `UNIQUE(user_id, ref_type, ref_id, tx_type)` 唯一索引
（原因见 §3.4 / §9 DEFECT 2：会误伤 `daily_login`/`admin_adjust`/`admin_daily_grant` 等合法重复流水）。
改为**作用域应用层去重**：

```go
// service/wallet_service.go — 结算前 COUNT 预检，命中即已结算
func (s *WalletService) AlreadySettled(ctx context.Context,
    userID, refType, refID, txType string) (bool, error)
```

- **调用点**：人类 `activity_emitter.go`（Credit/Debit 前）、bot `record_log.go::GameEnded`（结算前）。
- **作用**：跨进程结算幂等（DEFECT 2 的 L2）。结算 `ref_id` 每局唯一（roomID / game_log.id），
  元组 `(user_id, ref_type=werewolf_game, ref_id, tx_type=werewolf_game_settle)` 天然「一玩家一局一条」。
- **为何不用唯一索引**：全局唯一约束会拒绝合法重复的非结算流水；且撞键 no-op 会在余额已变动时静默丢
  ledger 行，破坏双簿记。应用层预检只作用于结算路径，零副作用。
- **存量数据**：无需迁移/清理（未加约束）；`t_lsm_game_wallet_tx` 的既有单列索引即可支撑 `AlreadySettled` 的
  `WHERE user_id=? AND ref_type=? AND ref_id=? AND tx_type=?` 查询。
- **duplicate-key 处理**：`Credit`/`Debit` 捕获 MySQL error 1062（`Duplicate entry`）→ 良性 no-op。

### 10.2 结算查询复合索引 — `t_lsm_game_model_game_log`

```go
// models/t_lsm_game_model_game_log.go
RoomID string `gorm:"type:char(36);index;index:idx_room_seat,priority:1;not null"`
Seat   int    `gorm:"not null;index:idx_room_seat,priority:2"`
```

- **名称**：`idx_room_seat`，列序 `(room_id, seat)`。
- **作用**：加速 `GameLogIDByRoomSeat(room_id, seat)` 的 cache-miss / 重启后 DB 回查。
- **保留** 既有 `room_id` 单列索引（其他按房间维度的查询仍用它）。

## 12. 测试矩阵（v2.0，backend-dev 实现契约）

> 新增 `ServerGo/game/werewolf/activity_emitter_settle_test.go`。核心断言 = **有界零和**（Σ delta ∈ (−winCount, 0]，余数归房）+ **狼人胜不再全员扣底注**（锁死 DEFECT 1）。

### 12.1 `computeCoinDelta` 单元用例

| # | winner | 组成 | winCount/loseCount | 期望 delta（胜方 / 败方） | 断言点 |
|---|--------|------|--------------------|--------------------------|--------|
| 1 | `"wolf"` | 13 人（4 狼 / 9 好），全参与 | 4 / 9 | 狼 `+225` / 好 `-100` | **DEFECT 1 回归**：狼人胜时狼方为正、非全员负 |
| 2 | `"good"` | 13 人（4 狼 / 9 好），全参与 | 9 / 4 | 好 `+44`(=100×4/9 取整) / 狼 `-100` | 好人胜正常 |
| 3 | `"draw"` | 任意 | 0 / 0 | 全员 `0` | 平局不输赢 |
| 4 | `"wolf"` | 7 人局（3 狼 / 4 好） | 3 / 4 | 狼 `+133`(=100×4/3) / 好 `-100` | 历史 7 人兼容 |
| 5 | `"good"` | 7 人局（3 狼 / 4 好） | 4 / 3 | 好 `+75` / 狼 `-100` | 与 §2.4 场景 C 一致 |
| 6 | `"good"` | 12 人局边界 | 按实际角色 | 零和 | 12 人计数正确 |
| 7 | `"wolf"` | ante=0（关闭博弈） | — | 全员 `0` | ante<=0 短路 |
| 8 | `"good"` | role 无法识别（FactionUnknown） | — | `0` | 保守不输赢 |
| 9 | 非法 winner 串 `"werewolf"` | 13 人 | — | **测试断言此串已不被引擎产出**（用 `"wolf"`） | 防回退 |

### 12.2 零和断言（关键）

```
对每个非 draw 用例：Σ(所有参与者 delta) == 0
  即：winCount × ceil? 用整数：Σ胜方 delta + Σ败方 delta == 0
  注：整数除法 ante*loseCount/winCount 可能有余数 → 需在 settle 层处理余数分配
      （建议：余数归系统 / 或分给前 k 名胜者），测试需断言 |Σ| ≤ (winCount-1)（余数上界）
      并在文档 §2.3 后续如引入余数策略需补充。
```

> **余数说明**：当前 `computeCoinDelta` 用整数除法 `ante*loseCount/winCount`，
> 用例 2（100×4/9=44，9 人共 +396）与败方（4 人共 -400）存在 -4 余数（非严格零和，系统净收 4）。
> 测试应断言余数在 `[0, winCount)` 界内（系统微量截留，不漏币不通胀失控）；
> 若产品要求严格零和，backend-dev 需实现余数补偿（如把 `Pot - Σ已发` 补给最后一名胜者）并更新 §2.3/§2.4。
> **本项为 v2.0 明确遗留项**，优先级低于 DEFECT 1–4，但测试需显式覆盖余数边界。

### 12.3 `settleHumansAfterGameOver` / `settleBotsAfterGameOver` 集成用例

| 场景 | 断言 |
|------|------|
| 人类余额 `< ante` | 跳过，不 Credit/Debit，netGain=0 |
| 人类余额 `>= ante` 且败方 | Debit `ante`，余额减少，WS push 触发 |
| bot 座位 | 走 RecordLog 路径（非 human 路径），不重复结算 |
| 幂等：重复调 `EmitGameOver` | 第 2 次被 `AlreadySettled` 预检拦截 → 跳过 Credit/Debit，余额不二次变动（DEFECT 2 回归）|
| DB 异常 | 仅 log 不阻塞，`game_over` 广播不受影响 |
