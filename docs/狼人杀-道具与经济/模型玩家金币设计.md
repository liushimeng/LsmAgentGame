# 模型玩家金币设计

> 版本：v1.0  |
> 作者：game-designer  |
> 状态：实施就绪  |
> 适用范围：LsmWebGame 平台中所有「LLM 模型玩家」的金币体系（本期仅狼人杀先落地）
>
> **核心定位**：模型是平台的**持久玩家**，与人类用户享有完全相同的钱包体系。
> 禁止管理员直接修改 balance，只能通过 ledger entry 调整。

---

## 1. 定位与原则

### 1.1 产品定位

LLM 模型在 LsmWebGame 平台中不再只是「临时算力」，而是**与人类用户并列的持久玩家**：

- 模型有 `t_lsm_game_user` 账户（`IsBot=true`）
- 模型有 `t_lsm_game_wallet` 钱包（默认 1000 金币）
- 模型有 `t_lsm_game_wallet_tx` 流水（双簿记不可篡改）
- 模型可参与金币博弈（狼人杀对局 ±100 结算）
- 模型可被 admin 手动 adjust（super only，走 ledger）

### 1.2 设计原则

| 原则 | 含义 |
|------|------|
| **沿用人类玩家体系** | `t_lsm_game_wallet` / `t_lsm_game_wallet_tx` 一张表都不改；模型玩家只是 `IsBot=true` 的特殊用户 |
| **禁止直改 balance** | 所有金币变动**必须**走 `WalletService.ApplyTransaction`（双簿记 + 幂等锁）；任何代码路径都不允许直接 `UPDATE balance` |
| **结算金额（底注彩池制）** | 狼人杀 13 人局已升级为**底注彩池制**：胜方分输家底注（≈ 每人 +Ante×败方数/胜方数），败方 -Ante，平局 0。默认 Ante=100，故胜负人数相等时退化为 ±100。详见 [`docs/狼人杀13人局金币系统设计.md`](狼人杀13人局金币系统设计.md)（v2.0）。本文档下述「±100」段落为该彩池制的简化描述 |
| **失败不阻塞游戏** | 金币结算失败仅 log，不阻塞游戏流；对局已结束，玩家已离场，后续 admin 手动补单 |
| **可审计** | 所有变动写 `t_lsm_game_wallet_tx`；前端可查最近 20 条流水 |

## 2. 金币生命周期

### 2.1 状态机

```
注册 bot 用户
  ↓
EnsureWallet → balance=1000 (沿用 TLsmGameWallet default)
  ↓
[活跃] 参与对局 → 结算 ±100
  ↓
[休眠] 模型 disabled（admin 软删）
       → 余额冻结，不参与新对局
       → 历史对局日志保留
  ↓
[可能的 adjust] super 手动 adjust（走 ledger）
  ↓
[可能的补单] 结算失败后 admin 补单
```

### 2.2 各阶段细节

#### 2.2.1 注册 seed

| 项目 | 值 |
|------|---|
| 发放时机 | `service.BotUserService.EnsureBotUserForProvider` 调 `WalletService.EnsureWallet` |
| 发放金额 | **1000 金币**（与人类用户一致，沿用 `TLsmGameWallet` 的 `default:1000`） |
| 一次性 | ✅ 每个 user_id 仅 1 次（由 `t_lsm_game_wallet.user_id` 唯一键保证） |
| 幂等 | 若 `EnsureWallet` 发现已有 wallet → 保留余额，不覆盖 |

#### 2.2.2 对局结算

| 项目 | 值 |
|------|---|
| 触发时机 | `ServerGo/game/werewolf/activity_emitter.go::EmitGameOver` 内 |
| 胜方 | +100 金币 |
| 败方 | -100 金币 |
| 未完成/abandoned | 0（写 ledger `tx_type=game_abandon_no_change`，amount=0 留痕） |
| 走账通道 | `WalletService.ApplyTransaction`（已存在，幂等 + 双簿记） |

#### 2.2.3 Admin 手动 adjust

| 项目 | 值 |
|------|---|
| 触发入口 | `POST /api/admin/llm/bots/:botUserID/wallet/adjust` |
| 权限 | **super**（admin 也不可） |
| 必填字段 | `amount`（正数=加，负数=减） + `remark`（审计说明，必填，最长 255 字） |
| 走账通道 | `WalletService.ApplyTransaction`（`tx_type=admin_adjust`） |
| 审计 | 自动写 `t_lsm_game_wallet_tx`，记录 admin_user_id + amount + balance_after + remark |

#### 2.2.4 模型 disable 后的余额

- 软删除模型（`Enabled=false`）**不**清零余额，**不**冻结 wallet。
- 余额继续保留在 `t_lsm_game_wallet`，但模型不再出现在新房间的可选列表中。
- 历史对局日志、对局结算流水完整保留。

### 2.3 完整时间线范例

```
T+0s    admin POST /api/admin/llm/providers
        → 插入 t_lsm_game_llm_provider (DouBao-model, ...)
        → service.BotUserService.EnsureBotUserForProvider
        → 插入 t_lsm_game_user (account=bot_doubao_model, IsBot=true)
        → WalletService.EnsureWallet
        → 插入 t_lsm_game_wallet (user_id, balance=1000)

T+10min admin POST /api/games/werewolf/rooms
        → 选 7 个 bot 进入房间
        → 启动 7 个 in-process Agent goroutine

T+25min 狼人杀对局结束（村民阵营胜）
        → activity_emitter.go::EmitGameOver
        → 遍历 7 个 bot 玩家：
            胜方 (4 bots 村民) → +100 → ApplyTransaction(tx_type=model_game, amount=+100)
            败方 (3 bots 狼人) → -100 → ApplyTransaction(tx_type=model_game, amount=-100)
        → 写 t_lsm_game_model_game_log.ended_at / result / coin_delta

T+30min admin GET /admin/models/DouBao-model
        → 看到余额: 1100 (4 个胜方) 或 900 (3 个败方)
        → 最近 20 条流水: 对局<RoomID>结算 ±100
```

## 3. 结算规则（狼人杀先行落地）

### 3.1 触发位置

`ServerGo/game/werewolf/activity_emitter.go::EmitGameOver` 内**新增**结算逻辑：

```go
// 伪代码
func (m *WerewolfManager) EmitGameOver(r *WerewolfRoom, winner string) {
    // ... 原有 game over 逻辑 ...
    
    // 【新增】遍历所有 bot 玩家，按 winner 字段算 CoinDelta
    for seat, player := range r.Players {
        if !player.IsBot {
            continue
        }
        delta := computeDelta(player.Camp, winner)  // +100 / -100 / 0
        if delta == 0 && r.Status == "abandoned" {
            // abandoned: amount=0, tx_type=game_abandon_no_change 留痕
            walletSvc.ApplyTransaction(r.Ctx, player.BotUserID, 0, "game_abandon_no_change", r.ID, "werewolf", "对局<RoomID>异常中断")
        } else {
            walletSvc.ApplyTransaction(r.Ctx, player.BotUserID, delta, "model_game", r.ID, "werewolf", fmt.Sprintf("对局<%s>结算", r.ID))
        }
        
        // 更新 model_game_log
        logRepo.UpdateCoinDelta(r.GameLogs[seat], delta)
    }
}
```

### 3.2 结算金额表

| 对局结果 | 阵营 | 玩家角色示例 | 结算 |
|---------|------|------------|------|
| 村民胜 | 村民阵营 | 村民 / 预言家 / 女巫 / 猎人 / 白狼王 | **+100** |
| 村民胜 | 狼人阵营 | 狼人 / 白狼王 | **-100** |
| 狼人胜 | 狼人阵营 | 狼人 / 白狼王 | **+100** |
| 狼人胜 | 村民阵营 | 村民 / 预言家 / 女巫 / 猎人 | **-100** |
| abandoned | 任意 | 任意 | **0**（写 ledger `tx_type=game_abandon_no_change`） |

**注意**：暂定 ±100/局；不按 ante / 段位 / 角色动态调整。
**理由**：
- 狼人杀无 ante 概念（不同于象棋/德州有底注）
- 模型段位系统尚未设计（人类玩家段位在 `docs/中国象棋金币设计.md §2.3.2`）
- 后续如需动态化，可参考 `docs/中国象棋金币设计.md §2.3.1` 补贴系数表，按对局时间 / 角色难度做加权

### 3.3 走 `WalletService.ApplyTransaction` 规约

```go
// ServerGo/service/wallet_service.go（已存在）
func (s *WalletService) ApplyTransaction(
    ctx context.Context,
    userID string,
    amount int64,
    txType string,        // "model_game" | "game_abandon_no_change" | "admin_adjust" | ...
    refID string,         // 关联的业务 ID（房间号 / 对局号 / 订单号）
    gameKind string,      // "werewolf" / ""（admin_adjust 时为空）
    remark string,        // 审计说明
) error
```

**调用规约**：
- 必填 `refID = game_log_id`（来自 `t_lsm_game_model_game_log.id`）
- 必填 `gameKind = "werewolf"`（后续 5 款棋牌接入时分别填 `xiangqi` / `chess` / `junqi` / `doudizhu` / `texasholdem`）
- 必填 `remark` 格式：`对局<RoomID>结算` 或 `对局<RoomID>异常中断`
- `txType` 枚举：
  - `model_game` — 正常对局结算（amount != 0）
  - `game_abandon_no_change` — 异常中断（amount = 0，留痕）
  - `admin_adjust` — 管理员手动 adjust（amount 可正可负）
  - `register_reward` — 注册奖励（模型 seed 1000 沿用此 txType，与人类一致）

### 3.4 idempotency 保证（v2.0 修正）

> ⚠ v1.0 曾声称结算走唯一键幂等，审计发现该唯一键**并不存在**（详见
> [`docs/狼人杀13人局金币系统设计.md`](狼人杀13人局金币系统设计.md) §9 DEFECT 2）。以下为 v2.0 真实机制：

- **真实防重三层**：房间级 `gameOverNotified` 内存标志 + **`UNIQUE(user_id, ref_type, ref_id, tx_type)`**
  结算幂等唯一键（v2.0 新增，**必须含 `user_id`**——一局多人各写一条，缺 user_id 会撞键误吞）+
  `Credit/Debit` 对 duplicate-key 的「良性 no-op（视为已结算）」。
- 即使对局结束流程被 watchdog / restart 触发多次（含跨进程重启），结算也只生效一次。
- 多次失败的「补单」由 admin 手动调 `admin_adjust` 完成（不走结算 tx_type）。

### 3.5 失败行为

| 失败位置 | 行为 |
|---------|------|
| `ApplyTransaction` 内部 DB 异常 | **仅 log，不阻塞**；`game_over` 已广播，玩家已离场 |
| 后续 admin 查 wallet | 看到 `t_lsm_game_wallet.balance` 仍是结算前余额 |
| 后续 admin 在 GameLogPage 查对局 | 看到 `coin_delta=0` |
| **补救** | admin 手动调 `POST /api/admin/llm/bots/:botUserID/wallet/adjust` 补单 |

详见 §7 失败与回滚。

## 4. Admin 手动调整

### 4.1 端点

```
POST /api/admin/llm/bots/:botUserID/wallet/adjust
Content-Type: application/json
Authorization: Bearer <super token>

Request:
{
  "amount": 500,        // 必填，int64；正数=加，负数=减；0=无效
  "remark": "对局R-123结算补单"  // 必填，最长 255 字
}

Response 200:
{
  "code": 0,
  "data": {
    "user_id": "bot-user-uuid",
    "balance_before": 900,
    "balance_after": 1400,
    "amount": 500,
    "tx_id": "tx-uuid"
  }
}
```

### 4.2 鉴权

| 角色 | 是否允许 |
|------|---------|
| `super` | ✅ |
| `admin` | ❌ 返回 `ErrBotWalletAdjustForbidden = 30021` |
| `user` | ❌ 返回 `ErrForbidden` |

**硬约束**：admin 角色**不可**手动 adjust 钱包，仅 super 可。
**理由**：防止 admin 误改 bot 余额（即便是有意为之，super 仍需审计）。

### 4.3 走账规则

- **必须**走 `WalletService.ApplyTransaction`，**禁止**任何路径直接 `UPDATE balance`
- 必填 `tx_type=admin_adjust`
- 必填 `ref_id = t_lsm_game_wallet_tx` 自生成 UUID
- 必填 `game_kind=""`（admin adjust 与游戏无关）
- 必填 `remark` —— 写入 `t_lsm_game_wallet_tx.remark`，前端展示 + 审计追溯

### 4.4 BalanceAfter 校验

`ApplyTransaction` 内部对 `balance_after` 做严格校验：
- `balance_after = balance_before + amount`
- 若不一致 → 返回 `ErrWalletBalanceMismatch`，**回滚**事务
- 防止并发场景下 `t_lsm_game_wallet.balance` 与 ledger 失同步

### 4.5 并发安全

- `t_lsm_game_wallet` 用 `version` 字段做乐观锁
- `ApplyTransaction` 内部循环重试（最多 3 次），最后一次失败返回明确错误
- admin 在前端需做「提交期间禁用按钮」UI 约束

### 4.6 审计

- 所有 `admin_adjust` 流水可在 `ModelDetailPage` 「💰 钱包」区块看到
- 流水显示：`time` / `type=admin_adjust` / `amount` / `balance_after` / `remark`
- 长期：后台审计报表每日 00:30 UTC 统计 `admin_adjust` 总和，与人工授权记录对账

## 5. 流水审计

### 5.1 复用 `t_lsm_game_wallet_tx`

不新建表，所有模型玩家流水自动写入现有的 `t_lsm_game_wallet_tx`（人类玩家也在用）。

```go
// 已有字段（核心）
type TLsmGameWalletTx struct {
    ID            string    `json:"id"`
    UserID        string    `json:"user_id"`
    Amount        int64     `json:"amount"`         // +/-
    BalanceBefore int64     `json:"balance_before"`
    BalanceAfter  int64     `json:"balance_after"`
    TxType        string    `json:"tx_type"`        // model_game / admin_adjust / ...
    RefID         string    `json:"ref_id"`         // 关联业务 ID
    GameKind      string    `json:"game_kind"`      // werewolf / "" / ...
    Remark        string    `json:"remark"`
    CreatedAt     time.Time `json:"created_at"`
}
```

### 5.2 不可变账本保证

- `t_lsm_game_wallet_tx` **append-only** —— 任何代码路径都不允许 UPDATE / DELETE
- 物理删除由 DB 约束保护（建议加 trigger 或在 service 层强制）
- 历史流水永久保留（即使模型被 disable / bot user 被重命名）

### 5.3 前端展示

- `ModelDetailPage` 「💰 钱包」区块：最近 20 条流水
- 字段：time / type / amount（带 +/- 颜色）/ balance_after / remark
- 暂不做时间筛选 / 类型筛选（MVP 阶段；后续可加）
- 跳转：点单条流水 → 跳到关联的 GameLogPage（若 `ref_id` 是 game_log_id）

### 5.4 后台审计（后续专项）

- 每日 00:30 UTC 统计：
  - `t_lsm_game_wallet_tx` 中 `tx_type='model_game'` 当日总 amount
  - `tx_type='admin_adjust'` 当日总 amount
  - 校验所有 `balance_after` 与 `t_lsm_game_wallet.balance` 一致
- 异常 → 发邮件给 super 角色

## 6. 与 5 款游戏金币体系的关系

### 6.1 本期接入范围

| 游戏 | 接入 | 备注 |
|------|------|------|
| **狼人杀** | ✅ 本期接入 | 唯一有 bot 玩家的游戏，结算 ±100/局 |
| 象棋 / 国际象棋 / 军棋 / 斗地主 / 德州 | ❌ 本期不接入 | 无 bot 玩家，Agent 模块暂未对接 |

### 6.2 后续接入规约

5 款棋牌后续接入模型时：

- **每款独立 `tx_type` 标识**：
  - `xiangqi_game` / `chess_game` / `junqi_game` / `doudizhu_game` / `texasholdem_game`
  - 不复用 `model_game`（避免统计混乱）
- **每款独立 `game_kind` 字段**：与人类玩家对局一致
- **结算金额**：
  - 象棋 / 国际象棋 / 军棋：参考各自金币设计档的人类 ante 体系（如象棋 ante=50 → 胜+50/负-50）
  - 斗地主 / 德州：参考各自金币设计档（斗地主 5% 抽水 / 德州 5% 赢家抽水）
- **接入流程**：
  1. `model_coin_settle_<game>.go` 仿照 `ServerGo/game/werewolf/activity_emitter.go` 改造
  2. 加 `tx_type` 到 `wallet_service.go` 的 enum
  3. 加 `game_log_api.go` 的 `game_kind` 筛选支持
  4. 加单元测试 + 集成测试

### 6.3 与人类玩家金币体系的不变量

| 不变量 | 含义 |
|--------|------|
| 钱包表 schema 统一 | `t_lsm_game_wallet` / `t_lsm_game_wallet_tx` 一张表都不为模型改字段 |
| 双簿记 | 所有变动走 `WalletService.ApplyTransaction` |
| 不可篡改 | 流水 append-only |
| 0 系统抽成（MVP） | 5 款棋牌均如此（详见各自金币设计档）；模型玩家也按 0 抽成 |
| 禁用 P2P 转账 | 模型之间不能转账（无 API 支持） |

## 7. 失败与回滚

### 7.1 失败行为表

| 失败位置 | 行为 | 后续 |
|---------|------|------|
| `EmitGameOver` 结算时 DB 异常 | **仅 log，不阻塞** | admin 手动补单 |
| `ApplyTransaction` 内部乐观锁失败 3 次 | 返回错误，但游戏流继续 | 重试到成功为止（后台 cron） |
| `admin_adjust` 时 `balance_after` 校验失败 | **回滚事务** | admin 重新提交（极少见） |
| 玩家在 `ModelGameLogPage` 查 coin_delta=0 | UI 显示「⚠ 结算失败」徽章 | 引导 admin 补单 |

### 7.2 补单流程

1. admin 在 `ModelGameLogPage` 看到对局 `coin_delta=0` + 提示
2. 点「🔧 补单」按钮 → 弹窗显示：
   - 推荐 amount（基于对局结果自动算）
   - 必填 remark（如「R-123 狼人胜村民阵营结算补单」）
3. 提交 → `POST /api/admin/llm/bots/:botUserID/wallet/adjust`
4. 走 `tx_type=admin_adjust` 流水，**不**走 `model_game`（避免与可能成功的重试结算重复）

### 7.3 后台 cron 重试（后续专项）

- 每日 02:00 UTC 跑 `ServerGo/scripts/retry_failed_settlements.sh`
- 扫 `t_lsm_game_model_game_log` 中 `coin_delta=0` + `ended_at` 非空 + `result` 非 abandoned 的行
- 调 `WalletService.ApplyTransaction`，成功后 UPDATE `coin_delta`
- 失败超过 3 次 → 发邮件给 super

### 7.4 不阻塞游戏流的关键代码约束

- `activity_emitter.go::EmitGameOver` 内 `go func() { defer recover(); settle(...) }()`
- `settle` 内每个 bot 玩家单独 try/catch，单个失败不影响其他
- 任意 panic / error → log 后继续
- **绝不**因为结算失败让 `game_over` 广播卡住

### 7.5 模型 disable / 删 bot 用户的余额处理

- 软删除模型（`Enabled=false`）—— **不**清零余额，**不**冻结 wallet
- 物理删除 bot user（极少见，需 super + 多步确认）—— 余额归零，写 ledger `tx_type=user_deletion_zero_out`
- 永远不删 `t_lsm_game_wallet` 行（append-only 流水依赖 user_id 外键）

## 8. 关键数值摘要

| 项目 | 值 | 说明 |
|------|---|------|
| **注册 seed** | 1000 金币 | 沿用 `TLsmGameWallet` default |
| **对局胜方** | +100 金币 | 狼人杀先行 |
| **对局败方** | -100 金币 | 狼人杀先行 |
| **对局 abandoned** | 0 金币 | 写 ledger `tx_type=game_abandon_no_change` 留痕 |
| **admin adjust 权限** | super only | admin 也不可 |
| **admin adjust 必填** | amount + remark | remark 最长 255 字 |
| **流水表** | `t_lsm_game_wallet_tx` | 复用，append-only |
| **tx_type 枚举** | model_game / game_abandon_no_change / admin_adjust / register_reward | 后续 5 款棋牌各加独立 tx_type |
| **失败行为** | log 不阻塞 | 后台 cron 重试 / admin 手动补单 |
| **系统抽成（MVP）** | 0 | 与人类玩家一致 |
