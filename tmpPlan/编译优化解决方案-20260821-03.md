# 编译优化解决方案 — GitHub Actions CI 三 Job 全红修复

> 日期：2026-08-21 · 编号：20260821-03
> 范围：`.github/workflows/ci.yml` · `proto/gen.sh` · `ClientWeb/src/styles/` · `ServerGo/game/werewolf/` · `scripts/ci/check_line_limit.sh`
> 硬约束：`rebuild_restart_app.sh` 核心能力（前端构建 → 静态拷贝 → 清缓存 → ldflags 注入 → 杀旧进程 → 健康检查 + 版本号校验）**一字不改**。

---

## 1. 问题现象

GitHub Actions CI #48 三个 Job 全部失败（总耗时仅 25 秒，属于「起步即崩」，非业务逻辑跑崩）：

| Job | 失败时长 | 表象 |
|---|---|---|
| ServerGo (build + test) | 19s | Go 编译/测试失败 |
| ClientWeb (typecheck + build) | 21s | tsc 类型检查/构建失败 |
| Project conventions | 7s | 项目规范校验失败 |

## 2. 本地复现与根因分析（全面排查）

按 CI 原命令逐条本地复现（今日 HEAD `13e7db5`）：

| CI 步骤 | 本地命令 | 结果 |
|---|---|---|
| go build | `cd ServerGo && go build -o /tmp/x main.go` | ✅ 通过 |
| go vet | `go vet ./...` | ✅ 通过 |
| go test | `go test ./... -count=1` | ✅ 通过（exit 0） |
| tsc | `npx tsc -b --noEmit` | ✅ 通过 |
| build | `npm run build` | ✅ 通过 |
| 规范检查 | `bash scripts/ci/check_line_limit.sh` | ❌ **本地即失败**（2 项违规） |

本地全绿但 CI 全红 → 差异一定来自「checkout 之后的文件集合不同」或「工具链版本不同」。逐项排查：

### 2.1 根因 A（ServerGo Job）：生成产物被 gitignore，CI checkout 缺失

`.gitignore` 排除了 `ServerGo/proto/pb/`（protobuf 生成代码），但**已提交的源码**大量 import 该目录：

```
ServerGo/ws/client.go / proto_router.go / proto_codecs.go … import "LsmAgentGame/proto/pb/…"
```

本地这些 `.pb.go` 由 `proto/gen.sh` 生成后常驻工作区，所以本地编译通过；CI 全新 checkout 里该目录**根本不存在**，`go build` 在几秒内以「找不到包」编译错误失败 —— 与 19 秒快速失败的现象吻合。

### 2.2 根因 B（ClientWeb Job）：同源问题（TS 侧生成产物）

`.gitignore` 同样排除 `ClientWeb/src/proto/`，而 `services/ws.ts`、`services/protoRegistry.ts` 等已提交文件 import 该目录。CI checkout 缺失 → `tsc -b --noEmit` 批量报「Cannot find module」—— 与 21 秒快速失败吻合。

> 验证：`git ls-files ServerGo/proto/`、`git ls-files ClientWeb/src/proto/` 均为空；本地文件存在。

### 2.3 根因 C（Project conventions Job）：§4 行数违规（本地可复现）

```
❌ [超出 §4 上限]   ClientWeb/src/styles/werewolf-v2.css: 1813 行 > 1800 行
❌ [baseline 恶化]  ServerGo/game/werewolf/agent_runner.go: 2058 行 > 登记上限 1982 行
```

- `werewolf-v2.css`：历史拆分后又被后续批次写回 1813 行（globals.css 注释里已有多次同款拆分记录）。
- `agent_runner.go`：登记基线 1982，当前 2058，恶化 76 行（§4 白名单只允许变短）。

### 2.4 已排除的兼容性问题（重要：这些不是根因）

| 怀疑点 | 排查手段 | 结论 |
|---|---|---|
| Go 工具链版本差（本地 1.26.4 / CI 按 go.mod 装 1.25.0） | `GOTOOLCHAIN=go1.25.0 go build / go vet` | ✅ 1.25.0 下 build+vet 均通过，版本差无害 |
| CI 无 MariaDB → go test 挂 | 阅读相关测试 | ✅ DB 依赖测试均有 build tag（`walletintegration`/`llmintegration`）隔离 + `t.Skip` 兜底 |
| CI 无 `LsmAgentGame.conf` → config.Load panic | 阅读 `config/config.go:Load` | ✅ §config-auto-bootstrap：缺文件时自动从默认值生成，CI 沙箱可跑 |
| `package-lock.json` 未入库（ci.yml 注释如此声称） | `git ls-files` | ⚠️ **注释已过时**：lockfile 实际已入库（迁移提交 b67ebb3 带入），且与 package.json 同步（`npm ci --dry-run` 通过）。注释需修正，避免误导后续维护 |
| lockfile 的 `resolved` 指向国内镜像 npmmirror.com，CI 在海外拉不下来 | 分析 npm 行为 | ✅ 保留 `npm install`（而非 `npm ci`）：npm ≥ 8 会把异源 resolved 重写到当前 registry（runner 默认 npmjs.org），国内外网络双兼容 |

## 3. 修复方案

### 方案 A — CI 增加 proto 生成步骤（治根因 A/B）

原则：`.proto` 源文件是唯一事实来源（CLAUDE.md 既有政策），**不**把生成产物入库，改为在 CI 里现场生成。

1. **`proto/gen.sh` 增加可选参数**（向后兼容）：
   - `bash proto/gen.sh` / `all` —— 生成 Go + TS（现状，本地开发用）
   - `bash proto/gen.sh go` —— 仅 Go（CI backend Job 用，无需 node_modules）
   - `bash proto/gen.sh ts` —— 仅 TS（CI frontend Job 用，无需 protoc-gen-go）
   - 参数只影响「检查哪些插件 + 跑哪段生成」，清理/收集/统计逻辑不变。
2. **ci.yml backend Job** 在 setup-go 之后插入：
   - 安装 protoc **v28.3**（与本地 `/tmp/protoc` 版本完全一致，从 GitHub Releases 下载 zip 解压；runner 在github 侧网络访问 github.com 无障碍）
   - `go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.34.2`（**钉死**与 go.mod 中 `google.golang.org/protobuf v1.34.2` 同版本，避免生成代码与运行时库版本漂移；runner 走默认 proxy.golang.org）
   - `bash proto/gen.sh go`
3. **ci.yml frontend Job** 在 npm install 之后插入：
   - 安装同款 protoc v28.3
   - `bash proto/gen.sh ts`（`@protobuf-ts/plugin` 已在 devDependencies，npm install 后可用）

> 已本地验证：`proto/gen.sh` 全量再生产物与现工作区**逐字节一致**（md5 全同），生成步骤确定性可靠。

### 方案 B — werewolf-v2.css 拆分（治根因 C-1）

严格遵循 CLAUDE.md §4 + §2.1 硬约束 #4（`globals.css` 的 `@import` 顺序不可调整）：

- 新建 `werewolf-v2-base.css`（原文件第 1–1275 行，整段搬移）与 `werewolf-v2-ext.css`（原文件第 1276–1813 行，「LLM 调用相位状态机指示器」起的整块，段边界干净）。
- `werewolf-v2.css` 变为纯入口（§4 规定的形态），仅含两行按原级联顺序的 `@import`。
- `globals.css` **完全不动**：`werewolf.css → werewolf-v2.css → werewolf-emotion.css → werewolf-speech.css` 覆盖链中，werewolf-v2.css 的展开内容顺序不变，同优先级选择器覆盖链零回归。
- **零回归验证**：拆分前后各跑一次 `npm run build`，`dist/assets/index-*.css` 必须字节一致（内容哈希不变）。

### 方案 C — agent_runner.go 纯搬移（治根因 C-2）

§4 规定：Go 拆到同 package 多个 `snake_case.go`，纯代码搬移、不改逻辑/签名。

- 新建 `ServerGo/game/werewolf/agent_runner_whisper.go`，搬入 4 个私聊/插话通道方法（主题内聚「私语通道」，合计约 330 行）：
  - `WolfWhisper`（狼队密语）
  - `WolfpackAssign`（狼队分工重排，WolfPack 系统留言通道）
  - `Whisper`（对活人私聊）
  - `Interject`（插话）
- `agent_runner.go` 从 2058 → 约 1720 行，**降到 1800 以下**。
- 同步修正两文件 import 块（搬移后各自只留用到的包）。
- `scripts/ci/check_line_limit.sh` 的 BASELINE 删除 `agent_runner.go` 条目（已回落到硬上限内，债务清零；其余 3 条登记债务不动）。

### 方案 D — ci.yml 过时注释修正 + 国内外网络兼容说明

- 修正「没有提交 package-lock.json」的过时注释：lockfile 已入库，`npm install` 保留的理由是——lockfile 的 `resolved` 指向国内镜像 `registry.npmmirror.com`（本地 `rebuild_restart_app.sh` 的 `npm ci` 靠它在国内网络稳定工作），而 npm ≥ 8 的 `npm install` 会把异源 resolved 重写到 runner 默认 registry（npmjs.org），**GitHub 海外 runner 与国内开发机各走各的稳定源**。若改 `npm ci` 则强制走 resolved URL，海外 runner 直连国内镜像偶发不稳，故不用。
- 在 workflow 头部补一段「网络环境兼容」注释，说明各依赖源的选择依据。

### 方案 E — 不动项（明确保留）

| 项 | 决定 | 理由 |
|---|---|---|
| `rebuild_restart_app.sh` | **一字不改** | 用户硬约束；且其 `npm ci`（npmmirror resolved）与 `go mod tidy`（GOPROXY=goproxy.cn）本就适配国内网络 |
| 本地 `GOPROXY=https://goproxy.cn,direct` | 不动（环境级） | 已验证 go1.25.0 toolchain 经此代理可正常下载 |
| 本地 npm registry=npmmirror | 不动（~/.npmrc） | 同上 |
| `.gitignore` 对 proto 产物的排除 | 不动 | 维持「.proto 源为唯一事实来源」政策，CI 现场生成即可 |
| 其余 3 条 BASELINE 债务文件 | 不动 | 未恶化，属独立重构提交范围，不与本批次混 |
