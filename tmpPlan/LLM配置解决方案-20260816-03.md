# LLM 模型配置 —— 测试数据污染生产库 + 删除功能失真 解决方案

> 编号：§20260816-03
> 日期：2026-08-16
> 触发：用户在 `🤖 LLM 模型管理` 页删除了 7 条测试记录，重启后记录**全部重现**。
> 结论：**两个独立缺陷叠加**，一个把测试数据写进了生产库，另一个让「删除」变成一场幻觉。

---

## 0. 结论速览

| # | 缺陷 | 严重级 | 一句话根因 |
|---|------|--------|-----------|
| **P0-1** | Go 集成测试直连生产 `lsmDB` 写入测试行，且清理**静默失败** | P0 | `defer cancel()` 在 `t.Cleanup` **之前**执行 → 清理时 ctx 已 canceled → `DELETE` 全部失败，错误被 `_ =` 吞掉 |
| **P0-2** | 「删除」是软删除，但列表接口**不过滤** `enabled=0` | P0 | `ListProviders` 裸 `Find(&rows)` 无 `Where("enabled")`；前端乐观移除本地行并弹「已删除」，刷新即重现 |

两者叠加后的用户观感：**「测试数据凭空出现，而且删不掉」**。

## 1. P0-1 —— 测试数据是怎么进生产库的

### 1.1 测试直连生产库

`ServerGo/llm/registry_integration_test.go:99-113`：

```go
func newRegistryIntegrationDB(t *testing.T) *gorm.DB {
	ensureChdirProjectRoot()
	cfg := config.Load()          // ← 读真实 LsmAgentGame.conf
	gormDB, err := db.Init(cfg)   // ← 连的就是 127.0.0.1:3306/lsmDB 生产库
	if err != nil {
		t.Skipf("SKIP: cannot connect to DB: %v", err)
	}
	registryIntegrationDB = gormDB
	return gormDB
}
```

`ensureChdirProjectRoot()` 会向上找到项目根的 `LsmAgentGame.conf`，于是**测试一跑就是对生产库做读写**。

> **订正**：这两个测试文件从创建之初（`75fa2e5`，2026-08-13）就带着
> `//go:build llmintegration` 标签，所以 `go test ./...` **不会**触发它们。
> 污染来自那次刻意执行的 `go test -tags llmintegration ./llm/...`。
> 结论不变（测试确实写了生产库），但归因要准确：门禁缺的不是 build tag，
> 而是「即使显式带 tag，也不该默认打生产库」这一层。
测试用 `uniqueModelSuffix(t)` = `t.Name() + 时间戳` 生成 model key，这正是 DB 里那些
`mt_TestMigrateConfigProvidersToDB_Insert` / `dbmodel_TestNewRegistry_LoadFromDB_OverridesConfig_214249.131`
的来源 —— **表名即函数名，铁证**。

### 1.2 清理为什么没生效（真正的根因）

每个测试都是这个形状：

```go
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()                                    // ← ①
...
t.Cleanup(func() {                                // ← ②
	_ = gormDB.WithContext(ctx).                  // ← ③ 用的是同一个 ctx
		Where("id = ?", row.ID).
		Delete(&models.TLsmGameLlmProvider{}).Error  // ← ④ 错误被 `_ =` 丢弃
})
```

Go 的执行顺序是 **`t.Cleanup` 晚于 `defer`**（Cleanup 在测试函数返回*之后*才由 testing 框架调用，
而 `defer cancel()` 在函数返回时就已执行）。已用最小复现实验证明：

```go
func TestOrder(t *testing.T){
  ctx,cancel:=context.WithTimeout(context.Background(),5*time.Second)
  defer cancel()
  t.Cleanup(func(){ t.Logf("ctx.Err()=%v", ctx.Err()) })
}
// 实测输出：CLEANUP sees ctx.Err()=context canceled  <-- ctx ALREADY CANCELED
```

于是 ④ 的 `DELETE` **必然**返回 `context canceled`，一行都删不掉；
而 `_ =` 把这个错误彻底吞掉，测试**照常 PASS**，作者永远看不到清理失败。

**受影响清理点共 7 处**：
- `llm/migrate_test.go:93` / `:165` / `:255`
- `llm/registry_integration_test.go:156` / `:237` / `:353` / `:443`

全部是同一模式，无一例外。

### 1.3 为什么 `remark` 会被改写、`updated_at` 是今天

DB 里的测试行 `remark` 多为
`metadata-only update from LsmAgentGame.conf (api_key preserved from DB)`，
但 `LsmAgentGame.conf` 的 `llm.providers` 实测为 `null`（已确认），
`MigrateConfigProvidersToDB` 开头就 `if len(cfg.Providers)==0 { return }` 直接返回 —— 说明
**这些 remark 是 2026-08-13 测试运行当时写下的**（测试自己构造了 `cfg.Providers`），不是启动时写的。

而 `updated_at = 2026-08-16 11:40~11:41`（今天）**正是用户点击「删除」的时刻** —— 见 P0-2。

## 2. P0-2 —— 「删除」为什么删不掉

### 2.1 后端：软删除（设计如此）

`ServerGo/api/model_admin_api.go:717-745`：

```go
// Soft delete: sets enabled=false instead of physically removing the row.
// Keeps the audit trail intact ...
res := h.gormDB.WithContext(c.Request.Context()).
	Model(&models.TLsmGameLlmProvider{}).
	Where("id = ?", id).
	Updates(map[string]any{"enabled": false})
```

软删除本身是**合理设计**（`t_lsm_game_model_game_log.provider_id` 有审计外键语义，
且飞行中的 7-AI 房间不能被硬删除打断）。注意表结构**没有** `deleted_at` 列，
`enabled` 就是唯一的删除标记。

用户的删除**确实执行成功了** —— 实测 7 行全部 `enabled=0`，`updated_at` 精确落在
`11:40:47 ~ 11:41:07`，与用户操作时刻一一对应。

### 2.2 列表接口不过滤 —— 这才是「重现」的原因

`ServerGo/api/model_admin_api.go:274-277`：

```go
var rows []models.TLsmGameLlmProvider
if err := h.gormDB.WithContext(c.Request.Context()).
	Order("created_at ASC").
	Find(&rows).Error; err != nil {   // ← 无 Where("enabled = ?", true)
```

软删除的行**照常全量下发**。所以：删除 → 后端置 `enabled=0` → 刷新 → 列表又把它读回来。

### 2.3 前端乐观移除 —— 制造「删除成功」的假象

`ClientWeb/src/store/modelAdmin.store.ts:116-125`：

```go
await api.deleteProvider(id);
set((s) => ({
  providers: s.providers.filter((p) => p.id !== id),   // ← 本地移除
  toast: '已删除',                                      // ← 弹成功
```

前端**不重新拉列表**，只在本地数组里过滤掉，并弹「已删除」。
于是当次页面看起来干干净净，一刷新/重启全部回来 —— 与用户描述完全吻合。

### 2.4 完整因果链

```
测试写入 7 行 (P0-1)
   └→ 清理静默失败，行永久留在生产库
        └→ 用户在 UI 点删除
             ├→ 后端 enabled=0（成功，但只是软删除）
             ├→ 前端本地过滤 + 弹「已删除」  ← 假象在此产生
             └→ 刷新/重启 → ListProviders 不过滤 → 7 行重现
```

补充：`populateLocked`（`registry.go:1155`）会把 `enabled: row.Enabled` 带进内存，
`Get()` 对 `enabled=false` 会拒绝（`registry.go:555`），所以这些行**不会**被真的用于对局；
纯粹是**管理页可见性**问题。但可见即困扰，且违反 §7.1「操作结果必须真实可见」。

## 3. 修复方案

### U1 —— 测试彻底不碰生产库（P0-1 主修）

**三层防御，缺一不可：**

1. **默认跳过（最重要）**：`llmintegration` build tag 只能挡住不带 tag 的运行，
   挡不住「刻意带 tag 但忘了切库」——本次事故正是如此。因此在 tag 之外再加
   一道运行期门禁：
   ```go
   if os.Getenv("LSM_TEST_ALLOW_DB") != "1" {
       t.Skip("SKIP: DB integration test; set LSM_TEST_ALLOW_DB=1 to run")
   }
   ```
   于是 `go test -tags llmintegration ./llm/...` 默认也只是 skip，不再写任何库。

2. **拒绝生产库名**：即使开了开关，也校验目标 DB 不是生产 schema：
   ```go
   if cfg.Database.Name == "lsmDB" && os.Getenv("LSM_TEST_FORCE_PROD_DB") != "1" {
       t.Skip("refuse to run DB tests against production schema lsmDB")
   }
   ```
   建议配套提供 `lsmDB_test` schema 供本地集成测试使用。

3. **清理必须用独立 ctx + 断言错误**：新增测试辅助
   ```go
   // cleanupProviderRows 用独立的 context —— 绝不能复用测试主 ctx，
   // 因为 defer cancel() 早于 t.Cleanup 执行（§20260816-03 P0-1）。
   func cleanupProviderRows(t *testing.T, gormDB *gorm.DB, where string, args ...any) {
       t.Helper()
       t.Cleanup(func() {
           ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
           defer cancel()
           if err := gormDB.WithContext(ctx).Where(where, args...).
               Delete(&models.TLsmGameLlmProvider{}).Error; err != nil {
               t.Errorf("cleanup failed (残留测试数据!): %v", err)  // ← 不再吞
           }
       })
   }
   ```
   把 7 处 `t.Cleanup` 全部换成它。**错误必须 `t.Errorf`** —— 清理失败即测试失败，
   这是唯一能让「污染」立刻暴露的方式。

4. **统一测试前缀 + 兜底清理**：所有测试 model key 统一加 `zztest_` 前缀，
   并在 `TestMain` 退出前按前缀兜底清一次，防止 `t.Fatal` 提前返回漏掉个别行。

### U2 —— 列表过滤软删除行（P0-2 主修）

`ListProviders` 默认只返回 `enabled=true`，并支持 `?include_disabled=1` 显式查看：

```go
q := h.gormDB.WithContext(ctx).Order("created_at ASC")
if c.Query("include_disabled") != "1" {
    q = q.Where("enabled = ?", true)
}
```

保留 `include_disabled` 是为了运维仍能找回误删的行（软删除的价值所在）。

### U3 —— 提供真正的硬删除

软删除挡不住「测试脏数据」这类**本就不该存在**的行。新增
`DELETE /api/admin/llm/providers/:id?hard=1`（**super admin 限定**）：

- 先检查引用：`t_lsm_game_model_game_log` / `t_lsm_game_model_chat_message` 是否有
  `provider_id` 指向它；
- **有引用** → 拒绝硬删（409），提示改用软删除，保护审计链（§118）；
- **无引用** → 连同 `t_lsm_game_user` 里的 bot user 一并物理删除。

实测本次 7 行测试数据在两张日志表中引用数**均为 0**，且无关联 bot user，可安全硬删。

### U4 —— 前端删除后强制对账

- 删除成功后**重新 `fetchProviders()`**，不再只做本地 `filter`；
- 文案按后端返回区分：`soft:true` → 「已停用（软删除）」，`hard:true` → 「已彻底删除」；
- 提供「显示已停用」开关（对应 `include_disabled=1`），让软删除行**可见可恢复**，
  而不是既看得见又删不掉。

### U5 —— 清理现存 7 行脏数据

一次性 SQL（已核对无引用、无 bot user）：

```sql
DELETE FROM t_lsm_game_llm_provider
 WHERE model LIKE '%Test%'
   AND id NOT IN (SELECT DISTINCT provider_id FROM t_lsm_game_model_game_log WHERE provider_id IS NOT NULL);
```

### U6 —— 机制化防复发（对齐 §20260812-04 U6 / §20260813-04 U5）

**收口到单一助手 + 兜底网**，而不是靠每个作者自觉写对 ctx：

- 所有清理**只能**走 `cleanupProviderRows`（自建 ctx + 失败 `t.Errorf`），
  7 处旧写法全部替换，包内不再有第二种清理写法；
- `TestMain` 按 `zzt_` 前缀兜底扫尾，**删除行数非零就打印 WARNING**
  并让整包测试失败 —— 「有测试没管好自己」必须被看见；
- 硬删除权限门禁由 `api/model_admin_delete_test.go` 4 项断言锁定。

> **原计划的 AST lint 未实施**。理由：本缺陷的根因是「7 处各写一遍清理」，
> 收口成唯一助手后，「复用外层 ctx」这种写法已无处容身 —— 消除模式本身
> 比检测模式更彻底。若后续再出现第二种清理写法，再补 AST lint 才划算。
> 这里如实记录，避免文档承诺了未落地的护栏（正是 §130「声明了却从不接线」）。

## 6. 教训（待并入 CLAUDE.md §13）

1. **`defer cancel()` 早于 `t.Cleanup` —— 这是 Go 测试清理的头号陷阱。**
   凡在 `t.Cleanup` 里做 DB/网络 I/O，**必须自建 context**，绝不复用测试主 ctx。
2. **`_ = xxx.Error` 是最有效的缺陷伪装。** 清理失败静默 → 测试 PASS → 污染累积一整个版本。
   **清理失败必须 `t.Errorf`**，让污染在产生的那一刻就 FAIL。
3. **测试连生产库这件事本身必须默认不可能**，而不是靠作者自觉。
   环境变量门禁 + schema 名黑名单是唯一可靠的护栏。
4. **软删除必须配套「列表过滤 + 可见开关」三件套。**
   只做软删除不改列表 = 用户眼里的「删不掉」；这是 §7.1「操作结果必须真实可见」的镜像违规。
5. **前端乐观更新在「删除」语义上是有害的。** 乐观移除 + 不 refetch，把后端的部分成功
   渲染成完全成功，刷新即打脸。**删除类操作必须以服务端为准重新对账。**
6. **软删除不是万能** —— 对「本就不该存在」的脏数据必须提供硬删除通道，
   否则运维只能手工 SQL（而手工 SQL 才是真正危险的）。
7. **脏数据会把测试变成永久失败** —— 残留行让 `migrate` 走 update 而非 insert 分支，
   `inserted=1` 断言从此必败。实测确认：清理生效前该测试 FAIL，清理后才 PASS。
   **清理失效不只是「脏」，它会连带毁掉测试的可重复性。**
8. **唯一索引 + 硬编码 fixture 名 = 定时炸弹** —— `agent_name` 有 UNIQUE 索引，
   而测试里硬编码 `"Reload"` / `"DB Agent"`。它们从没炸过，只因为上一轮的残留行
   恰好同名同内容；**清理一旦真的生效，第二次运行立刻 Duplicate entry**。
   本次一并改为带唯一 token（`testAgentName`）。
9. **唯一 token 必须放在会被保留的一端** —— `model` 是 varchar(64)，
   「测试名 + 时间戳」超长后截断会**把尾部时间戳切掉**，跨次运行 key 反而重复。
   改为**时间戳在前**才真正唯一。
10. **「整表语义」测试跑共享库永远不可能通过** —— 断言「DB 空 ⇒ seed 8 行」的测试，
    在有 10 行真实模型的库上必败。诚实做法是 `requireEmptyProviderTable` 显式 skip
    并说明需要独立 schema，**而不是放宽断言把测试变成永远为真的空壳**。
